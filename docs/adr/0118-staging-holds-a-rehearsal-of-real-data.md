# ADR-0118：staging 放真資料的預演，切換那天不搬

日期：2026-10-05
狀態：已接受
推翻：`.scratch/PRODUCTION_AUDIT.md` §3.2 的原則「永遠不要把正式資料倒進 staging」（原文留著，旁邊加了一句）

## 背景

staging 從一開始放的是 `scripts/seed-staging.mjs` 種出來的二十位假客戶。§3.2 的理由有兩個：匿名化腳本會漏欄位
（漏一個就是真名進了另一個資料庫）、把正式資料倒出來的那個檔案本身是風險。那兩個理由的前提是
**正式站已經有真資料、staging 要一份可以亂點的**。

2026-10-05 前提反過來了：正式站還沒記過任何真東西（9/28 定的：切換前 app 不記真的東西、切換那天一次匯進去），
而她要在切換前看「合併檔匯進去長什麼樣」—— 本機模擬器她點不到，staging 是唯一點得到的地方。

她的原話：

> **staging 改成放真實資料**（我決定的，代價我聽過了）
>
> staging 上那二十位種子假客戶要先清掉，我才貼合併檔；`npm run seed:staging` 之後不能隨手跑。
>
> **從此 staging 的畫面上有真名**：你在 staging 上測試時，截圖、驗收清單、PR 內文一個真名都不能帶。

問她 staging 上記的東西切換時要不要搬過去：

> 7. 不搬，staging 只當預演。切換那天正式站重新匯一次合併檔

## 決定

1. **staging 放真資料的預演。** 她把合併檔貼進去看；切換那天正式站重新匯一次，staging 上記的東西不搬。
   沒有匿名化這一步 —— 合併檔本來就是她自己的資料，不是從正式站倒出來的
2. **預演可以整份丟掉重來**：`scripts/reset-staging.mjs`（`npm run staging:reset`）清掉備份裡有的每一類資料
   （範圍直接讀 `restore-backup.mjs` 的 `SECTIONS`）與 Storage 上療程單的照片，留下主檔、設定、白名單、稽核、AI 用量。
   只認 staging 與模擬器；正式站一律拒絕，**沒有放行的旗標**
3. **假資料只種在本機模擬器**：`seed-staging.mjs` 每跑一次會把種子主檔整份寫回去，所以那個專案裡只要有一位不是種子建的客戶就拒絕（`refuseReason()`）
4. **橫幅照舊寫「測試環境」**，說明那一句改成「資料是真的，但這裡只是預演 —— 切換那天不會搬過去」
5. **還原演練只對著模擬器**：`--wipe` 會把備份裡沒有的那幾筆標成已刪除，對著 staging 演練一次就把預演弄亂了
6. **驗收換地方**：會寫入資料的驗收步驟在本機模擬器走；staging 給她點。staging 上測試時，截圖、驗收清單、PR 內文一個真名都不帶

## 為什麼不是匿名化

匿名化解決的是「從正式站倒資料出來」的風險。這裡沒有那一步：合併檔是從她自己的舊表與行事曆產的，
而她要看的就是**她的客戶**匯進去之後對不對 —— 把名字換成客戶A，她就認不出那一位的次數對不對了。

## 代價（她聽過、選了）

- staging 的畫面、它推出去的試算表、從它匯出的備份檔都有真名
- staging 的白名單上有誰，誰就看得到真資料 —— 她要自己看一眼 `allowedUsers`
- 合進 `develop` 的新程式第一次就跑在她的（預演）資料上。因為切換時不搬，弄壞了的代價是重新清空、再貼一次合併檔
- 以前「在 staging 上亂點」的習慣不成立了：那些點擊會寫在真的客戶身上

## 後果

- `CLAUDE.md` 上線那一節、`docs/STAGING.md` 第二、四、五、七節、`firebase-config.js` 的橫幅、`e2e-full.yml` 的註解跟著改
- E2E 一律跑在模擬器上（`deploy.yml`、`e2e-full.yml` 都不碰 staging 的資料庫），不受影響
