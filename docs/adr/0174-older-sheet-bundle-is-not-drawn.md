# ADR-0174：兩台同時推試算表時，比較舊的那一包不畫

日期：2026-11-05
狀態：已接受
延伸：[ADR-0013](./0013-sheet-sync-is-a-push-not-a-pull.md)（整包推送、冪等）、[ADR-0161](./0161-sheet-remembers-fingerprints.md)（指紋只記在試算表那一側）—— **照舊送整包**、照舊冪等。

## 背景

`.gs` 只用鎖讓請求排隊，不比新舊。她有手機與 iPad：兩台幾乎同時推時，新的那一包先拿到鎖畫完，舊的那一包等到鎖接著畫 ——
試算表停在舊的，要等下一次推送才對。11/5 上午她選「先觀察」，理由只有「要重貼 `.gs`」；同一天下午：

> 我不介意回去重貼……所以如果是有顧慮到要不要重貼的問題，可以不用顧慮了，你覺得可以改就改

（另一半「等不到鎖被拒」由 `.scratch/sheet-push-gaps/issues/01` 的重試接住。）

## 決定

1. **新舊的依據是稽核紀錄最新那一則的 `at`**（Firestore 的伺服器時間）。每一次寫入都經過 `repo.commit()`、跟著一則稽核，軟刪除也算；
   稽核刪不掉也改不掉。兩台的時鐘準不準無關。
2. **先讀那一則、再讀資料**（`data/sheetSync.js` 的 `buildBundle()`）：資料只會比那個時間新、不會舊，所以「這一包至少包含了那個時間以前的每一次寫入」成立。
   那一讀算進「讀到快取就這一趟不推」（ADR-0161 底下那一節）。
3. 時間放在請求的**最外層**（`{ token, bundle, dataAt }`，`domain/sheetPushTiming.js` 的 `pushBody()`），不進 `syncBundle()`、**不升 `SYNC_FORMAT`**。
4. `.gs` **拿到鎖之後**才比：比文件屬性 `lastDataAt` 舊 → 不畫、回 `{ ok: true, stale: true }`；一樣或比較新 → 照畫，**畫完才記**（畫到一半逾時不記）。
   整份重畫（`force`）比較舊照樣不畫。任何一邊沒有時間照畫（拿不準一律畫，最壞跟以前一樣）：舊版 app 沒帶 → 照畫、不記；
   那一則還沒送上雲端（`at` 是 null）→ 當成沒帶。
5. app 收到 `stale` **算成功**（試算表上已經是更新的那一份）：清待推標記照舊看 `version`，設定頁那一句講「試算表上已經是更新的那一份，這一次沒有重畫」（`pushedSay()`）。
   「有幾張沒更新」不動 —— 那是畫的那一次說的。

## 為什麼這樣是安全的

被擋下來的那一包（時間 T1）比試算表上的（T2）舊。它可能多帶了 T2 以後的寫入（它的資料是比較晚才讀的），但那幾筆寫入
每一筆都會讓寫的那一台再推一次，那一次的時間不會早於那一筆 —— 一定畫得上去。所以試算表最後一定會跟上，不會停在比較舊的那一份。

## 沒有選的

- **拿資料本身的 `updatedAt` 取最大**：刪掉的那一筆不會被讀進來 —— 刪除之後推的那一包會被當成比較舊的、不畫，刪掉的客戶留在試算表上。
- **用裝置的時鐘**（`generatedAt`）：兩台不一定對時，慢的那一台永遠畫不上去。
- **app 那一側記「上次推的是哪一版」**：兩台各記各的，跟 ADR-0161 不在手機記指紋是同一個理由。
- **不修**（11/5 上午的「先觀察」）：只有重貼這個成本，而 `.gs` 這一輪反正要重貼（`.scratch/sheet-push-gaps` 的 02、03）。

## 代價

- 打包多一次讀取（稽核最新那一則，打包之前、跟資料的讀取分開）。
- 她要重貼 `.gs` 並重新部署 —— 跟 02、03 同一次。沒升 `SYNC_FORMAT`，所以沒重貼的話 app 照樣推得上去（只是沒有這一道）。
