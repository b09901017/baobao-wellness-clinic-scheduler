# 待辦中心照流程分段，階段色就是來訪狀態色

待辦首頁上那一排分類的順序，從第一版到 2026-08-23 都是**寫死在樣板裡的
出現順序** —— 沒有任何人決定過它，它是「先寫的先出現」。

那個順序在只有四五列的時候看不出問題。它現在有十列，而她的原話是：

> 「希望能夠更直觀更符合⋯⋯就是可以讓我更清楚**流程排序、下一步**等等」

畫面回答的是「有哪些種類」，她問的是「接下來做什麼」。

## 段落就是她真的在做的順序

```
① 問到時間     問這輪的時間・客戶填好的時間
② 壓表         壓表登記
③ 等客人回覆   跟客人確認時間
④ 來訪前一天   Examine・耀聖
⑤ 來訪當天     簽療程單
⑥ 來訪之後     追蹤健檢報告 → 約二返
⑦ 要收回來的   改時間／取消
```

**編號講的是流程的第幾步，不是畫面上的第幾段。** 中間某一段空了（那很常見），
其餘的編號不重新編 —— 她記得的是「第四步是掛號」，而不是「從上面數下來第三塊」。

## 顏色：一個新色相都不開

ADR-0039 已經記著色相不夠用了（那是休假改走斜線紋的原因）。所以這一支
**借既有的來訪狀態色**，而且借得剛好：

| 段 | 顏色 | 為什麼是它 |
|---|---|---|
| ① 問到時間 ② 壓表 | 中性 | 那時候還沒有「來訪」這個東西 |
| ③ 等客人回覆 | 琥珀 | 那幾筆現在就是 `pending_confirm` |
| ④ 來訪前一天 | 靛藍 | 那幾筆現在就是 `confirmed` |
| ⑤ 來訪當天 | 靛藍→墨綠 | 那一天正在從已確認變成已完成 |
| ⑥ 來訪之後 | 墨綠 | 那幾筆已經 `done` 了 |
| ⑦ 要收回來的 | 硃紅 | —— |

**同一位客戶在待辦上落在琥珀色那一段時，日曆上那一筆也正是琥珀色的。**
這不是配色巧合，是同一個狀態機在兩個畫面上的兩種畫法。

## 三套視覺語言收成一套

原本一列上有兩種顏色系統：`.grouprow__dot`（茶色／accent／紅）與
`.grouprow--lead`（整列淡綠底，標「這幾列比較重要」）。加上新的段落線就是三套，
而它們講的是同一件事。

小圓點與淡綠底都拿掉了，只留段落那條線。**「哪一列比較重要」現在由位置回答** ——
它排在第幾段。

## 「下一步」在 DOM 上算，不在資料上算

那顆標籤標的是**流程上最前面那個還有東西的段**，不是數字最大的那一段：
她的問題是「接下來做什麼」，而流程的答案是從頭開始。

它在畫完之後掃 DOM，不是在產生 HTML 的時候算 —— 因為有三列
（問這輪的時間、客戶填好的時間、壓表登記）是**等資料回來才補進去的**，
產生 HTML 的那一刻還不知道它們有沒有東西。那三支填完會再叫一次。

同理，**空的段由 CSS 收掉**（`.flowgroup:not(:has(.grouprow))`），
不是在 JS 裡判斷。判斷寫在 JS 裡的話，補進來的那一列就得連帶重畫整塊，
而那是 ADR-0038 剛剛才拿掉的東西。

## 段裡的順序不能交給死線

「追蹤健檢報告」的死線是健檢日 + 21 天，「約二返」是拿到報告之後 + 7 天。
照死線排會把鏈條的第二站排到第一站前面（ADR-0042）。

所以 `domain/todoFlow.js` 的 `FLOW` 是一個**有序的陣列**，段與段裡的順序
是同一份資料 —— 因為它們本來就是同一個順序：她做事的順序。

**認不得的種類排段裡最後，而且歸在「來訪前一天」。** 認不得的只有兩種來源
（已經拿掉的打電話與 Abovee、她手動加的），兩種都是來訪之前要做的事。
歸到「要收回來的」等於把它們藏在最下面，而它們可能是今天就該做的。

## Consequences

**規則放在 `domain/todoFlow.js`，不放在 `views/home.js`。** 「這件事是流程的
第幾步」之後進度追蹤頁也會問同一句，而同一件事在兩個畫面歸到不同的段，
她不會知道哪個算數（同 ADR-0028 的理由）。

**七個段落標題吃掉大約 200px。** 這是這一支付出的代價，用「不必再想順序」換的。
空的段整段收掉，實務上同時有東西的通常是四到五段。

**「依客戶」那個看法不分段。** 那一頁問的是「這個人身上還有幾件事」，
流程順序在那裡沒有意義。
