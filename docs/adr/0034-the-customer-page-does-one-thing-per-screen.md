# 客戶那一頁改成一頁一件事，「整個禮拜五」由日期推出來

第一版的客戶表單是**一頁三題往下捲**：固定哪個星期不行、這個月哪幾天不行、
還有什麼要說的；選起來的東西複述成底下一張清單，半天在那張清單上改。
使用者第一次真的發出去之前自己先填了一次，回饋是：

> 「我覺得有點雜亂，資訊太多」「往下滑更亂」「每個日期都跑出來太亂了」

所以整頁重做。這一支記的是被換掉的三個決定，以及為什麼換掉之後原本的理由
還站得住。

## 一頁一件事，不要往下捲

**第一頁只有日曆，第二頁是確認並送出。** 不是「下一頁」而是「填好了」——
使用者的原話是「不然會覺得填不完」，而長輩看到「下一頁」會先想「還有幾頁」。

往下捲之所以比換頁糟，是因為捲到一半的畫面**同時露出兩題的一半**，
看起來永遠像沒做完。換頁的每一頁都是完整的。

## 拿掉兩個東西

**「這個月都可以」那顆大按鈕。** 它原本是給沒有限制的客戶的逃生口，但它跟
「填好了」重複了 —— 什麼都不點直接按「填好了」，確認頁就會寫「這個月都可以，
沒有不方便的日子」。改成在抬頭多一句「整個月都方便的話，直接按下面那顆按鈕」，
一句話取代一顆佔掉一整行的按鈕。

**「固定哪個星期不行」那一題。** 它問的東西和日曆重疊：客戶要嘛在那一題勾
禮拜五，要嘛在日曆上點掉四個禮拜五，兩條路通到同一個地方，而**兩條路本身
就是雜亂**。留日曆那一條，因為那是他心裡真正在想的東西（他想的是「18 號要出國」
不是「exclude_weekday」）。

## 「每個禮拜五不行」變成推出來的

拿掉那一題不代表拿掉那條規則。`domain/availabilityForm.js` 的 `groupPicks()`
在轉規則的時候收合，而且**規則、原文、給人看的複述三邊共用它** ——
客戶按下送出時看到的字，就是她收到的字。

三層，由大到小：整個月 → 整個星期 → 連續的日子。

**第二層的條件刻意嚴格：那個月裡的每一個禮拜五都要被點到，而且半天別一致，
少一個就不收。** 少的那一天他是真的可以，收成「每個禮拜五」會把它一起擋掉 ——
而「多擋一天」在排班上是看不出來的錯，她只會覺得這個客戶怎麼那麼難排。

連續的日子從三天以上才併改成**兩天就併**。原本的理由是「兩天併成『9/22 到 9/23』
比兩列還難讀」，那是在一張只有這件事的清單上成立；在客戶那一頁，
一天一列才是他嫌亂的主因。

## 半天改成點完浮出來，不是到下面那一列改

原本的設計是「點一下＝整天不行，要改半天到下面那一列改」，理由是
**三態循環的誤觸看不出來、而且點錯要再點三下才回得到原點**。那個理由沒有變，
但「到下面那一列改」被使用者指名為最亂的地方。

換成：**點一個日期 → 底下浮出「整天／只有上午／只有下午」→ 選完收起來。**
從底下浮出來而不是畫面正中央，因為拇指構得到，而且不會蓋住日曆上半部 ——
他要看得到自己剛剛點的是哪一格。

原本那個理由靠兩件事接住：

- **三選一是明講的，不是循環的。** 每一次都看得到自己選了什麼，沒有「現在是第幾態」
- **誤觸在第二頁看得見。** 複述整個搬到確認那一頁，那一頁本來就只有複述，
  按下「確定送出」之前一定會經過它

代價是每一天要點兩下（點日期、選整天）。出國八天變成十六下。這被接受：
連續的日子在確認頁會收成一條，而**填錯一天的代價比多點幾下大得多**。

## Consequences

`formResponses` 的 `weekdays` 欄位留著，但表單永遠送空陣列 —— 已經送出的那幾份
裡面有值，`normalizePicks()` 與 Rules 都不動，少一次資料遷移。

`weekdayBlock()`（把被星期擋掉的格子畫成斜線）整支刪掉，連同那個狀態的 CSS
與「這是您說的每個禮拜五不行」那句提示。沒有那一題就沒有那個狀態。

SPEC 第 8.9 節整節改寫。ADR-0031（獨立入口）、0032（先進收件匣）、0033（第三區）
都沒有被推翻 —— 這一支換的是那一頁怎麼問，不是它在系統裡的位置。
