# 「連結已發出、還沒填」是問時間的第三種狀態，但不改變那一列的定義

ADR-0028 把「問這輪的時間」做成待辦中心的一列，並且寫明它讀的是
**「有沒有一份有效的收集」**，不管那份收集是誰打的字。表單做出來之後，
中間多了一段以前不存在的時間：**連結發出去了，客戶還沒填。**

那一段裡她既沒有收集，也不該再問一次。

## 不動 `customersToAsk()`

`domain/scheduling.js` 的 `customersToAsk()` 維持原樣：誰該進來、怎麼排，
一個字都不改。理由是它回答的問題沒有變 —— 「這一輪的時間還沒問到誰」。
連結發出去了確實**還沒問到**，那一位本來就該留在名單上，
不然她會以為問完了，然後那位客戶整個月沒排。

多出來的軸放在 `domain/availabilityForm.js` 的 `splitByInvite()`：
拿 `customersToAsk()` 的結果與邀請清單，分成三區。

```
從來沒問過   ← 一定是漏的
該重問了     ← 週期到了
已經發出連結 ← 在等他填，先不要再問
```

前兩區是 ADR-0028 就有的，第三區是新的，而且**排在最後面**：
她開這一頁是為了知道「現在要問誰」，等回覆的那幾位不是現在要做的事。

## 數字照樣包含他們

首頁那一列的數字不減掉「已經發出連結」的人 —— 這一輪的時間**確實還沒問到**，
把數字做小會讓她以為進度比實際好。改成在那一列的說明裡講出來：
「其中 N 位已經發出連結」。

一個數字後面配一句話，比兩個互相矛盾的數字好懂。

## Consequences

`customersToAsk()` 與它的測試完全沒有被動到。ADR-0028 的三個邊界
（範圍照壓表那道濾網、順序不照計分、資料回來才補那一列）全部原封不動。

代價是這一頁多讀一份資料（`formInvites`，一次查詢）。它跟已經在讀的三份
一起 `Promise.all`，不多一輪往返。讀失敗就當沒有邀請 —— 那時三區退化成兩區，
就是 ADR-0028 原本的樣子，她照樣問得了人。

**過期的邀請不算「已經發出」。** 連結過期了客戶就填不了，那一位要回到
「該重問了」那一區。判斷用邀請的 `validTo`，跟收集的有效期同一套。
