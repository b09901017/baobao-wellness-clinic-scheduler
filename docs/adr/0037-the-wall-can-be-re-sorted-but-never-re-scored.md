# 卡片牆的排序可以換，但每一種都只是同一份名單的重排

`CLAUDE.md` 有一條規矩：任何「先看誰」的排序或推薦名單都要用
`domain/scheduling.js` 的同一組計分，理由是**同一位客戶在兩個畫面排名不同，
她不會知道哪個算數**。

使用者要的是這個：

> 或是可以多一個讓我選，照預設排（就是評分表那邊的排）或是照喜愛程度，
> 照復能剩的多的排，照離上次排最久的排序這樣

## 這不是第二套計分

分數是把四件事（限制多寡、喜好、快到期、多久沒來）揉成一個數字。
她坐下來壓表的時候，心裡常常只有其中一件：「今天先把有問到時間的清掉」
「先弄喜歡的那幾位」。那時候她要的不是另一種分數，是**把同一份名單換個方式排**。

所以 `QUEUE_SORTS` 裡沒有任何新的計算：每一種都只是拿 row 上**已經有的那一欄**
去比大小（`needsAvailability`、`priority`、`totalRemaining`、`daysSinceLast`），
而那幾欄本來就是分數的原料。同一位客戶在壓表與時段反查仍然是同一個分數、
同一組理由標籤，那條規矩沒有被推翻 —— 它的界線變清楚了：
**不可以有第二個「系統認為誰比較急」的答案；她自己挑一種看法不算。**

## 三個選擇

**預設是那一批凍結下來的順序**（也就是分數排的那個），排在第一顆。
她不選就是原本的行為，而那是這一頁該有的樣子。

**每一種都是穩定排序**，所以同一個值的那幾位仍然照預設順序。
「照喜好排」出來的不是一份被洗過的名單，是**同一份名單、喜好高的先**——
她昨天記得的相對位置不會整個變掉。

**排法與搜尋字不進 `batches`。** 進度要跨裝置（SPEC 第 1 節），但「我現在正在
用喜好排、正在搜尋『王』」不是進度。她在 iPad 上搜尋，不該讓手機那邊也只剩姓王的。

## Consequences

`sortQueueRows()` 與 `QUEUE_SORTS` 放在 `domain/scheduling.js` 而不是 UI 裡 ——
排序是業務規則，而且這樣才測得到「同值時保持預設順序」這件不變量。

卡片牆上的丸子從一排變兩組（篩選、排序），中間用 `.chiprow__sep` 與一個
小標「排序」隔開。兩件事長得一樣的話，她會以為點了「喜好」就會篩掉別人。

沒有做的：把她上次選的排法記到雲端、或做成設定。等她真的每次都選同一種再說。
