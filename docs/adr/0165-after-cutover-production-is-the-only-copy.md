# ADR-0165：切換之後，正式站是唯一的一份 —— 不再整份重匯

日期：2026-10-20
狀態：已接受
延伸：[ADR-0118](./0118-staging-holds-a-rehearsal-of-real-data.md)（staging 是真資料的預演，切換那天不搬）、
[ADR-0143](./0143-cutover-day-deletes-production-with-firebase-tools.md)（切換那天連主檔一起刪）。

## 背景

2026-10-20 下午切換做完：正式站與 staging 都清空（登入白名單與 AI 用量帳本留著），寫進同一份 ——
現在的種子＋合併檔 v10（34 位客戶、227 天來訪）。做法跟 `docs/STAGING.md`「切換那天」寫的不一樣：
在本機模擬器上讓 app 自己的匯入跑一次，再把那一份整份搬到兩個專案、讀回來逐欄比對（見 STAGING.md 那一節的紀錄）。

切換之前，資料一錯就「清空 → 照 Abovee 與舊表重產合併檔 → 重匯」。那時候 app 上沒有只存在 app 裡的東西，重來不會丟。

從切換那一刻起，她每天在 app 上記的（簽療程單、拍 Abovee、記一句、勾待辦、改期、取消、加購）**只存在正式站**。
重產的合併檔帶不回這些。

## 決定

1. **永不整份重匯、不清空重來。** 合併檔那條路只用過這一次。
2. **發現錯，在 app 裡改那幾筆**：日曆、拍 Abovee、客戶詳情、資料健檢的修正。
3. **app 改不到的**（例如已完成的段改不回來 —— 狀態機刻意這樣），**或一次要改很多筆**：寫一支只動那幾筆的腳本，一律四步 ——
   **備份**（設定 → 匯出備份，檔案放 `.local/references/`）→ **試跑**（只數不動）→ **寫** → **整份讀回來比對**。切換那天就是這樣做的。
4. **改資料的形狀要帶著既有資料走**：新欄位、改名、拿掉一種東西，配一列資料健檢
   （CLAUDE.md 連動表「`domain/seed.js`（種子）加一筆、改一格」那一列的三條護欄），不寫「清空重來」的版本。
5. **月底對帳只讀**（`.claude/skills/month-end-reconciliation/`）：它列出來的，照第 2、3 條改。
6. **staging 是切換那天正式站的複本**，之後各走各的；staging 上記的不搬回正式站。

## 為什麼不是「錯了就再重匯一次」

- 重匯要先清空：匯入碰到同名的客戶整位跳過（`mergeImport.js` 的 `planForCustomer()`，以免建出第二份），
  所以不清空就補不了既有的客戶 —— 而清空會把切換之後只存在 app 裡的東西一起丟掉
- 舊表與行事曆在切換之後不再更新，重產出來的只會比 app 舊
- 第 3 條的四步留得下備份與比對結果；重匯留不下「改了哪幾筆」

## 後果

- 舊表、行事曆、合併檔、Abovee 擷取從「來源」變成「參考」：`.local/references/` 照舊留著，月底對帳與查舊帳會讀
- `calendar-sheet-merge` skill 不再產切換用的合併檔
- 上 `main` 之前先在正式站匯出一份備份 —— 程式寫錯而寫壞資料時，那一份與 Firestore 的時間點還原是退路
