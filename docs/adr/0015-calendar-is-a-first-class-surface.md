# 日曆是可以編輯的第一線畫面，來訪與個人行程並存

SPEC 第 8.6 節原本把日曆定位成唯讀的檢視 —— 取代 TimeTree 的顯示功能，資料一律從來訪來。使用者要求日曆要能像一般日曆 app 一樣直接新增與編輯，而且要放得下**不是來訪的東西**：公出、休假、演講。我們決定讓日曆成為與壓表同級的入口，並在它上面放兩種各自獨立的東西：

- **來訪** —— 綁客戶，會產生任務，會扣次數，狀態走 SPEC 第 4.1 節那台狀態機。
- **個人行程** —— 不綁客戶，不產生任務，不扣次數，可以跨天，只有名稱、類別、顏色與起訖。

兩者刻意**不共用同一個資料形狀**。把它們合併成一個「事件」集合再用欄位區分，會讓「這筆要不要扣次數」「這筆要不要產生任務」變成到處都要判斷的分支，而漏判的後果是次數算錯 —— 那是這個專案最不能出錯的東西。分開之後，個人行程的程式碼碰不到額度，也就不可能扣錯。

## Consequences

新增 `events` 集合放個人行程。它是唯一一種**可以跨天**的資料：來訪的定義是「客戶某一天到院一次」（見 `CONTEXT.md`），跨天的來訪不存在。

日曆的月檢視要把跨天的個人行程攤成每一週各自的一條色條，那是純排版計算，放在 `domain/events.js`。

從日曆新增來訪走的是同一支來訪編輯器與同一套驗證，所以醫療禁忌照樣硬性阻擋、任務照樣產生、次數照樣只在完成時扣。**日曆是入口，不是第二套邏輯。**

SPEC 第 4.9 節「TimeTree 可以退場」的結論不變，但理由變強了：原本只取代它的顯示，現在連她記在 TimeTree 上的休假與公出也搬得過來。

日曆上的東西仍然只有她自己排的。同事在 Abovee 上壓的看不到（第 4.7 節），所以空格子不等於那個時段真的空著，畫面上必須寫明。
