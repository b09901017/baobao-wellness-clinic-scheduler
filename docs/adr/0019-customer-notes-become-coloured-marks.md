# 客戶的特殊狀況改成多筆彩色備註，會籍退出畫面

兩件事一起發生，因為它們動的是同一塊畫面。

## 會籍不再出現在任何客戶畫面上

使用者的原話：「不用會籍資料」「其實也根本沒有會籍這件事，客戶都不需要有會籍到期日期等這種標籤標示」。

`membershipExpiresAt` 原本出現在四個地方：新增客戶表單、編輯基本資料表單、客戶清單的每一列、客戶詳情的一顆徽章；還有客戶清單的「會籍快到期」篩選與壓表卡片牆的「快到期」篩選。**這六個都拿掉了。**

**欄位本身留在資料上，不刪。** 舊資料照樣讀得到，`domain/sheetReport.js` 的報表欄位、`domain/audit.js` 的欄位名稱對照、`domain/scheduling.js` 算急迫度時的後備值都不動 —— 拆掉一個沒有人在填的欄位，換來的是四個檔案的連動與一份對不起來的舊報表，而留著它一個成本都沒有。之後不會再有人填它，急迫度就退回用額度自己的 `expiresAt` 算，那本來就是比較準的那一個。

清單頁空出來的那一行改成 SPEC 第 8.5 節本來就要求、但一直沒做的**上次來訪與下次預約**。

## 特殊狀況改成多筆彩色備註

`customer.notes` 原本是一個自由文字欄位（「特殊狀況」）。使用者要的是「可以有備註…會有多個備註…用顏色小丸之類的方式呈現」。

新增 `customer.marks`：`[{ text, color }]`，最多 12 則、每則最多 40 字，顏色從六個裡挑。規則在 `domain/customerMarks.js`。

**顏色不帶任何意義。** 程式不可以因為顏色而改變行為 —— 一旦「紅色代表不能排」這種規則出現，它就變成一個沒有人驗證、也沒有寫進 SPEC 的業務規則。真正會影響排班的是**永久限制**（其中的醫療禁忌是唯一的硬性阻擋），那是另一個欄位，界線寫在 `CONTEXT.md`。

**`marks` 是真相，`notes` 是它換行接起來的純文字鏡像，每次存檔一起寫**（`toCustomerFields()`）。這樣試算表報表、壓表卡片上的特殊備註（`domain/scheduling.js` 的 `selfNote`）與舊資料匯入都不必知道 `marks` 存在。

**舊客戶不需要被搬移過。** `readMarks()` 在沒有 `marks` 時把 `notes` 逐行拆成灰色備註 —— 而匯入器產生的 `notes` 本來就是一行一件事的多行字串，拆出來剛好就是她想要的那幾則。

## Consequences

`firestore.rules` 的 `validCustomer()` 多一條 `marks is list` 的形狀檢查。內容不驗證：長度與重複由 `domain/customerMarks.js` 擋在寫進去之前，那是「畫面掃不完」的問題不是資料正確性問題。

代價是同一件事有兩個欄位。為了不讓它們各自演化，兩者只能經由 `toCustomerFields()` 一起寫出去，`domain/customerMarks.js` 是唯一知道它們關係的地方，`tests/customer-marks.test.js` 盯著「寫出去再讀回來是同一份」。

編輯備註不在「編輯基本資料」那張表單裡，它有自己的底部面板（ADR-0018）——一個欄位兩個地方可以改，遲早會出現「我剛剛不是改過了嗎」。
