# 預約的狀態記在來訪上，那天實際發生了什麼記在時段上

`SPEC.md` 第 4.1 節那台狀態機把五個狀態都放在來訪上，次數也就整筆一起算：
一筆 `done` 的來訪，它底下每一段都算做過。2026-08-20 使用者指出這不夠用 ——
**客人做了一半就走是會發生的**，不常，但會。那時整筆標成已完成會多扣一次，
標成未到又會少扣兩次，兩種都是錯的，而錯的方向剛好是她最痛的那件事。

我們**不把五個狀態都搬到時段上**，只搬「結果」：

| 狀態 | 講的是什麼 | 記在哪裡 |
|---|---|---|
| `pending_confirm` / `confirmed` / `cancelled` | 這次**預約**走到哪裡 | 來訪 |
| `done` / `no_show` | 那天**實際發生**了什麼 | 來訪（整筆）＋ `slot.attended`（逐段） |

前三個逐段不會不一樣：同一天的時段是一起壓、一起問的，客人說不行的那幾段在確認
動線裡就被移出來訪了（第 8.1 節）。把它們也搬下去，換來的是每一段各自要走一次
確認動線 —— 而客人是一次講完一整天的。

## `attended` 的讀法只有一條，寫在計數規則旁邊

`domain/entitlements.js` 的 `slotOutcome()`。放在那裡是因為
`domain/visits.js` 已經 import 了它的 `counts()`，反過來 import 會變成循環；
而這條規則本來就是**計數規則**，而計數只能有一份實作（ADR-0004）。

兩個容易讀錯的地方寫進了那支的註解：

- **只有已完成的來訪才逐段看。** 匯入器會在 `confirmed` 的來訪上寫
  `attended: false`（`domain/mergeImport.js`），那句話的意思是「還沒發生」，
  不是「沒做」。看它就會把還沒到的來訪算成未到。
- **沒寫過（`undefined` / `null`）一律當成有做。** 舊資料與匯入的來訪（ADR-0011）
  都沒有逐段記過。把它們當成沒做，會讓所有人的次數一夜之間全部退回去。
  只有明確的 `false` 才是「這一段沒做」。

## 既有資料一格都不會動

改法之前，沒有任何一筆 `done` 的來訪帶得到 `attended: false`：
來訪編輯器寫的是 `attended: to === 'done'`（標成 done 時全是 `true`），
`domain/legacyImport.js` 一律寫 `true`，`domain/mergeImport.js` 的 `false`
只出現在 `confirmed` 上。所以這次改動**不會讓任何一位客戶的次數改變**，
也不需要重算既有的計數欄位。

## Consequences

`counts()` 從「數這筆來訪有幾個時段掛到這份額度」改成「逐段問 `slotOutcome()`」。
`recount()` 與 `summarize()` 不必跟著改 —— 前者呼叫 `counts()`，
後者讀前者寫出去的計數欄位，三支仍然只有一份實作（ADR-0004）。

收尾的規則在 `domain/visits.js` 的 `closeVisit()`，待辦中心的收尾畫面與
來訪編輯器的狀態按鈕走同一支。**一段都沒做就是整筆未到** ——
「來了但什麼都沒做」不存在，那就是沒來。

代價是同一件事現在有兩個層級（來訪的狀態、時段的結果），而它們可能互相矛盾：
一筆 `done` 但每一段都 `attended: false` 的來訪在資料上是合法的。
`closeVisit()` 產不出那種東西，但手改 Firestore 可以，所以資料健檢的「狀態異常」
把它列進去了（`domain/health.js` 的 `checkVisitStatus()`）——
次數看起來扣了、實際上一次都沒扣，而畫面上分不出來。
