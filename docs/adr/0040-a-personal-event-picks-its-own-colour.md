# 個人行程自己挑顏色，存的是名字不是色碼

個人行程是「公出、宜蘭休假、高齡演講」（`CONTEXT.md`）。

對系統來說這三件事**一模一樣**：那個時段有事、不綁客戶、不產生任務、不扣次數。
系統看不出它們的差別，也不應該看得出來 —— 那正是 `domain/events.js` 碰不到額度
的理由（ADR-0015）。

但對她來說差很多，而**那個差別只有她知道**。

使用者的原話：

> 然後個人行程可以選顏色

## 這和客戶身上的備註是同一個形狀

ADR-0019 對備註下過同一個判斷：顏色由使用者自己分，系統不因為顏色改變任何行為。
那一支的結論在這裡原封不動成立，所以做法照抄，不要另外發明一種。

## 決定

**一筆行程可以挑一個顏色，選填。休假也可以挑。**

- 名單借 `domain/customerMarks.js` 的 `MARK_COLORS`：灰、綠、茶、紅、藍、紫。
  **色票只能有一份** —— 兩個地方各挑六個顏色，遲早會變成兩組不一樣的六色。
  六個的理由也照舊：再多她自己也分不清哪個是哪個。
- **存的是名字（`'violet'`）不是色碼（`#7a6096`）。** 存色碼的話深色模式那一份
  就沒有人換得掉，而且以後要調色就得回頭改每一筆資料。
- 沒挑（`color` 是 `null` 或根本沒有這個欄位）就跟著那一類本來的顏色走。
  2026-08 以前建的行程身上都沒有這個欄位，**不需要資料搬遷**。

### 顯示端寬容，存檔端不寬容

`colorClass()` 對認不得的顏色回空字串，讓它落回類別的預設色；
`validateEvent()` 對認不得的顏色**報錯**。

兩邊不一致是刻意的。顯示端的寬容是為了**已經存在的資料** ——
畫不出來就整筆消失是最糟的失敗方式。存檔端的嚴格是為了不讓新的髒資料進來。

這跟同一支檔案裡 `describeCategory()` 的作法（不認得的類別大聲印出來）也不衝突：
類別錯了是資料壞了、要看得見；顏色沒挑只是她還沒挑，畫成預設色才是對的。

### 休假身上的斜線紋不跟著顏色走

ADR-0039 給休假一層 45° 斜線紋，用來講「這幾天我不在」。
她把休假挑成紅色時，紅的是顏色，**斜線還在**。

實作上 `paintClass()` 對休假回**兩個 class**（`evcolor-red kind-leave`）：
顏色 class 蓋掉 `--kind-fg` / `--kind-bg`，斜線紋掛在 `.kind-leave` 的
`background-image` 上，兩者管的是不同的屬性，蓋不到彼此。
`.evcolor-*` 在 `app.css` 裡**排在 `.kind-*` 後面**，這是它蓋得掉的前提。

### 挑的顏色可能撞到來訪狀態

六色裡的藍、綠、紅，跟已確認、已完成、未到的顏色是相近的色相。
她把一筆個人行程挑成藍色，月檢視上就會有一條看起來像「已確認的來訪」的藍色條。

**不擋。** 那是她的畫面、她的分類，而且兩者在別的地方分得出來
（個人行程可以跨天、沒有狀態徽章、點開是另一種卡片）。
擋的話等於系統替她決定哪個顏色代表什麼，而 ADR-0002 說 app 記錄決定、不做決定。

## Consequences

- `--mark-*` 那六個值是給 **6px 的小圓點**設計的，當 11px 的字擺在色塊上
  對比度不夠（茶色只有 3.27:1）。所以另外有一組 `--evcolor-*`：
  **名單（id 與標籤）是同一份，值是這個情境專用的**，每一個都壓到
  字對底 ≥ 4.6:1（深色 ≥ 4.7:1）。
  下一次有人要加第七個顏色，兩邊都要加。
- `firestore.rules` 的 `validEvent()` 多擋一條 `color` 的形狀。
  **它只擋「連字串都不是」，不擋「不在那六個裡面」** —— Rules 這一層守的是形狀，
  詞彙表是 domain 的事，把六個名字抄進 Rules 就等於有兩份名單要同步。
- 編輯器上「不挑」那一顆做成**空心圈**：它長成那一類本來的顏色，而那個顏色
  也在底下六顆裡（個人行程預設是紫，六顆裡也有紫），兩顆實心點會一模一樣。
  空心講的是「這不是一個顏色選擇」。
