# 只有日曆改得了一筆來訪

ADR-0020 定了「先讀取，要改按鉛筆」，而那條規矩後來被三個畫面各自實作了一次：
日曆、客戶詳情、待辦中心。三個地方都有那張讀取卡片，三個地方都有那支鉛筆。

2026-08-25 她點進去之後問：

> 不懂什麼情況點完詳情進去後會需要修改？應該就不用修改吧？

那是一個好問題，而答案是「沒有」。三個入口不是三個功能，是**同一件事有三條路**。

## 三個畫面各自在回答什麼

| 畫面 | 她在那裡問的問題 | 改一筆來訪算不算它的工作 |
|---|---|---|
| 日曆 | 「八月三號那天還塞得下嗎」 | **算** —— ADR-0020 的整個前提 |
| 客戶詳情 | 「他還剩幾次、這個月哪天來」 | 不算 |
| 待辦中心 | 「今天要去 Examine 掛哪幾個人」 | 不算 |
| 進度追蹤 | 「這個月做了多少」 | 不算（本來就是 `canEdit: false`） |

## 決定

**只有日曆的讀取卡片有鉛筆。** 客戶詳情、待辦中心、進度追蹤的卡片一律唯讀。

- 三個畫面仍然共用同一支 `visitReadHtml()`（ADR-0018 的理由沒有變：
  同一筆來訪在四個地方長得不一樣，她會以為是四種東西）。
- 客戶詳情的「來訪紀錄」那一列也不再是連到編輯器的連結 —— 留一條繞過去的路，
  等於這個決定只做了一半，而半個決定比沒有決定糟：她會開始每一列都試一次。
- 待辦中心讀不到那一筆的時候，以前的退路是直接進編輯器。那條路現在通到
  一個她不該落在的地方，改成講出來是哪一種情況（還在讀／找不到）。

## 順帶：唯讀的卡片不解釋規則

`visitReadHtml()` 底下本來印著：

> 改時間不是改日期 —— 取消這一筆再重排一筆，舊系統的登記才會長出取消任務。

她的原話是「我完全看不懂他想說什麼」。看不懂是合理的 —— **那張卡片上根本沒有
一個地方改得了日期**，那句話對著一個不存在的按鈕解釋它為什麼不能按。

規則本身（SPEC 第 7 節規則 10）沒有變，而且仍然寫在它真的會發生的兩個地方：
來訪編輯器的狀態卡（「要改期就取消後重新排一筆」）與取消確認框
（「改期不是改日期，是取消後重新排一筆」）。

判準記在這裡，之後每一句說明都可以拿來問一次：

> **這句話在講一件她從畫面上看不出來、而且不知道就會做錯的事嗎？**
>
> 在解釋一個畫面上根本沒有的動作 → 刪。
> 在解釋一個她看得到卻按不動的東西 → 留。

## Consequences

- 從客戶詳情要改一筆來訪，路徑變成「回日曆 → 找那一天 → 點那一筆 → 鉛筆」。
  多兩步，而那兩步正是「我確定要改班」這個意思。
- `#/visits/:id` 這條路由還在（日曆的鉛筆用它），直接打網址仍然進得去。
  沒有把它擋掉是刻意的：那不是她會做的事，而擋掉會讓稽核紀錄裡的連結失效。
