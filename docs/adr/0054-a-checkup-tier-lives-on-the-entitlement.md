# 健檢的金額等級是額度上的一個欄位，不是三個課程

她手上的健檢有金額等級之分：0.75 萬、8 萬、12 萬（舊資料裡還有「5萬(心臟)」）。
加購時她要選得到，而選了之後那一筆要叫「8萬健檢」——兩筆都叫「健檢」的話
她在客戶詳情頁分不出哪一筆對哪一筆。

那個問題 `followupDraft()` 的註解已經寫過一次了（二返為此帶上了來源的名字），
只是健檢那一端沒有補上。

## 三個做法

| | 怎麼存 | 代價 |
|---|---|---|
| A | 額度上的一個 `tier` 欄位 | 主檔上只有一個「健檢」課程；等級是額度的屬性 |
| B | 同上，但等級寫死在程式裡 | 她加不了新的等級 |
| C | 每個等級各開一個課程 | 每個等級都要記得把 `followupCourseId` 指到二返，漏設就整條二返鏈斷掉 |

**2026-08-25 使用者選 A（而且要能自己加）。**

C 的彈性最大，但它把一件「顯示上的差別」變成「主檔上的三筆設定」，
而其中一筆漏設 `followupCourseId` 的後果是那位客戶的二返額度永遠不會被配出來
—— 而那件事要等到她真的要記一筆二返時才會發現。`CONTEXT.md` 早就把界線畫好了：

> **健檢**：健康檢查課程。有金額等級之分（例：0.75 萬、12 萬），
> **等級只影響顯示名稱與價格，不影響流程與任務。**

## 決定

`entitlements` 多一個選填的 `tier`（字串，例 `'8萬'`）。

- **只影響顯示名稱。** `tieredLabel(tier, courseName)` → `'8萬健檢'`。
  `taskRules.js`、`followups.js`、`entitlements.js` 的計數，一行都不因為它而變。
- 配出來的二返自動叫「二返（8萬健檢）」—— `followupDraft()` 本來就抄來源的
  `label`，那一段一個字都不用改。
- 加購那一張表在課程丸子底下多一排「幾萬的」，**只在選到有配二返的課程時出現**。
  判準是 `followupCourseId` 有值，不是名字裡有沒有「健檢」兩個字 ——
  課程是她自己在主檔建的，用字串包含比對正是舊 Apps Script 靜默失效的原因
  （`domain/followups.js` 的檔頭）。
- 丸子上是常用的三個（`TIER_PRESETS`），最後一顆「其他…」展開一個文字欄。
- **既有的健檢額度不補 `tier`，也不猜。** 猜一個金額出來比空白糟得多。

## 價格呢

`SPEC.md` 第 5.3 節的 `entitlements` 沒有價格欄位，整個 app 也不碰錢
（那在她的方案文宣上）。所以這一輪只做顯示名稱那一半。`tier` 這個欄位留著，
之後真的要記價格時它就是掛點 —— 那時候它會變成一張對照表的 key，
而不是再多一個並排的欄位。

## Consequences

「調整」那一張表**沒有**這一排（她點進去只是要改一個數字）。所以
`readEntitlement()` 只有在那一排真的在畫面上時才回報 `tier` ——
少帶一個欄位就等於把它清成 null，那正是 2026-08-25 修過的
`normalize()` / `normalizePatch()` 那一種形狀（`domain/notes.js`）。
要改等級就改「進階設定」裡的顯示名稱，那是同一件事的另一半。

`firestore.rules` 的 `validEntitlement()` 多一條：`tier` 選填、是字串、20 字以內。
