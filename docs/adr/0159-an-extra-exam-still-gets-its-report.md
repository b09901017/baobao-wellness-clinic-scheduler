# ADR-0159：健檢做的比買的多，多出來那一次也追報告；補了二返額度之後那一串重算

日期：2026-10-19
狀態：已接受
推翻：[ADR-0139](./0139-the-report-task-does-not-wait-on-the-follow-up.md)「名額」那一句裡的上限
（「`min(做完的健檢, 二返總次數) − 做完的二返 − 先定案的`（上限跟 `owed()` 同一個）」）—— 報告那一張不再被二返額度的總次數蓋住。
ADR-0139 其餘（照位置配、先定案的、二返做完才不追）照舊。
延伸：[ADR-0042](./0042-the-report-comes-before-the-follow-up.md)、[ADR-0065](./0065-two-things-happen-when-the-report-arrives.md)、
[ADR-0068](./0068-growing-a-task-and-keeping-it-are-two-rules.md)、[ADR-0070](./0070-a-warning-may-only-say-what-really-happens.md)、
[ADR-0142](./0142-the-booking-slot-goes-to-the-exam-whose-report-is-in.md)、[ADR-0158](./0158-incomplete-read-does-not-save.md)。舊的幾支一個字都不改。

## 背景

她 2026-10-19 逐條回答上線前那份清單：

> 5.  健檢做的次數比買的多，多出來那一次不會長報告那一串待辦。 好 修

我問「沒有二返額度的那一次，『約二返』先不長，等你補了額度才長？」，她答「是」。

ADR-0139 把「追蹤健檢報告」從 `owed()` 那道閘門拿出來，但名額照抄了 `owed()` 的上限（二返額度的總次數）。
那是當時的技術選擇，不是她要的：買 1 次健檢配 1 次二返、做了 2 次健檢 → 第二次一張報告都不長，
「寄報告給醫師」等不到報告被勾掉，也不長。app 不擋超用（ADR-0002），所以多做的那一次是真的做了 —— 報告照樣要追、照樣要寄給醫師。

第一段查到的另一個洞：加購、客戶詳情「補一筆二返額度」、改二返的次數**都不重算**健檢那條鏈。
補了額度之後，那一次健檢的「約二返」要等她下一次存這位客人的某一筆來訪才長出來。

## 決定

### 一、報告與寄報告不吃二返額度，「約二返」照舊吃

- **每一次做完、二返還沒做完的健檢都追報告**：名額＝做完的健檢 − 做完的二返 − 先定案的。二返做完的次數照舊佔名額，
  照位置配給最舊的那幾次（`placeSeconds()`）—— 只有「二返額度不夠」不再佔
- 報告勾掉 → 「寄報告給醫師」（第二圈本來就不看額度）
- 「約二返」照舊受 `owed()` 管：`min(做完的健檢, 二返總次數)` 那個上限留著。**沒有額度不長，補了才長**

### 二、匯進來的舊健檢不補報告

拿掉上限之後，切換那天匯進來、健檢做的比二返額度多的舊健檢，第一次存這位客人時會長一張死線是健檢日＋21 天、
一出生就逾期的「追蹤健檢報告」。那一段在舊系統裡早就走完了。

**超出二返額度的那一次、是匯進來的（`importedFrom`）、從來沒有過任何一張鏈上待辦（含勾過又清掉的，`seenTasks()`）→ 不長。**

為什麼這樣判：

- **只看「從來沒有過待辦」不夠**：在 app 裡做完的超出那一次，在這一支之前也從來沒有過待辦（被上限擋著）——
  只看這一條的話，以後每一次超出的健檢都永遠長不出來，等於什麼都沒修
- **「報告的死線已經過了」要今天的日期**：健檢鏈那一支（`syncFollowupTasks()`）是純函式，五個呼叫端（存檔、勾待辦、
  三種確認框的試算）都要多傳一個今天；漏傳一個，確認框講的就跟寫下去的不一樣（ADR-0070）。`importedFrom` 是資料自己帶的
- **只管超出二返額度的那幾次**：在額度裡的匯入健檢，ADR-0139 已經決定照樣追，這一支不動

代價：切換那天匯進來、**最近三週才做、又剛好是超出的那一次**，app 不會提醒追報告。超出本來就少，再加上最近才做，幾乎碰不到；
真的碰到時她自己記一筆隨手記。

### 三、改到健檢或二返額度，同一個 commit 重算那一串

**改到的是健檢或二返的那一筆，就拿寫完之後的額度重算一次健檢那條鏈，跟額度寫在同一個 commit**
（`data/visits.js` 的 `chainAfterEntitlements()`）：

| 路 | 在哪 |
|---|---|
| 加購一筆、加購一整個方案、拍訂購單加購到既有客戶 | `data/customers.js` 的 `createEntitlement()`／`addEntitlements()` |
| 改一筆額度（次數、日期…）、改一組購買日 | `updateEntitlement()`／`updateEntitlements()` |
| 刪掉一筆額度、從已刪除項目還原 | `removeEntitlement()`／`restoreEntitlement()` |
| 資料健檢「補上二返額度」（不經過上面那幾支） | `data/health.js` 的 `applyFixes()` |

建新客戶（`createWithPlan()`）不用：還沒有任何來訪。動到的不是健檢或二返（營養品、復能）就不讀、不算。

- **讀不完整就不重算、不擋寫額度**（ADR-0158 反過來用）：寫額度本身不吃來訪，額度照寫，那一串等下一次存來訪再算
- **次數改少了也要重算**：多出來的那一張「約二返」收起來，理由講「二返的次數不夠」—— 以前收起來的理由一律是「二返已經約好了」，
  額度變少時那是假話
- **確認框照真的會發生的講**（ADR-0070）：客戶詳情「補一筆二返額度」與「刪除這筆額度」、資料健檢「補上二返額度」，
  拿同一支試算（`chainPlanLines()`／`chainCountLines()`）。以前「補一筆二返額度」寫死「補了之後，健檢標成已完成才會長出『約二返』的待辦」——
  重算之後已經做完的那幾次補完就長，那一句變成假話。改次數那一張表沒有確認框，不講

## 後果

- 健檢超用的那一次：做完 → 追蹤健檢報告 → 勾掉 → 寄報告給醫師；「約二返」不長，客戶詳情那一張健檢卡片看得出二返額度不夠。
  去改二返那一筆的次數，存完「約二返」就在待辦上
- 資料健檢一次補好幾位的二返額度：那幾位做完的健檢的報告待辦**按下去那一刻**就長出來（以前要等下一次存那一位的來訪）。確認框照種類數出來
- 改額度多讀四份（課程、全部來訪、任務、設定）—— 只在改到健檢或二返時讀
