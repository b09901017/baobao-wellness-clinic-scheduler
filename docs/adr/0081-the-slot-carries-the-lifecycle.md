# ADR-0081：整條生命週期記在時段上，來訪是那一天的容器

日期：2026-09-08
狀態：已接受
推翻：[ADR-0025](./0025-what-happened-is-recorded-per-slot.md) 的**後半**
（「前三個逐段不會不一樣」那一段）。它的前半沒有被推翻 —— `slot.attended`
留著，逐段記結果那件事當初就是對的。

## 背景

她 2026-09-08 回報「長按取消會把當天全部取消」之後，被問到要怎麼只取消一段時，
反問了四件事：

> 不太懂？理論上不是應該每個時段都要有那三個狀態嗎？不然試算表是怎麼記的！？
> 等等 我頭有點痛，所以現在是限制一天一筆來訪嗎？為甚麼要這樣限制？
> 我希望是從底層開始改，而不是還要修修補補，然後之後會很難維護

四件事各自的答案：

**一、沒有「一天一筆來訪」這條限制。** `firestore.rules` 的 `validVisit()`
只擋「至少一個時段、狀態要合法」，`validateVisit()` 也沒擋。真正發生的是
**壓表那一頁的合併**（`withExtraSlot()`）。SPEC 第 4.4 節那句「不要做成一格一格
分開建立預約」講的是**建立的動線**（她一次填一天），後來被當成了資料模型的鐵則。

**二、已經做了一半。** ADR-0025 在 2026-08-20 就把「結果」搬到時段上了：

| 狀態 | 那時記在哪 |
|---|---|
| 已完成 / 未到 | 逐段（`slot.attended`） |
| 待確認 / 已確認 / 已取消 | 整筆 |

**三、試算表當時是錯的。** `domain/sheetReport.js` 的 `mark()` 讀
`markFor(v.status)` —— 整筆的狀態。所以一筆標「已完成」、其中一段
`attended: false` 的來訪，兩段都印 ✓。那一支自己的註解寫著這件事還沒做。

**四、確認動線會刪掉資料。** 客人說「10:30 那段不行」時，那一段是被
**從 `slots` 陣列裡刪掉**的。沒有紀錄它曾經被壓過，也不會長出「取消 Abovee」
—— 而她真的在 Abovee 上壓過那一格。

## 決定

**整條生命週期搬到 `slot.status`，`visit.status` 改成推導出來的。**

### 一、時段多一格 `slot.status`

值域就是 `VISIT_STATUSES`，不另外開一組。`slot.attended` **留著不動**：
既有資料靠它，而它是 ADR-0025 的欄位。新資料兩個都寫。

### 二、`visit.status` 照樣寫進文件

不寫的話有四個地方要一起改，而它們都不該為這件事動：

- `firestore.indexes.json` 的 `deletedAt + status + date` 複合索引
- `firestore.rules` 的 `validVisit()`
- 試算表報表
- 備份與還原

推導規則（`visitStatusFrom()`，由「還沒定案」往「定案」比，**第一個對上的算數**）：

```
1  全部取消              → cancelled
2  有一段還沒問過客人    → pending_confirm
3  有一段談定了          → confirmed
4  有一段做了            → done
5  其餘                  → no_show
```

第 4、5 條把 `closeVisit()` 那句「一段都沒做就是整筆未到」原封不動接了過來。

### 三、舊資料零遷移

`slotStatus()` 先看 `slot.status`，沒有就從 `visit.status` + `slot.attended` 推
—— **那一段跟 2026-09-08 之前一模一樣**，有一支測試逐個狀態比對冪等性。

**只有一個例外**：整筆是 `cancelled` 或已刪除時，它蓋過時段上還沒定案的那一格。
2026-09-08 之前的 app 只寫整筆，而一格停在 `confirmed` 的舊時段不可以讓那一段
一直佔著次數。

補齊的時機是**她存過一次**：`data/visits.js` 的 `save()` 是唯一的路口，
在那裡跑 `withSlotStatuses()`。匯入那條路不走 `save()`（一次寫一整包），
所以 `data/legacyImport.js` 自己補一次。

### 四、確認與取消的界線分開

ADR-0025 當時說「同一天的時段是一起壓、一起問的」，所以前三個狀態不必逐段。

**那句話對「確認」成立，對「取消」不成立。** 確認是客人一次回答一整天；
取消是**事後一段一段**發生的 —— 機器壞了、治療師請假、客人只想改那一段。
那條界線當初沒有分開想。

所以：
- 確認動線裡客人退掉的那一段標成 `cancelled`，**不再從陣列裡刪掉**
- 長按一列時多一顆「取消這一段」，排在「取消一整天（N 段）」上面
- 來訪編輯器那顆 × 在既有來訪上是「取消」不是「刪掉」

## 為什麼不是別的做法

**每一段拆成獨立的一筆來訪。** 那會推翻 SPEC 第 4.4 節，而且「一天一筆來訪」
是掛號待辦掛著的那一層 —— 掛號是一天去一次，不是一段去一次。
容器留著、原子單位下移，兩件事都成立。

**只加一個 `slot.cancelled` 布林。** 那會變成第三個講同一件事的欄位
（`visit.status`、`slot.attended`、`slot.cancelled`），而三個欄位遲早有一個
跟另外兩個對不起來。一格 `status` 收得下全部五種。

**`visit.status` 不再存，全部現算。** 索引、Rules、試算表、備份四個地方要一起改，
而它們都不是這一輪的題目。

**取消的時段回傳一種新的 `slotOutcome()`。** 每一個 `switch` 都要多一條，
而漏掉的那一條會**無聲地**把取消掉的那一段算進次數，要等到她對帳才發現。
回 `null`（＝不佔任何次數）跟整筆取消是同一種答案。

## 後果

- **同一件事有兩個層級**（時段的狀態、整筆的推導值），它們可能對不起來。
  資料健檢新增一列「來訪的狀態跟它的時段對不起來」，一鍵重推。
  **只寫 `status` 一格**，時段一個字都不碰。
- **「哪幾段還算數」只有一支 `isLiveSlot()`。** 掛號那一族、紀錄那一族、
  療程單、後果說明全部走它 —— 各寫一次 `s.status !== 'cancelled'` 的話，
  遲早有一處忘了，而症狀是一段已經取消的來訪還在要求她簽療程單。
- **`bookingSystemsForVisit()` 刻意不濾。** 整筆取消時每一段也都是 `cancelled`，
  濾掉的話「取消 Abovee」一張都長不出來。整筆還活著時哪幾段沒了是另一個問題，
  走 `cancelTasksForDeadSlots()`。有測試釘著這兩者不可以合併。
- **試算表順手修對了**（見背景第三點），而 `SYNC_FORMAT` 沒有變 ——
  符號那一格的格式一樣，只是算得對了。她不必回 Google 重貼。
- **`formSlotIndexes()` 回的仍然是原本那一格的索引。** 收尾畫面拿它逐段打勾，
  濾掉之後重編號的話她會在錯的那一段上簽名。
- **`withExtraSlot()` 的 `reopened` 現在是推導出來的**：新加的那一段是
  `pending_confirm`，整筆一推就退回「待確認」。既有那幾段會先把自己現在的
  狀態落下來 —— 不落的話它們會跟著退回去，而她其實已經談定那兩段了。
- 稽核紀錄多一條句子：「取消了其中 N 段」。**排在狀態變化後面** ——
  整天一起取消時主角是整筆的狀態，不是段數。

## 其他做法（她看過並選了現在這個）

**先不碰地基，把單段取消做成 UI 上的特例。** 她明確不要：
「我希望是從底層開始改，而不是還要修修補補，然後之後會很難維護。」
