# 壓表批次以客戶為單位，不以課程為單位

SPEC 第 8.2 節與 `batches` 的 `courseId` 都假設一次壓表在處理一個課程：選定復能與月份，
把該課程還有次數的人排成一列，一位一位過。使用者實際坐下來壓表的動作不是那樣 ——
公司系統上一次看到的是**某一天所有時段與診間的空位**，她的習慣是**挑一個人，
把這個人能壓的所有課程一次壓完，再換下一個人**。

按課程分批會逼她把同一位客戶拆成好幾批來處理：壓完復能那批，過幾天再開靜脈那批時，
同一個人又出現一次，而她在公司系統前面看到的空位是同一片。所以我們把批次的單位
從課程換成客戶：一批 = 一個月份 + 一列客戶，每位客戶底下記的是他這個月的所有時段，
跨課程。課程變成記錄每一筆時段時才選的欄位。

先搶先贏與否不進系統：除了復能以外的課程看到空位就能搶，復能要看那天排班的物理治療師
有幾位、一個人一次佔四小時再輪下一位。那是她在公司系統前面自己權衡的事，
app 看不到別人壓了什麼（ADR-0002），不該替她算。

## Consequences

`batches` 的 `courseId` / `courseName` 移除，`queue` 的每一筆變成「這位客戶這個月處理到哪」，
`state` 仍然是 pending / done / skipped。ADR-0001 的推導與凍結順序都不變，
只是推導的條件從「這個課程還有次數且這個月沒排過」放寬成「**任何一個**課程還有次數
且這個月還沒排滿」。

排序公式（SPEC 第 9 節、`domain/scheduling.js`）留著，但第三項的「剩餘次數 / 距到期天數」
要跨所有課程加總，不再是單一課程。時段反查照樣用同一組計分，那一頁仍然是先有時間再找人。

SPEC 第 8.2 節「先選課程」與整段課程佇列的描述作廢，改成客戶卡片流；
既有的 `tests/scheduling.test.js` 對 `buildQueue` 的課程參數要跟著改。

代價是壓表綜覽不再能只顯示「壓復能時只看復能的剩餘次數」。改用的辦法是卡片上
每個課程各給一個小數字，點進去才展開細節 —— 她要決定的是「這個人今天能壓什麼」，
那需要看到全部，而不是一個課程。
