# 試算表同步改成 app 主動推，Apps Script 只收不取

ADR-0010 把試算表同步做成「app 產生報表、她複製或下載後貼回去」，理由是
**不想要第三個放客戶健康資料鑰匙的地方**：讓 Apps Script 定時抓 Firestore 需要
一把服務帳號金鑰擺在 Apps Script 專案屬性裡，那把鑰匙外洩等於全部客戶的資料外洩。

使用者要的是自動更新。我們**保留那個理由，換掉方向**：Apps Script 不去拿，
改成 app 寫入成功後主動推一份過去。Apps Script 那一側因此**什麼憑證都不需要** ——
它只是一個 `doPost` 收件口，拿不到 Firestore，也不知道 Firestore 在哪裡。
實作在 `sheets/readonly-report.gs` 與 `public/js/data/sheetSync.js`。

擋住那個收件口的是一組密鑰，存在 Firestore 的 `config/app`（被 Security Rules 的
白名單守著），**不是寫在前端程式碼裡** —— 部署出去的 JS 是公開的。

## 三個實作上的選擇

**推整包，不推差異。** 每次都送全部客戶的完整報表。整包是冪等的，所以漏推一次
下一次會補回來；推差異就要在兩邊各維護一份「哪些變了」的帳，而那種帳一定會對不起來。

**不是每次寫入都推，是安靜十秒後推一次。** 她一次壓表會連續存十幾筆，
每筆都推等於十幾次往外打，而中間那十幾份沒有一份是有人在看的。

**推失敗永遠不會讓寫入看起來失敗。** 離線時（PWA 的常態）推送一定會失敗，
但那時資料已經安全地在 Firestore 裡了。失敗只留下一個待推標記，
下次寫入或下次開 app 補推。往回報錯只會讓她以為資料沒進去而再存一次。

## Consequences

ADR-0010 的另外兩個結論原封不動：**排版與次數只有一份實作**（`domain/sheetReport.js`，
有測試），`.gs` 一個數字都不重算；**單向，不做雙向同步**，試算表上改的東西
不會回到 app，`onEdit` 會當場還原並說明原因。

手動貼上那條路留著。自動的那條需要試算表那邊裝好指令碼，沒裝好、或她只是想
臨時貼一份到別的地方時，`#/settings/report` 的複製與下載照樣要能用。

代價是網頁應用程式的網址是一個公開端點。它只寫不讀 —— 沒有 `doGet`，
拿到網址也讀不出任何客戶資料 —— 最壞的情況是有人猜中密鑰後把她的報表寫成垃圾，
而那修復方式是按一次「立刻推一次」。這個代價比一把能讀走整個資料庫的金鑰小得多，
而那正是 ADR-0010 當初拒絕的東西。
