# 在壓表面板上選一個東西，不重畫整頁

第一版的壓表把每一次互動都接成 `paint(ctx)`：整頁 `innerHTML` 重寫、
重新掛一輪監聽、再把卡片組捲回選中那一張（`centerDeck()`）。
點一顆丸子、選一天、換一個人，走的都是同一條路。

使用者用了一輪之後的原話：

> 每當我點選一個東西，做什麼／器材／治療師等等，他就會像重新整理一樣，
> 閃一下並且回到最上面，這讓我很困擾，一點都不沉浸絲滑

## 為什麼這條路在這一頁特別貴

她記一位客戶要點五到六下（做什麼、幾點、器材或治療師、診間），一批二十幾位。
整頁重畫在別的頁面是「省事」，在這一頁是**一個晚上發生幾百次的閃爍**，
而且每一次都付三筆代價：

- `.deck` 重新建立 → `deck-in` 淡入動畫**重播一次**，也就是那個「閃一下」
- `.deck__card` 是 `overflow-y: auto` 的 → 它自己的 `scrollTop` 歸零，
  也就是那個「回到最上面」
- `.deck__track` 重畫 → `scrollLeft` 歸零，所以 ADR-0017 才需要每次重畫之後
  把卡片推回正中間

第三筆本來是設計的一部分（ADR-0017 明講了那個復位）。前兩筆從來不是誰決定的，
它們是「整頁重畫」這個作法的副作用 —— 而副作用比功能難發現，因為沒有人寫下它。

## 決定

**只重畫真的變了的那一塊。** 具體的分界：

| 她做了什麼 | 動到什麼 |
|---|---|
| 選時間、器材、治療師、診間 | 只改 `aria-pressed`，一個字的 HTML 都不重畫 |
| 換課程 | 只換 `[data-entfields]`（跟著課程走的那幾欄） |
| 換日子 | 小日曆只改哪一格被選中，只換 `[data-daypanel]` |
| 存好一筆 | 重讀資料，只換那張卡的內容，`scrollTop` 自己接回去 |
| 換人 | **只換那兩張卡**（舊的變 peek、新的展開），軌道不重畫 |
| 篩選、排序、搜尋 | 只換 `[data-wall]`，搜尋框不重建，游標留在裡面 |

**DOM 事件一律委派**在 `[data-page]` 與 `[data-deck]` 這兩個容器上。
這是上面那張表能成立的前提：任何一塊重畫之後都不必重新掛監聽，
也就不會有「這一塊重畫之後某顆按鈕就沒反應了」這種只在特定順序下出現的 bug。

**`ctx` 從 closure 搬到模組層。** 委派的處理器要拿到的是**當下**那一份資料，
不是它被掛上去那一刻的那一份；重讀之後整包換掉，處理器自然就讀到新的。

## ADR-0017 沒有被推翻

「左右滑交給 scroll-snap、旁邊那幾張只畫得出是誰、方向鍵與手勢並存」三件事都沒動。
`centerDeck()` 也還在 —— 只是它現在只在**整個軌道真的被重畫**時才跑
（開卡片組、以及「這位壓完了」之後名單可能整個變了那一次），
而不是每一次互動都跑。ADR-0017 記的是「重畫之後要復位」，
這一支記的是「大部分時候不要重畫」。

## Consequences

這一頁比其他頁多了一層規矩，看起來不一致 —— 這是刻意的：
它是唯一一個「同一張卡片上連續點五六下」的畫面，別的頁面沒有這個問題，
不需要為了對稱一起改。

驗證方式也跟別的頁不一樣。純函式那幾層照樣有 `tests/`，但
「點下去會不會閃、捲到哪裡會不會被洗掉」測不到 —— 這一輪是用一次性的
瀏覽器煙霧測試（假的資料層 + 真的 `schedule.js`）確認的：
挑日子與換課程之後 `.deck` 與 `.deck__card` 是**同一個節點**、
`scrollTop` 與 `scrollLeft` 不變。那個測試沒有留在版控裡
（它需要瀏覽器，而這個專案刻意沒有相依套件）。
