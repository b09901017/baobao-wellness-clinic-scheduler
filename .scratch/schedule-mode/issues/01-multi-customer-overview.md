# 壓表模式要能一次看到多位客戶，自己決定先處理誰

Status: ready-for-agent
回報者：使用者，2026-08-18
動工前先讀：`SPEC.md` 第 4.10、5.3、8.0、8.2、9 節與
`docs/adr/0002-app-records-decisions-it-does-not-make-them.md`

## 症狀

使用者的原話：

> 壓表我可能希望可以一次看到多個客戶的情況，然後可以決定我要先專注在哪個之類的

這不是跑出來的 bug —— 壓表模式還沒實作（`public/js/ui/views.js:40` 仍是第 7 步的骨架）。
症狀在文件裡：**現在照著 SPEC 第 8.2 節做，做出來的東西會是錯的**，
而且手機版會錯得比 iPad 版嚴重。

## 根因

**`SPEC.md:537`（第 8.2 節，行 533–597）**

> 這一頁的核心是**一次專注一位客戶的工單**，處理完往下一位。

- 手機版（行 539–566）整頁只有一張客戶卡，沒有任何看得到其他人的地方
- 佇列全貌被寫成「iPad 上多了三件手機做不到的事」之一（行 590–592），
  也就是**綜覽被定位成大螢幕的加值，不是主動線**
- 頂端進度寫成「3 / 12 位」，是照順序推進的模型

使用者要的是**先綜覽再決定**，而不是被系統決定順序。跳著處理在現行 SPEC 裡
只有 iPad 有，而她有一半時間拿手機。

**`SPEC.md:364`（第 5.3 節 `batches`）**

```
queue: [{ customerId, customerName, state, skippedReason }],
cursor,   // 目前處理到第幾位
```

`state` 已經是每位客戶自己的（`pending` / `done` / `skipped`），這部分夠用；
但 `cursor` 的語意是「處理到第幾位」，那是線性推進的模型，跳著做會失真。

**`public/js/ui/views.js:40`** 的 `/schedule` 骨架文案照抄了「一位一位」。

**`README.md:22`、`README.md:39`、`README.md:42`** 還寫著
「系統先算好建議時段讓她照著輸入」「並直接給出建議時段」「診間衝突當下就擋」——
這三句在 ADR-0002 與 SPEC 第 4.10 節確立後就已經是錯的，
跟這張 issue 同一區塊，一起修掉。

## 要做什麼

### 第一段：文件（現在就能做，不依賴任何未完成的步驟）

1. **改寫 SPEC 第 8.2 節成兩層**：

   - **綜覽** —— 選定課程後，一次列出所有待排客戶，每列要看得到足以決定
     優先順序的資訊：剩餘次數、可用天數、喜好程度、距上次多久、方案何時到期、
     永久限制標籤。可以從這裡跳進任何一位，不必照順序，處理完回綜覽。
   - **工單** —— 進到單一客戶後就是現在寫的那張卡：資訊攤開 + 快速記錄。
     完成後可以回綜覽，也可以直接往下一位。

   兩層在三個斷點都要存在，不是大螢幕特權：`< 600px` 綜覽與工單是兩個畫面，
   `≥ 900px` 用既有的 `.split`（`public/css/app.css:104`，900px 才變兩欄）
   左綜覽右工單並存。600–899px 沿用單欄但密度提高。

2. **每列要顯示什麼，寫進 SPEC，並標明手機取捨**：
   手機一列塞不下六項，挑姓名＋喜好、該課程剩餘次數、可用天數、
   以及**最強的那一個排序理由標籤**；其餘留給工單。
   排序理由一律是人話標籤（`可用 6 天・最少`、`距上次 21 天`、
   `方案 11/30 到期・剩 12 次`），**不要只給黑盒分數**（SPEC 第 9 節已經這樣要求）。

3. **改 SPEC 第 5.3 節 `cursor` 的註解語意**：從「目前處理到第幾位」改成
   「最後停留在哪一位（換裝置回來時捲到這裡）」。完成度一律由每筆 `queue`
   entry 的 `state` 推導，不從 `cursor` 推。頂端進度改成「已處理 3 / 12」，
   不是「第 3 位 / 12」。

4. **`views.js:40` 的骨架文案**改成與新的第 8.2 節一致。

5. ~~**修掉 README 那三句**（行 22、39、42）：不出建議時段、除醫療禁忌外只提示不阻擋。~~ **已完成**，見下方 Comments。

文件改完這張 issue 的第一段就算完成，可以先交付。

### 第二段：UI（第 7 步才做，這裡先把依賴寫清楚）

綜覽每一列需要的資料與它的來源：

| 欄位 | 來源 | 現況 |
|---|---|---|
| 該課程剩餘次數 | `domain/entitlements.js` 的 `counts()` | 已寫好且有測試 |

權重已經可以在設定 → 排序權重調（`public/js/ui/views/preferences.js`）。

## 不能違反的既有決定

- **`docs/adr/0002-app-records-decisions-it-does-not-make-them.md`：app 是記錄者不是判斷者。**
  綜覽是為了讓她決定先處理誰，**不是讓系統決定**。
  這一頁**不出建議時段**（SPEC 第 4.10 節，第一版不做），
  除醫療禁忌外所有檢查只提示不阻擋。
- **`docs/adr/0001-scheduling-queue-state-is-derived.md` 的 Consequences 與 SPEC 第 5.3 節：
  `queue` 的順序在批次建立當下凍結，不要每次開啟重算。**
  加了綜覽也一樣 —— 順序凍結是為了換裝置回來時不跳動，
  跳著處理靠的是「可以點任何一位」，不是「重新排序」。
  但每列的即時資訊（剩餘次數、可用天數）仍然現算。
- **先選課程**（SPEC 第 8.2 節，使用者原話：「壓復能的時候只要看到復能的剩餘次數就好」）。
  綜覽是**選定課程之後**的綜覽，不能變成跨課程的大表。
- **跨裝置續作**（SPEC 行 46–49）：手機與 iPad 共用同一個 `batch`，
  綜覽不能引入只存在本機的狀態。
- **SPEC 第 8.0 節**：以容器寬度判斷而非裝置型號、無 hover、無拖拉、
  最小點擊區 44px、字級 16px 起跳。可用日在手機用 chip 列表，
  31 格日期條只在 `≥ 900px` 出現。
- **CLAUDE.md 的文件分工**：規格改在 `SPEC.md`，這張 issue 不要變成第二份規格；
  若做到一半推翻了某個既有決定，補一支 ADR，不要偷偷改掉舊的。
