# 個人行程可以自己選顏色

Status: 待動工
來源：使用者，2026-08-23（spec.md 的 d 的後半）
確認過（2026-08-23）：**每一筆自己選，休假也可以選**

## 原話

> 「然後個人行程可以選顏色」

## 為什麼這件事有道理

個人行程是「公出、宜蘭休假、高齡演講」（`CONTEXT.md`）。這幾件事之間
**沒有系統看得懂的差別** —— 對系統來說它們一律是「那個時段有事、不綁客戶、
不產生任務、不扣次數」。但對她來說差很多，而且那個差別只有她知道。

這跟客戶身上的**備註**是同一個形狀：顏色由使用者自己分，系統不因為顏色
改變任何行為（ADR-0019）。所以做法照抄那一支，不要另外發明一種。

## 要做什麼

### 1. `domain/events.js`：顏色是一個名字，不是一串 hex

```js
export const EVENT_COLORS = ['grey', 'green', 'tea', 'red', 'blue', 'violet'];
```

跟備註同一組六色（`--mark-*`），理由也一樣：「六個就夠了 —— 再多她自己也分不清
哪個是哪個」。

**存名字不存 hex**：存 hex 的話深色模式那一份就沒有人換得掉，
而且色票以後要調就得回頭改每一筆資料。

- `colorClass(event)` → `'evcolor-violet'`，**沒選或不認得就回空字串**，
  讓它落回那一類本來的顏色（`kindClass()`）。
  這跟 `describeCategory()` 對不認得的類別大聲講出來的作法不同，是刻意的：
  類別錯了是資料壞了要看得見，顏色沒選只是她還沒挑，畫成預設色是對的。
- `validateEvent()` 多一條：`color` 有值但不在 `EVENT_COLORS` 裡就是錯的。
  存進去的東西要是乾淨的，顯示端的寬容是為了**已經存在的舊資料**，
  不是為了讓新的髒資料寫得進來。

### 2. 舊資料

現有的個人行程身上沒有 `color`，`colorClass()` 回空字串 → 落回類別預設色。
**不需要資料搬遷。**

### 3. `firestore.rules`

`validEvent()` 目前檢查的是「該有的欄位有沒有」，沒有擋多出來的欄位，
所以 `color` 不加也寫得進去。但依 `CLAUDE.md` 的連動表（新增欄位要在 Rules 開洞），
還是要補一條擋髒資料的：

```
&& (!('color' in d) || d.color is string)
```

`tests/rules.test.js` 跟著補。

### 4. `ui/views/eventEditor.js`

新增與編輯的表單多一排色丸，多一顆「跟著類別」的預設（不選）。

`ui/components/marks.js` 的 `mount()` 是備註專用的（文字＋顏色一起編），
借不過來。**要共用的是它底下那兩樣東西**：`domain/customerMarks.js` 的
`MARK_COLORS`（六色的 id / 標籤 / token）與 `app.css` 的 `.swatches` / `.swatch`。
色票只能有一份 —— 兩個地方各挑六個顏色，遲早會變成兩組不一樣的六色。

編輯器是 `mountNew` / `mountEdit`（掛在日曆的抽屜裡）與整頁兩個入口共用一份，
所以只會改到一個地方。**改完兩個入口都要看** —— 醫療禁忌硬性阻擋共用同一份的
理由（SPEC 第 8.3 節）同樣適用於這裡。

### 5. 日曆讀它

- 月檢視 `.monthbar`：`colorClass(e) || kindClass(e.category)`
- 日／週檢視的 `eventRow()`、`eventLine()`：同上
- `.evcolor-*` 那六個 class 在 `app.css`，各自設 `--kind-fg` / `--kind-bg`，
  跟 `.kind-*` / `.status-*` 是同一個介面。

### 6. 一個要講出來的取捨

她可以把一筆個人行程挑成藍色，而藍色在 issue `02` 之後是「已確認的來訪」。
**不擋** —— 那是她的畫面、她的分類，而且個人行程與來訪在日曆上本來就長得不一樣
（可以跨天、沒有狀態徽章、點開是另一種卡片）。

但**休假身上的斜線紋不跟著顏色走** —— 不管她把休假挑成什麼顏色，
斜線都在。那條紋路講的是「這幾天我不在」，不是一種配色。
