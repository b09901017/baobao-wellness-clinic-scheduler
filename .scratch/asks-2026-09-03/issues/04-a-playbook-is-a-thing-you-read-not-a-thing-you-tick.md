# 備忘錄：她自己寫的流程與心得，一份資料模型

Status: done

ADR-0057／0059（不為了一個畫面多寫一份資料）、ADR-0062（白話版不是第二份紀錄）、
`CONTEXT.md` 的「隨手記」「備註」「任務」「待辦」

## 她要的

> 我希望新增一個功能是，備忘錄，就是我可以記錄一些自己的心得或是像上面這樣要
> 注意的事項……像是復健科流程 這個就是屬於我會習慣的我會漸漸上手的，只需要
> 當下打開備忘錄看就好，不用什麼事前提醒或是事後提醒。
>
> 也許可以依科別/項目分類（如：點滴、復健科、營養諮詢、外檢）。在手機版可一鍵
> 隨時查閱，不需要變成打勾任務。然後也可以自己命名標題，標籤項目等等。

## 這個詞跟「隨手記」撞了，她決定怎麼分（2026-09-03）

`CONTEXT.md` 的「隨手記」詞條底下 `_Avoid_` 那一行原本明列著**備忘錄、筆記、便條** ——
也就是說，她口語講的「備忘錄」在詞彙表上等於「隨手記」。

兩個東西完全不同：

| | 隨手記 | 備忘錄（這一輪） |
|---|---|---|
| 誰讓它出現 | 客人臨時說的一件小事 | 她自己整理的一段流程 |
| 會不會消失 | 會 —— 勾掉就沒事了 | 不會，它是要一直查的 |
| 上日曆嗎 | 掛了日期就上（ADR-0044） | 不上 |
| 綁誰 | 選填綁客戶 | 綁**課程**，不綁人 |
| 一筆多長 | 一行字（200 字上限） | 一整份，分節 |

**她選的是：這個東西就叫「備忘錄」，把「隨手記」的 `_Avoid_` 裡那一項拿掉，
然後在兩個詞條上各寫一行界線。** 所以：

- 畫面上叫 **備忘錄**（頁面抬頭寫「備忘錄 / SOP」—— 她自己講的那個名字，
  SOP 那三個字讓「這不是隨手記」一眼看得出來）
- `CONTEXT.md` 的「隨手記」`_Avoid_` 拿掉「備忘錄」，**留著筆記與便條**
  （那兩個仍然是隨手記的禁用同義詞，而且不是這一輪要的詞）
- 兩個詞條各加一行指向對方：
  - 隨手記 →「與**備忘錄**的界線：隨手記是一件會被勾掉的小事，備忘錄是一份不會消失的流程。」
  - 備忘錄 →「與**隨手記**的界線：備忘錄綁課程不綁人、不上日曆、勾不掉。」
- 程式裡的識別字用英文 `playbook` / `playbooks`，跟全站其餘模組一致
  （`notes`、`events`、`visits` 都是英文）

## 資料模型

新的頂層集合 `playbooks/{id}`：

```js
{
  title,        // '營養點滴'。必填，<= 40 字
  tag,          // '點滴' | null。分類，選填，自由文字
  courseIds,    // ['course-iv-drip']。掛哪些課程，選填
  sections: [   // 有序，1–20 節
    {
      heading,  // '前情提醒' | ''（沒有標題就是一段直白的清單）
      when,     // 'before' | 'onday' | 'after' | null
      body,     // 多行純文字，<= 2000 字。一行就是一件事
    },
  ],
  pinned,       // bool。釘在清單最上面
  createdBy, createdAt, updatedAt, deletedAt
}
```

### 為什麼是頂層集合，不是 `config/` 底下的主檔

主檔（`config/app/{type}`）的東西有一個共同點：**別的資料用 id 指著它**
（時段指課程、來訪指診間）。備忘錄沒有人指著它，是它去指別人（`courseIds`）。

而且 `config.loadAll()` 會把**每一種主檔全部讀進來**，設定頁與壓表都在呼叫它。
備忘錄的 `body` 是長文字，塞進去等於她每次進壓表都多下載幾千字，
換不到任何東西。

### 為什麼一份備忘錄只有一個 `tag`

她講的是「標籤」（複數感），但清單是**照分類分組**畫的。多標籤的話同一份備忘錄
會出現在兩個群組底下 —— 而她要找「點滴那份」的時候看到兩份長得一樣的東西，
第一個念頭是「我是不是建了兩次」。

「這是點滴的還是外檢的」本來就只有一個答案。真的需要第二個維度時，
那個維度是 `courseIds`（掛哪些課程），而它本來就是多選的。

### 為什麼 `courseIds` 是選填

她自己講的：「像外檢沒有這個項目就可以不標，寫在標題就好」。
外檢不是系統裡的課程，所以掛不上去 —— 那一份備忘錄照樣存在、照樣查得到，
只是不會自動浮出來（issue 06）。

### `when`：這一節是什麼時候要看的

四個值，`null`（隨時看）是預設：

| `when` | 畫面上 | 什麼時候自動浮出來（issue 06） |
|---|---|---|
| `before` | 事前 | 那一筆來訪還沒到（`pending_confirm` / `confirmed` 且日期在今天之後） |
| `onday` | 當天 | 那一筆來訪就是今天 |
| `after` | 結束後 | 那一筆已完成／未到，或日期已經過了 |
| `null` | 隨時看 | 不自動浮，只在備忘錄那一頁看得到 |

**這一格是整個備忘錄功能唯一「系統看得懂」的地方**，其餘全部是給人讀的字。
她的筆記本來就是照這個切的（前情提醒／當天／結束），所以這不是我們發明的分段，
是把她已經有的結構記下來。

「飯後打針」放在點滴那份備忘錄的 `before` 那一節 —— 這就是她問的
「該何時提醒、怎麼提醒」的答案（issue 06），**不多開一張要勾的東西**。

## `/domain/playbook.js`（純函式）

| 函式 | 回答什麼 |
|---|---|
| `SECTION_WHEN` | 四個時機的清單（id / label），畫面與比對共用一份 |
| `normalize(pb)` | 空字串正規化成 `null`（`tag`）、去掉空白節、`courseIds` 去重 |
| `validatePlaybook(pb)` | 存檔前的檢查，回訊息陣列 |
| `groupByTag(list)` | 清單分組。**沒有分類的收在最後一組**，抬頭「沒有分類」，不叫「其他」 |
| `playbooksForVisit(list, visit)` | 這一筆來訪的時段掛到哪幾份備忘錄（比 `slot.courseId`） |
| `whenForVisit(visit, today)` | 這一筆現在該看哪一節（上表那四列） |
| `linesOf(section)` | `body` 拆成行、去掉空行 —— 閱讀頁與浮出來那一段共用，**兩份寫法遲早有一份會把空行畫成一個空的項目符號** |
| `matches(pb, q)` | 搜尋：標題、分類、每一節的標題與內文都比 |

`whenForVisit()` 放在 domain 而不是放在畫面裡，理由跟 `domain/todoFlow.js` 同一條：
日曆、確認動線、來訪編輯器三個地方會問同一句，而同一筆來訪在三個畫面浮出不同的
一節，她不會知道哪個算數。

## `/data/playbooks.js`

`repo` 的標準包裝（`list` / `getOne` / `create` / `update` / `softDelete` / `restore`），
所以自動有稽核、軟刪除、復原。

多一層**行程內快取**：

```js
// 備忘錄很少改，而它要在日曆、確認動線、來訪編輯器三個地方被問到。
// 每一次都重讀等於為了一段幾乎不變的參考文字，在她的行動網路上多打幾輪往返。
// 任何一次寫入都把它清掉 —— 她改完立刻要看到改完的樣子。
let cache = null;
```

**不排序、不加 `where`**：`repo.list()` 本來就帶 `deletedAt == null`，
而純等值查詢不需要複合索引。排序在 client 做（她的備忘錄不會有一百份）。

## `firestore.rules`

```
function validPlaybook() {
  let d = request.resource.data;
  return d.title is string && d.title.size() > 0 && d.title.size() <= 40
    && (!('tag' in d) || d.tag == null || d.tag is string)
    && d.sections is list && d.sections.size() <= 20
    && (!('courseIds' in d) || d.courseIds is list);
}

match /playbooks/{id} {
  allow read:   if allowed();
  allow create, update: if allowed() && keepsExistingId() && validPlaybook();
  allow delete: if false;
}
```

跟 `validNote()` 同一個深度：**只擋型別與大小，逐節的內容前端擋**
（SPEC 第 6.7 節的雙層驗證，Rules 那一層不逐欄位驗巢狀陣列 ——
`validVisit()` 對 `slots` 做過同一個判斷）。

`tests/rules.test.js` 要加：沒登入讀不到、標題空的存不進去、超過 20 節存不進去。

## `domain/dayReview.js`：留在「其他」

備忘錄的稽核會落進最後那一段「其他」（它的 `match` 永遠是 true，ADR-0062）。
**這是對的，不要為它多開一段**：改備忘錄不是她一天的流程裡的一步，
而那一頁分段的順序就是流程。ADR-0062 保證一則都不會被丟掉，所以它照樣看得到。

## 測試

`tests/playbook.test.js`（新）：

- `validatePlaybook()`：標題必填、節數上限、內文長度、`when` 認不得的值退回 `null`
