# 客戶詳情加購一整個方案，可以先微調

Status: 已完成
Blocked by: 04

## 她說的

> 客戶詳情那邊的加購可以加購一整個方案

> 我希望方案也可以微調，就是這個客戶的某個方案中的例如復能三選一(60)少幾次然後
> 換成其他的之類的，這個不常發生，但是就是可以如果我加購方案，可以微調這個方案

微調 =「**改次數 + 加項目**」（2026-09-06 確認）。

## 現在是什麼樣

`expandPlan()` 只有兩個呼叫端：新增客戶（`data/customers.js` 的 `createWithPlan()`）
與批次建立（`domain/bulkCustomers.js`）。**客戶詳情買不了方案** —— 她只能一項一項
加購。

而 `createWithPlan()` 在同一個 commit 裡做了三件事，少任何一件都會留下一份
「看起來正常、其實少了一半」的資料：

1. 建那幾筆額度
2. `missingPairs()`：健檢配二返（ADR-0022）
3. `deliveryNoteFor()`：營養品配一筆「哪天順便給」的提醒（ADR-0059）

那支檔頭已經寫過代價：「另外寫一支去建加購的話，那幾筆健檢就會少掉二返，
而那件事要等她幾週後真的要記一筆二返才會被發現」。

## 要做什麼

### 一、`data/customers.js`：把那三件事抽成一支，兩條路共用

```js
/** 一批額度連同它們的二返與交付提醒，一個 commit 寫完。 */
async function entitlementWrites(customerId, dataList, { customer }) { … }

export async function createEntitlement(customerId, data, opts) { … }   // 收一筆
export async function addEntitlements(customerId, dataList, opts) { … } // 收一批（新）
```

`createWithPlan()` 也改成走同一段組裝。**三條路一份實作** —— 這正是
`buy.js` 檔頭那句「多接一次的代價已經付過了」。

### 二、`domain/entitlements.js`：`expandPlan()` 多存一欄

```js
purchaseId,      // 這一次購買的 id。同一次展開出來的每一筆都一樣
sourcePlanQty,   // 展開當下、乘過購買數量之後的次數。單項加購沒有這一欄
```

`purchaseId` 是 `06` 那一頁分組與改購買日期要用的 —— 理由寫在那一支。
單項加購也給它一個（自己一組）。

它是**微調的證據**：`totalQty !== sourcePlanQty` 就是「這一項跟方案本來的不一樣」。
存數字而不是一個布林，是因為 `06` 那一頁要印得出「15 次（方案本來 20）」——
布林只講得出「改過」，而她想知道的是改成什麼。

存快照而不回頭查範本，理由同 ADR-0003：範本會被就地改。

### 三、客戶詳情：額度那一區多一顆「加購方案」

跟現有的「加購」並排。點下去是一張表：

```
加購方案

方案      (筋骨強身)(8萬方案)
買幾套     [ 1 ] +1 +5

展開之後會建立
  身體組成分析        4 次   [−][+]
  復健科醫師門診      2 次   [−][+]
  物理治療師諮詢      4 次   [−][+]
  營養師諮詢          4 次   [−][+]
  體適能檢查分析      4 次   [−][+]
  復能三選一(60)     20 次   [−][+]   ← 改成 15
  ILIB(60)          12 次   [−][+]
                                    ＋ 加一項

上面改過 1 項
                              [加購]  [取消]
```

- **次數改成 0 = 不要那一項**，那一列變灰、加一句「不建立」。不用另外一顆
  垃圾桶：`[−]` 按到 0 就是同一個意思，而多一顆刪除鈕等於多一種要學的操作。
- **「加一項」就是 `components/buy.js` 那一張表**，跟批次建立那一頁的微調面板
  一模一樣（`ui/views/customersBulk.js` 已經是這樣接的）—— 她不用學第二種操作。
- **「上面改過 N 項」那一句是必要的**，跟「進階設定」摺疊起來要講出改過幾樣是
  同一條規則：收起來的東西不能安靜地生效。

### 四、存下去

一次 commit：方案展開（扣掉 0 的）+ 加購的那幾筆 + 它們的二返 + 交付提醒。
走 `addEntitlements()`。

`toast.withSaveState()` 要傳 `key`（`tests/save-guards.test.js` 會掃出漏掉的）。

## 三個入口一起（她的第四點）

| 入口 | 現在 | 這一輪 |
|---|---|---|
| 客戶詳情 → 加購 | 一項一項 | 加一顆「加購方案」，含微調 |
| 新增一位客戶 | 選方案 + 加一項 | 展開清單也可以微調（同一個面板） |
| 快速建立一群 | 共用方案 + 每列微調加一項 | 同上；共用方案的微調**套用到整批** |

三邊的微調面板是**同一支** `ui/components/planTweak.js`（新）。
呼叫端只回答「哪一塊要重畫」，跟 `buy.wire()` 同一個分工。

批次那一頁的共用方案微調套用到整批 —— 一位一位改她要點五六十下。
**每一列本來就有的「微調」仍然只影響那一位**，兩層不衝突。

## 不做的

- **不改方案範本。** 微調只活在這一次購買上（ADR-0003：展開後與範本脫鉤）。
  面板上要有一句話講清楚：「只改這一位，方案範本不變」。
- **不做「換成其他的」這個動作本身。** 她的原話是「少幾次然後換成其他的」——
  那是兩步：把復能改成 15、再「加一項」加 5 次 INDIBA(30)。做成一個「換」的
  動作要她先想清楚換的是什麼，而分兩步她每一步都看得到結果。
- **不在這一頁改已經買好的額度。** 那是額度卡上的「調整」，一頁一件事（ADR-0034）。

## 測試

- `tests/bulk-customers.test.js`：微調過的展開結果帶得出 `sourcePlanQty`；
  次數改成 0 的那一項不出現在結果裡。
- `tests/domain.test.js`：`expandPlan()` 的 `sourcePlanQty` 有乘過購買數量。
- `tests/save-guards.test.js`：新按鈕有 `key`。
- `tests-e2e/`：加購一個方案 + 微調一項 + 加一項，存完之後客戶詳情上額度的
  張數與次數對得起來，而且**健檢那一筆真的配到了二返**（這一條是這支 issue
  最容易安靜壞掉的地方）。

## 連帶

`firestore.rules` 的 `validEntitlement()` 補 `sourcePlanQty`（`null` 或大於 0 的整數）
與 `purchaseId`（`null` 或字串）的形狀檢查，`tests-e2e/rules/` 跟著補一條。
