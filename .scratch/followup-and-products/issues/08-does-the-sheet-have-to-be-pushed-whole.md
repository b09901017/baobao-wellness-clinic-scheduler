# 試算表每次都要整包重推嗎？（回答）

Status: 已回答，等她決定要不要做
提問者：使用者，2026-08-27（「我想問試算表每次都要全部重新更新嗎 不能只動修改的那些嗎，還是你有甚麼顧慮?」）
動工前先讀：`docs/adr/0010`、`docs/adr/0013`、`docs/adr/0024`

## 現在怎麼運作

1. 任何一次寫入成功 → `data/repo.js` 的 `onCommitted` 通知 `sheetSync.schedule()`
2. 排一個 10 秒的計時器（`QUIET_MS`）。10 秒內又有寫入就重新計時 ——
   **她一晚上壓十幾筆，只會換來一次推送**
3. 時間到 → `buildBundle()` 讀「全部客戶 + 全部額度 + 前後 400 天的來訪 + 全部任務 + 主檔」，
   排成整包送出去
4. `sheets/readonly-report.gs` 收到之後，一位客戶一張分頁，**清空重畫**

所以「整包」有兩層：**送整包**，而且**對面清空重畫**。

## 為什麼當初這樣做

`domain/sheetReport.js` 的檔頭寫著理由：**整包是冪等的。**

漏推一次（離線、關瀏覽器、Apps Script 掛掉），下一次會補回來，
不需要在兩邊維護一份「哪些變了」的帳。而那種帳**一定會對不起來** ——
對不起來的那一天，畫面上看起來跟推好了一模一樣，這正是舊 Apps Script
靜默失效的模式。

## 真正的代價在哪裡

| 環節 | 現在的代價 |
|---|---|
| Firestore 讀取 | 每次推送重讀全部客戶／額度／來訪／任務。**這是最貴的一項** |
| 網路 | 一包 JSON。50 位客戶大約幾百 KB |
| Apps Script | 每張分頁清空重畫。這是 `.gs` 那邊最慢的一段 |

10 秒的安靜期已經把「一晚壓二十筆 = 二十次推送」壓成一次了。
所以現在的問題不是**推太多次**，是**每一次都太重**。

## 可以只推改動過的那幾張嗎

可以，而且不必放棄冪等。作法是**每張分頁算一個指紋**：

1. `syncBundle()` 給每一張 sheet 算一個 hash（那張的 `rows` + `dates` + `tasks` +
   `followupNotes` 全部序列化之後雜湊）
2. 把「上次推成功時每張的 hash」記在這台裝置的 `localStorage`
3. 這次只送 hash 變了的那幾張，另外送一份**完整的名單**（誰應該存在）
4. `.gs` 只重畫收到的那幾張，並且刪掉不在名單裡的分頁

第 3 步的完整名單是關鍵：沒有它，刪掉的客戶那張分頁會永遠留在試算表上。

**它仍然是冪等的**：hash 對不上就重推，`localStorage` 被清掉就整包重推一次。

### 但省不到最貴的那一項

指紋要算得出來，就得先有資料 —— 也就是 `buildBundle()` 那幾次 Firestore 讀取
**一次都省不掉**。省下來的只有網路與 `.gs` 的重畫時間。

## 我的建議

**先不要做。** 三個理由：

1. 最貴的是 Firestore 讀取，而這個作法省不到它
2. 這是**唯一一條**通往試算表的路，弄壞了她會在幾天後才發現（她不是每天看試算表）
3. 現在沒有證據說它慢。同步是背景跑的、失敗不擋寫入、痕跡留在設定頁

**如果要做，先做這個**（更便宜、風險更低）：
把 `buildBundle()` 那幾次讀取改成吃 app 已經在記憶體裡的那一份，
不要每次都重打 Firestore。那才是真正的成本所在。

→ **等她說一句「我覺得慢」再動。** 現在沒有那句話。
