# 進度追蹤頁：一頁看完每位客戶這個月排了哪些時段、各自到哪一步

Status: open
回報者：使用者，2026-08-20
動工前先讀：`SPEC.md` 第 8.0 節（斷點）、第 8.5 節（客戶總覽）、
`docs/adr/0004-counts-are-derived-in-detail-cached-in-lists.md`、
`docs/adr/0018-detail-pages-are-one-page-not-a-stack-of-cards.md`

## 她要什麼

> 我還希望多做一個進度追蹤頁面，也就是呈現每個客戶，我目前這個月預約了那些時段，
> 而這些時段分別的狀態是什麼（待確認，已確認，已完成），我希望能有一個頁面讓我
> 一目了然的掌握我所有客戶的情況，並且這個頁面要和 todo 日曆對的上…
> **進度追蹤那頁是唯讀的不能修改**

## 現在沒有，兩個最接近的都不是

| | 為什麼不是 |
|---|---|
| 客戶總覽 `#/customers` | 一位客戶一列的**合計**（各池進度、上次來訪、下次預約），看不到每一段各自是什麼狀態 |
| 客戶詳情的「這個月」 | 一次只看得到一位 |

## 想要的樣子

一位客戶一列（或一組），底下攤開這個月的每一筆來訪與時段，
每一段標出三種狀態的其中一種。**唯讀**：不能點進編輯器改東西。

四個實作上的重點：

1. **狀態的分類與顏色不可以自己寫一份。** 和日曆（`issues/03`）用同一組
   `status → { label, cls }`。使用者原話：「這很重要」。
   同一位客戶在兩個畫面顯示不同狀態，她不會知道哪個算數
   —— 這和 `CLAUDE.md` 那張表上「排序不要另寫一套」是同一種毛病。
2. **次數現算，不讀計數欄位。** 這一頁是拿來核對的，
   而 ADR-0004 說真正不能錯的地方一律現算。它一次要讀二十幾位客戶的來訪，
   所以要先量一下讀取量 —— `visits` 有 `date` 的複合索引（`SPEC.md` 第 5.4 節），
   照月份範圍一次撈完再自己分組，不要一位客戶打一次。
3. **唯讀要防得住誤觸。** 她說「不小心動到會有提醒」。
   最乾淨的做法是這一頁根本沒有可以改東西的控制項；如果要留「點進去看那一筆」
   的連結，那要是**讀取模式的資訊卡片**（ADR-0020 那條規矩：
   「她點一筆的十次有九次只是要確認那天幾點、誰、做什麼」），不是編輯器。
4. **版型三段都要能用**（`SPEC.md` 第 8.0 節）。手機是單欄堆疊，
   iPad 橫式可以做成客戶 × 日期的矩陣。**不要做成只有 iPad 能看的表格** ——
   `SPEC.md` 第 1 節：不能有任何功能只有某台裝置做得到。

## 要問她的

- **「這個月」是固定當月，還是可以往前後翻？** 月底她已經在排下個月了，
  只給當月大概不夠用。
- **要不要放進導覽列？** 現在底下五個分頁（待辦／客戶／壓表／日曆／設定）已經滿了。
  可以掛在客戶頁的一顆切換，或是日曆頂端多一個檢視。這會影響她找不找得到它。
