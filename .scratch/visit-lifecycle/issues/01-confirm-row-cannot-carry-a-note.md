# 「跟客人確認時間」那一列寫不了「禮拜一再問問」

Status: done
回報者：使用者，2026-08-20
動工前先讀：`SPEC.md` 第 8.1 節的確認動線、`CONTEXT.md` 的「任務」「隨手記」「備註」、
`docs/adr/0019-customer-notes-become-coloured-marks.md`

## 症狀

她的原話：

> 我看著 todo 一個一個和客戶確認，有些可以直接打勾，有些可以在這個 todo 旁備註，
> 禮拜一再問問等等

`#/todo/confirm` 現在只有兩個結果：打勾確認，或是逐段標「客人說不行」。
**沒有第三條路** —— 「問了但還沒回」「她說禮拜一再說」這種狀態寫不進去，
下次打開那一列長得跟從來沒問過的一模一樣。

## 為什麼現在沒有

確認清單不是任務，是從 `visits(status === 'pending_confirm')` **推導**出來的
（`ui/views/home.js` 的 `renderConfirm()`），所以它沒有 `note` 欄位可以寫。

現有的三個欄位都不對，這是刻意的界線（`CONTEXT.md`）：

| | 為什麼不對 |
|---|---|
| `visit.note` | 是「這一天」的事，而且只有來訪編輯器改得到 —— 她人在 LINE 裡，不會為了寫一句話點進去 |
| **隨手記** | 沒有掛在「這件事」上，勾掉之後和這筆來訪就斷了 |
| **備註**（`customer.marks`） | 跟著人一輩子，不會消失（ADR-0019）。「禮拜一再問問」下禮拜一就過期了 |

## 想要的樣子

在確認清單那一列旁邊直接寫一句，寫完那一列要看得出「問過了，在等」。

要決定的兩件事（動工前先想清楚，這一支的重點在這裡）：

1. **這句話存在哪裡。** 建議存在 `visit` 上一個新欄位（例：`followUpNote` 加
   `followUpAt`），一位客戶好幾天的來訪就每一筆各自帶 —— 因為她問的常常是
   「9/3 那天可以嗎」而不是整包。要是決定一位客戶只寫一句，就要說清楚
   它掛在誰身上。
2. **要不要影響「已等 N 天」。** 現在那個數字是從壓表當下算的
   （`waitedDays()`），寫了備註之後她心裡的計時應該從「問過的那天」重新算，
   否則紅字會一直掛著。

`customers/{id}/availability` 上已經有一個 `followupNote`（「禮拜一再確認一次」），
是同一種東西在另一個地方 —— 命名請對齊，不要一邊叫 `followUp` 一邊叫 `followup`。

## 不要順手做的事

- 不要把它做成一種**任務**。任務是來訪自動產生、有死線的（`CONTEXT.md`），
  這一句是她手寫的、隨時會被換掉的。做成任務就要決定死線是哪天，而那沒有答案。
- 不要因為寫了備註就把那筆來訪移出確認清單。事情還沒完，移走就等於忘記。

### 這一支要決定的兩件事，決定了

**① 那一句存在哪裡 → `visit.followupNote` + `visit.followupAt`，一位客戶所有還在等的來訪各自帶一份同樣的字。**

這一支原本猜「她問的常常是『9/3 那天可以嗎』而不是整包」，所以想做成逐筆各寫各的。
實際看動線之後改了：確認清單是**一位客戶一列**（`byCustomer()`），
而她的原話是「在這個 todo 旁備註」—— 那個 todo 就是那一列，就是那個人。
客人也是一次講完一整天的（這正是確認動線不做整批的理由的反面）。

所以欄位留在來訪上（因為它必須跟著 `pending_confirm` 一起過期，
掛在客戶身上就變成永遠不會消失的**備註**了），但**寫的時候一次寫完那位客戶的每一筆**。
一個 commit，不是好幾筆 —— 分開寫的話她按復原只退得回其中一筆，
那比沒有復原更糟（`repo.withUndo` 的既有規矩）。

**② 影響「已等 N 天」→ 影響，從問的那天重新算。**

問過了就不再算「久了」（`late === false`），文字也從「已等 6 天」變成「問過了・1 天前」。
理由就是這一支寫的：那個數字唯一的用途是「這個該催了嗎」，
她禮拜五才問過的人禮拜六不該是紅的，不然紅字一直掛著然後她就不看它了。

### 三個沒寫在這一支裡、但做了的決定

1. **規則搬進 `/domain`，開了一支新檔。** 原本 `waitedDays()` 住在 `ui/views/home.js`
   裡，而「這一列現在是什麼狀態」是一條會被問第二次的規則 ——
   `issues/07` 的進度追蹤頁要問同一句話。照 `CLAUDE.md` 的規矩它不該留在畫面上，
   所以開了 `domain/confirmations.js`，順便讓它測得到（`tests/confirmations.test.js`）。

2. **確認或取消時把那一句收掉。** 「禮拜一再問問」在轉成 `confirmed` 之後就過期了，
   留著只會在別的畫面變成一句騙人的話。改動留在稽核紀錄裡，沒有真的消失。

3. **順手修掉一個和註解不符的地方。** 舊的 `waitedDays()` 註解寫著
   「那時顯示『剛壓』，不要假裝是 0 天」，但呼叫端寫的是 `?? 0`，
   所以時間戳還沒回來時畫面上印的正是「已等 0 天」。現在真的會印「剛壓」。

### 刻意沒做的

- **不是任務。** 沒有動 `TASK_KINDS`，沒有動 `syncTasksForVisit()`。
- **寫了備註不會把那一筆移出確認清單。** 事情還沒完，移走就等於忘記。
- **`firestore.rules` 不用改。** `validVisit()` 只驗必填的那四個，多的欄位放行。
- **客戶詳情頁沒有跟著顯示那一句。** 它是「確認動線」的東西，不是客戶的背景資訊 ——
  真要它出現在第二個地方，那是 `issues/07` 的事，而且要讀 `domain/confirmations.js`。
