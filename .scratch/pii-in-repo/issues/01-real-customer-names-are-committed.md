# 有六位真實客戶的姓名已經被 commit 進 repo 了

Status: open
發現者：Claude，2026-08-20（比對她給的 `.xlsx` 與 repo 內容時掃到的）
動工前先讀：`SPEC.md` 第 10 節「資安」、`CLAUDE.md` 的文件分工那一段

## 症狀

`SPEC.md` 第 10 節寫著：

> **絕對不能 commit 的**：…任何含**真實客戶資料**的匯出檔、備份 JSON、截圖
>
> 一旦真實客戶資料被 commit 過，就算之後刪掉，**它仍然留在 git 歷史裡**。

`CLAUDE.md` 也寫著「`docs/legacy/` 與 `docs/adr/` 不放任何真實客戶姓名或健康資訊」。

但拿 2026-08-20 那份 `.xlsx` 的 21 位客戶姓名去掃被 git 追蹤的檔案，
**六位對得上，散在六個檔案裡**：

| 檔案 | 幾位 | 以什麼形式 |
|---|---|---|
| `.claude/skills/calendar-sheet-merge/SKILL.md` | 1 | 姓名比對的例子 |
| `.claude/skills/calendar-sheet-merge/references/findings.md` | 1 | 「照抄的話客戶會叫 ⋯⋯」的例子 |
| `.claude/skills/calendar-sheet-merge/references/shorthand.md` | 3 | 行事曆簡寫對照表的例子 |
| `.claude/skills/calendar-sheet-merge/scripts/merge.mjs` | 3 | 程式註解裡的例子 |
| `.scratch/followup-visit/issues/01-…` | 1 | 引用行事曆原文的例子 |
| `public/js/domain/legacyImport.js` | 1 | 註解裡的解析範例，**還帶著器材偏好** |

全部都是**當成範例寫進註解與文件**的，不是資料檔 —— 寫的人是為了把規則講清楚。
但 `docs/legacy/README.md` 同樣在講規則，那裡從第一天就一律寫「客戶A、客戶B」，
可見這條線本來就畫得出來。

**這不是這一輪動到的東西，是既有狀況。** 記下來是因為它違反的是專案自己的規矩，
而且時間拖越久、歷史越長，處理起來越麻煩。

## 想要的樣子

兩件事分開看，難度差很多：

### 1. 把工作區裡的名字換成匿名（容易，值得馬上做）

六個檔案的姓名換成 `客戶A`、`客戶B`，語意一個都不會掉 ——
那些例子講的是「去姓」「異體字」「分頁名和 A2 對不起來」這些**規則**，
規則不需要真名。`legacyImport.js` 那一筆還要順手把器材偏好一起改掉。

改完之後補一個測試，讓它掃不到真名再回來 —— 但**測試裡不能寫真名**
（否則就是又 commit 了一次）。作法可以是掃「中文姓名 + 三到四位數字」這種形狀，
或是讓她把名單放在一個 gitignore 的檔案裡由測試選讀。這一段要想清楚再動手，
`tests/no-secrets.test.js` 是現成的骨架（它掃的是私鑰特徵，同一個模式）。

### 2. 洗掉 git 歷史（麻煩，要她決定）

改工作區**不會**讓名字從歷史裡消失。真的要清掉得 `git filter-repo` 之類的東西
重寫歷史並強推，而那會讓所有既有的 clone 失效、PR 對不上。

**要不要做是她的決定，不是技術決定。** 判斷的依據是：

- repo 是 **private** 的，看得到的人目前只有她自己
- 洩漏的是**姓名**，沒有病歷、電話、地址；只有 `legacyImport.js` 那一筆
  把姓名和器材偏好放在一起
- 對照之下，真正會出事的是服務帳號金鑰，而那個有 `tests/no-secrets.test.js` 守著

我的建議是**先做第 1 件、把第 2 件當成「知道有這回事」**，
除非哪天這個 repo 要開放給同事或轉成公開 —— 那時第 2 件就變成必須做。

## 不要順手做的事

- 不要為了清歷史就去改別人已經合併的 commit，先問她。
- 不要在修的時候順便把那些例子刪掉。**例子要留著**，只是換成假名 ——
  那幾條規則（去姓、異體字、分頁名打錯）是真的踩過的坑，講清楚比乾淨重要。
