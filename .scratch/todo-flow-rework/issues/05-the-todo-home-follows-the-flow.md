# 待辦首頁要照流程的順序排，看得出下一步

Status: done
來源：使用者，2026-08-23
動工前先讀：本資料夾的 `spec.md`、`SPEC.md` 第 8.0、8.1 節、
`docs/adr/0039`（顏色為什麼不夠用）

## 原話

> 「我希望優化 todo 總覽那邊的 UIUX，目前分門別類其實還不錯，但希望能夠更直觀
> 更符合，就是例如照著我剛剛說的那些流程，或是用不同顏色，或是不同呈現方式等等
> ⋯⋯ 就是可以讓我更清楚流程排序 下一步等等」

## 現況

`views/home.js` 的 `overviewHtml()`：三顆大數字，底下一排 `grouprow`。
每一列都長得一樣，順序是**寫死在那個樣板裡的出現順序**，而那個順序沒有任何人
決定過 —— 它是「先寫的先出現」。她要的是「下一步是什麼」，而畫面回答的是
「有哪些種類」。

## 要做什麼

### `domain/todoFlow.js`（新，純函式）

段落的定義與歸屬放在 domain，不放在畫面裡：「這件事是流程的第幾步」
之後進度追蹤頁也會問同一句，而同一件事在兩個畫面歸到不同的段，
她不會知道哪個算數（同 ADR-0028 的理由）。

```js
export const STAGES = [
  { id: 'ask',     n: 1, label: '問到時間',   tone: 'none'      },
  { id: 'book',    n: 2, label: '壓表',       tone: 'none'      },
  { id: 'confirm', n: 3, label: '等客人回覆', tone: 'pending'   },
  { id: 'before',  n: 4, label: '來訪前一天', tone: 'confirmed' },
  { id: 'onday',   n: 5, label: '來訪當天',   tone: 'onday'     },
  { id: 'after',   n: 6, label: '來訪之後',   tone: 'done'      },
  { id: 'undo',    n: 7, label: '要收回來的', tone: 'no-show'   },
];

/** 一種待辦屬於哪一段。認不得的種類回 'before'。 */
export function stageOf(kind)
```

歸屬：

| 待辦 | 段 |
|---|---|
| 問這輪的時間、客戶填好的時間 | `ask` |
| 壓表登記 | `book` |
| 跟客人確認時間 | `confirm` |
| Examine、耀聖 | `before` |
| 簽療程單 | `onday` |
| 追蹤健檢報告、約二返 | `after` |
| 取消 ⋯⋯（`isCancelKind`） | `undo` |
| **認不得的**（舊的打電話／Abovee、她手動加的） | `before` |

認不得的落在 `before` 不是隨便挑的：那幾種本來就是「來訪之前要去做的事」。
但這一條要寫在註解裡，不然下一個人會以為是漏掉。

### 顏色：**段落的顏色就是那一筆來訪當下在日曆上的顏色**

`tone` 對到 `tokens.css` 已經有的那四個來訪狀態色，不新增任何色相：

| tone | 用哪個 token | 為什麼 |
|---|---|---|
| `none` | 中性（`--text-mute`） | 那時候還沒有來訪這個東西 |
| `pending` | `--visit-pending`（琥珀） | 那幾筆現在就是「已壓表・待客人確認」 |
| `confirmed` | `--visit-confirmed`（靛藍） | 那幾筆現在就是「已確認」 |
| `onday` | `--visit-confirmed` → `--visit-done` 的漸層一小段 | 那一天正在從已確認變成已完成 |
| `done` | `--visit-done`（墨綠） | 那幾筆已經完成了 |
| `no-show` | `--visit-no-show`（硃紅） | 要收回來的 |

**這是這一支唯一的「用顏色」**：ADR-0039 已經記著色相不夠用，所以這裡一個新色相
都不開，改成借既有的語意 —— 而且借得剛好，因為待辦的階段本來就對應來訪的狀態。
同一位客戶在待辦上是琥珀色的那一段，日曆上那一筆也正是琥珀色的。

畫法：段落標題左邊一條 3px 的直線 ＋ 一個小小的段號，**不要整段染色**
（整段染色會讓七段變成七片色塊，而那一頁最重要的顏色是「逾期紅」）。

### 版面

```
8月23日
今天有 12 件，其中 3 件逾期了

[逾期 3] [今天 5] [明天 2]      ← 照舊，這是分流不是流程

│① 問到時間
│   問這輪的時間        3   其中 2 位已經發出連結
│   客戶填好的時間      1   客戶自己填的，看過就收下
│② 壓表
│   壓表登記            8   這個月還有 8 位沒排
│③ 等客人回覆
│   跟客人確認時間      5   壓好了、還沒問過本人
│④ 來訪前一天
│   Examine             4   預約作業 → 查核 → 已報到
│   耀聖                4   右下角 → 未報到 → V
│⑤ 來訪當天
│   簽療程單            2   來了、單簽了就打勾，次數這時才扣
│⑥ 來訪之後
│   追蹤健檢報告        1   報告通常兩三週出來
│   約二返              2   報告拿到了，回去跟客人約
│⑦ 要收回來的
│   改時間／取消        1   要回頭取消舊登記

隨手記 …
```

- **0 件的那一段整段不畫**（含標題）。段裡的列本來就是 0 不畫。
- 段落順序**固定**，不隨數字重排。這一頁要教她的就是這個順序。
- `grouprow` 本身不重畫 —— 只是被放進段裡。`grouprow__dot` 那顆小圓點拿掉，
  改由段落那條線承擔顏色（一列一個點 ＋ 一段一條線是兩套視覺語言）。
- **「依客戶」那個看法不分段**，維持現在的樣子：那一頁問的是
  「這個人身上還有幾件事」，流程順序在那裡沒有意義。

### headline 講下一步

`headline()` 現在講「今天有 N 件，其中 M 件逾期了」。加一句更有用的：
**最前面那個非空的段**是什麼。例：`今天有 12 件・下一步是壓表（8 位）`。
逾期優先於流程 —— 有逾期就先講逾期。

## 不做

- **不新增任何色相**（ADR-0039）。
- **不做可收合的段落。** 七段裡通常只有三四段有東西，收合等於多一次點擊
  才看得到本來就看得到的東西。
- **不動三顆大數字。** 逾期／今天／明天是緊急度分流，跟流程是兩個軸，
  合在一起會兩個都講不清楚。
- 不把段落順序做成可設定的。

## 驗證

- `npm test`，新測試涵蓋 `stageOf()` 的每一種與認不得的那一種

- 瀏覽器：把某一段清空 → 整段（含標題）消失，其餘段的編號**不重新編**
  （編號講的是流程的第幾步，不是畫面上的第幾段）
- 深色模式下七段的線都看得見

- **`.grouprow--lead`（整列淡綠底）也拿掉了。** 原本只打算拿掉小圓點，
  但畫出來之後那片綠底跟段落線是兩套顏色在同一列上打架 ——
  「客戶填好的時間」是綠底、它的段落線是灰的，而「跟客人確認時間」是綠底、
  段落線是琥珀的。「哪一列比較重要」現在由**位置**回答：它排在第幾段。
- **段裡的順序要自己排，不能交給死線。** 「追蹤健檢報告」的死線是 21 天、
  「約二返」是拿到報告之後 7 天，照死線排會把鏈條的第二站排到第一站前面。
  所以 `FLOW` 是一個有序的陣列，段與段裡的順序是同一份資料。
- **「下一步」在 DOM 上算，不在資料上算。** 有三列是等資料回來才補進去的，
  產生 HTML 的那一刻還不知道它們有沒有東西。同理，空的段由 CSS 的 `:has()` 收掉 ——
  寫在 JS 裡的話補進來那一列就得重畫整塊，而那是 ADR-0038 剛拿掉的東西。
