## 這一輪最大的一個發現：委派監聽跨頁還活著

`ui/shell.js` 的 `renderShell()` 只建立一次 `#view`，**每一頁都畫在同一個元素上**。
而好幾頁把委派的 click 監聽掛在那個元素**本身**（一次接住兩百列比接兩百顆按鈕
便宜得多，ADR-0038 那一段就是這樣寫的）。監聽跟著元素走，所以：

1. 同一頁重畫一次就多一顆
2. **換頁不會收掉它們** —— 它們一路活到重新整理
3. 而且在別的頁面上照樣被觸發

第 3 點是真正的傷害。屬性名撞在一起的有四組：

| 屬性 | 在這一頁的意思 | 在那一頁的意思 |
|---|---|---|
| `data-month-step` | 客戶詳情：換月份 | 記一次：換月份並整頁重畫 |
| `data-kind` | 舊資料匯入：分類鈕（要讀 `index`） | 日曆：頂端的篩選丸（沒有 `index`） |
| `data-task` | 客戶詳情：勾一筆任務 | 待辦中心：勾選框 |
| `data-visit` | 客戶詳情：浮出讀取卡片 | 待辦中心：跳到來訪 |

issue 04 只是這一組裡最看得見的那一個。

**修法分兩層，第二層才是真的修好：**

1. `ui/shell.js` 換頁時把 `#view` 整個換成一個新節點（`cloneNode(false)`）。
   舊節點連同它身上的監聽一起被丟掉，**沒有任何人需要記得拆**。
   順帶修掉另一件事：`render()` 是 async 的，換頁時上一頁可能還在等資料，
   以前它回來之後會把新的那一頁蓋掉。
2. 同一頁重畫自己（`paint()` → `paint()`）換頁換不掉，所以四個畫面的委派改掛在
   每次重畫都會被換掉的容器上（`[data-availform]`、`[data-detailpage]`、
   `[data-entform]`、`[data-mergepage]`）。三個 AbortController 跟著拿掉。

`tests/layering.test.js` 多一支守衛：`/ui/views` 底下不可以把 `addEventListener`
掛在整頁的 `el` 上。

## 怎麼驗的

**用假的 Firestore 在 Chromium 裡把 app 真的跑一遍。** 假的那一份刻意模仿真實語意
（`where('x','==',null)` 對缺欄位的文件不成立、`orderBy(f)` 會把缺 `f` 的文件整個
排除、`writeBatch` 一次成功或一次失敗），時間固定在 2026-08-25。

| 層 | 做了什麼 | 結果 |
|---|---|---|
| 路由 | 45 條全部畫出來 | 零錯誤，沒有一頁停在「載入中」 |
| 第一層按鈕 | 348 顆逐顆點過（每顆之前先回到乾淨的那一頁） | 零錯誤 |
| 浮層裡的按鈕 | 打開 157 次浮層，點了裡面 276 顆 | 零錯誤 |
| 完整流程 | 見下 | 全過 |
| iPad 版型 | 1180px 再跑一次第二層 | 零錯誤 |
| 客戶那一頁 | `/form.html?t=…` 畫得出來、點得動 | 過 |

跑過的流程：壓表開一批 → 挑日子（含點紅格子與休假那天）→ 記一筆 →
跟客人確認時間（寫一句話 → 進隨手記；逐段退回 → 加進日曆 → 中央的卡片）→
勾掉追蹤健檢報告 → 約二返長出來 → 拿回來 → 約二返收回去 →
加購健檢選等級 → 換月份記一次 → 改一份跳出差異確認 →
切深色 → 重新整理仍然是深的 → 資料健檢列出同月兩份。

導覽的迴歸另外跑一輪：換頁捲回最上面、日曆的篩選丸不會被匯入那一頁接走、
返回鍵退回客戶詳情而不是離開這個人、返回鍵收掉卡片但底下那一頁留著、
對話框的返回等於取消。
