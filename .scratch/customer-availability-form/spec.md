# 客戶自己填這一輪的時間

她的流程第一步是「問客戶下個月哪幾天方便」。現在是她在 LINE 上一位一位問，
客戶回一段自由文字，她再轉述進 app 讓解析器去猜。

這一輪要做的是：**讓答案一出生就是結構化的**，解析器不必猜。

> 「之後我可能會希望用表單之類的形式，讓客戶自己填下個月的時間」
> —— 使用者，`.scratch/visit-lifecycle/spec.md` 第 7 節，當時列為「暫不做」

## 1. 為什麼不是 Google 表單

討論過三個版本，最後選自建。三個決定性的理由：

1. **客戶全是長輩。** Google 表單只給得起 31 個 checkbox 的清單，給不起一個
   點得動、看得懂的日曆。填答率是這件事唯一的成敗變數，而客戶端的體驗直接決定它。
2. **日期選項的維護。** 表單要嘛每個月手工重建 30 個選項，要嘛改成「1–31 號」
   而讓客戶看不到星期幾。自建的日曆自己長出來，什麼都不用維護。
3. **答案怎麼進 app。** Apps Script 推 Firestore 需要一把服務帳號金鑰
   （ADR-0010 拒絕過的東西）；app 去讀試算表則要多一組 Google OAuth scope。
   自建這條路上兩者都不存在。

代價是要開一個**未登入也能寫入**的洞，那是這整件事最貴也最危險的部分，
所以 rules 寫得比其他集合都緊（第 6 節）。

## 2. 客戶那一頁

網址：`/form.html?t=<token>`，一位客戶一個月一條，token 就是邀請的文件 id。

### 只問三件事，30 秒填完

順序刻意是**星期先於日期**：先答完「每個禮拜五不行」，日曆上那四五個禮拜五
就自動標掉，客戶少點四五下，而且**看到的決定變少了**。

| | 問什麼 | 存成 |
|---|---|---|
| ① | 固定哪個星期不行？ | `exclude_weekday`（可帶 `partOfDay`） |
| ② | 這個月哪幾天不行？ | `exclude_date` / `exclude_range` |
| ③ | 還有什麼要跟我說的嗎？（選填） | 原文，照抄 |

**刻意不問「哪幾天方便」**（不產生 `prefer`）。原因是語意陷阱：客戶勾「二四方便」
的意思是「這兩天最好」，不是「其他天不行」，但兩邊都很容易讀成後者。同一份資料
兩個人讀成不同意思，比少問一題糟。她自己記錄時仍然可以手動加 `prefer`。

### 一條規則貫穿整頁

> **點一下 = 那個時間整天不行。要改成半天，在下面那一列改。**

不做「點第二下變上午、第三下變下午」的三態循環：誤觸看不出來，而且點錯了要
再點三下才回得到原點 —— 長輩到第二下就會放棄。

被選起來的東西一律在底下**複述成一列一列的中文**：

```
您說不方便的日子
  9/18（四）    整天不行 ▾    ✕
  9/22–24       整天不行 ▾    ✕     ← 連續的自動併起來
```

那顆「整天不行 ▾」點開是三顆大按鈕（整天／只有上午／只有下午）。
絕大多數人不會碰到它，因為預設就是最常見的答案。

這張清單同時是**複述**：長輩看到自己講的話被寫成中文才會安心。
誤觸看得見（多一列）、取消一下就好（✕）。

### 不做拖拉

SPEC 第 8.0 節的「無拖拉」講的是「不靠拖拉就做不到的功能」，手勢當快捷是允許的
（ADR-0017、0020、0021），所以這是體驗判斷不是規則問題。不做的理由：

- 要讓手指在日曆上拖得動就得關掉那一區的原生捲動，長輩想捲頁時畫面不動，
  他會以為當掉了
- 長輩對「拉」沒把握，對「點」有把握，而且每一下都有回饋
- 出國八天點八下不痛，連續的日子在複述清單裡自動併成「9/22–24」，
  看到的結果跟拉出來的一模一樣

### 被星期擋掉的日子

日曆上畫成淡紅斜線，**不可點**。點下去只浮出一句「這是您說的每個禮拜五不行」
並附一顆「回去改」。

**不做「這一個禮拜五可以」的例外** —— `domain/availability.js` 沒有那種規則形狀，
硬做就是發明一個 domain 不認得的東西。

### 送出前一頁複述

大字，把①②③全部寫成人話讓他看一次，兩顆按鈕：`確定送出` / `回去改`。
長輩填表最大的恐懼是「我不知道自己按了什麼」，這一頁值一半的成本。

頁首另有一顆大按鈕 **「這個月都可以，沒問題」**，按了直接跳到這一頁。
沒有這顆，沒有限制的客戶會打開連結、不知道要做什麼、然後關掉。

### 送出之後

不重填（第 5 節）。同一條連結再打開一律顯示：

> 收到了，謝謝您 🙂
> （把他填的東西再顯示一次）
> 如果要修改，直接在 LINE 跟我說就好。

## 3. 她那一頁

### 拿連結

**不做「連結清單」那一頁。** 她要的不是一堆網址，是一則可以直接貼的訊息 ——
裸網址拿到手還是得自己打一句話。所以兩個入口都是同一則訊息：

- 待辦中心「問這輪的時間」點進去，每一列一顆「複製 LINE 訊息」，訊息裡含連結
- 客戶詳情最底下那一排的「LINE 訊息」，同一則

**連結在按下「產生連結」的那一刻才建立。** 她有二十幾位客戶但這一輪可能只問十二位，
先全部產生等於留下一堆沒發出去的邀請。已經產生過而且還沒被填的，重開那一頁直接顯示。

### 收回來

待辦中心多一列「**客戶填好的時間**」。點進去一位一位看：客戶名、月份、送出時間、
系統讀成的規則、客戶自己打的那段話。

**不直接生效**，她按「收下」才成為本輪可用性（ADR-0002：app 是記錄者不是判斷者）。
收下的同時給她一則回覆客戶的訊息 —— 那不只是禮貌，它是**最便宜的驗證**：
把系統讀到的東西複述回去，讀錯了客戶會當場說「不是啦我是說⋯⋯」。

## 4. 資料

```js
// formInvites/{token}          token = repo.newId() 產生的 20 字元亂數
{
  customerId, customerName,
  month,                 // 'YYYY-MM'，要問的那個月
  validFrom, validTo,    // 收下之後那份收集的有效期，預設整個月
  expiresAt,             // Timestamp。連結本身失效的時刻，rules 靠它擋
  sentAt,                // 'YYYY-MM-DD'，她產生連結那天
}

// formResponses/{token}        id 就是 token —— 一個 token 只有一份答案
{
  token, customerId, customerName, month,
  weekdays: [{ weekday: 0-6, partOfDay: 'am'|'pm'|null }],
  dates:    [{ date: 'YYYY-MM-DD', partOfDay: 'am'|'pm'|null }],
  freeText,              // 客戶自己打的，照抄
  submittedAt,           // Timestamp
  takenAt,               // null；她收下之後才有
}
```

### 收下之後長成什麼

`domain/availabilityForm.js` 的 `collectionFrom()` 把答案轉成一份收集：

- `rules` —— ①②直接轉，不經過解析器。連續三天以上併成 `exclude_range`
  （兩天併起來讀成「9/22 到 9/23」反而比兩列不清楚）
- `rawText` —— 第一行是把①②組回去的人話，第二行是客戶的自由文字**照抄**。
  SPEC 第 4.3 節的「原文永遠是最終依據」在這裡的等價物就是第二行
- `source: 'form'` —— 畫面上要看得出這一份是客戶自己填的

**產生的 rawText 餵回 `parseAvailability()` 要得到同一組規則**，這是一個有測試盯著的
不變量。理由：她之後在收集畫面按「用原文重新解析」時不可以得到不一樣的東西。
也因為這樣，轉出來的規則**不標 `manual`** —— 標了會在重新解析時被 `mergeRules()`
再加一次，變成兩份。

## 5. 暫時不重填

客戶送出一次就結束。填錯了的出路是**她重發一條新連結**，她那邊就是再點一次
「複製訊息」，一個動作。

這個決定同時讓 rules 變得極簡單：文件 id 就是 token，第二次送出是 `update`
而不是 `create`，而客戶沒有 `update` 權限 —— **不重填是被 rules 保證的，不是靠前端**。

## 6. 未登入的那個洞

`firestore.rules` 現在是預設全拒、白名單才進得來。這是第一次讓沒登入的人寫東西，
所以四道限制缺一不可：

1. **token 猜不到** —— Firestore 自動 id，20 字元、62 種字元，約 119 bits
2. **`get` 開、`list` 關** —— 兩個都用 `allow read` 會讓任何人一次列出全部邀請，
   而邀請上有客戶的名字。這是這一段最容易寫錯的地方
3. **建立時要有一份沒過期的邀請** —— rules 自己 `get()` 那份邀請來比對
   `customerId`、`month`、`expiresAt`，前端送什麼都繞不過
4. **只能建立，不能改也不能刪** —— 客戶改不了自己送出的東西，她也退不回去
   （要退就是重發一條）

客戶那一頁**讀不到任何既有資料**：邀請上只有名字與月份，沒有次數、沒有病史、
沒有來訪。連結被轉傳的最壞情況是別人看到「某人 9 月 18 號不行」。

## 7. 客戶那一頁是獨立入口，不是 hash route

`/form.html`，不是 `#/f/xxx`。理由與 consequences 見 ADR-0031。

## 8. 不在範圍內

- **重填**（第 5 節）
- **推播通知**。她打開 app 才看得到有人填了 —— 她本來就一天開十幾次待辦中心
- **讓客戶自己選時段**。這個 app 從頭到尾不是預約系統（SPEC 第 4.7 節），
  表單收集的是「限制」，不是「預約」
- **`prefer`（方便的星期）**（第 2 節）
- **表單裡出現剩餘次數、永久限制、來訪**。連結會被轉傳
