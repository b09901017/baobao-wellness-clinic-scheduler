# 試算表推送在路上時又寫一筆，那一筆永遠推不上去

Status: todo
來源：`../spec.md`
動工前先讀：`docs/adr/0013`（推，不是拉）、`data/sheetSync.js` 全檔

## 現在壞在哪

1. 存一筆（例如客戶甲確認）→ 安靜 10 秒後開始推整包
2. Apps Script 重畫二十幾張分頁要十幾秒 —— 這段時間裡又存了一筆（客戶乙確認）
3. 第一次推送回來成功 → **客戶乙那一筆不在試算表上，而且不會補推**，
   設定頁照樣顯示「上次推送成功」，要等她下一次再存任何東西才會補上

實跑（假的 Apps Script，第一次故意慢 15 秒回）：一共只收到 1 次推送，客戶乙那一格是 `○`（資料庫裡是已確認），
`localStorage` 的 `sheetSync.dirty` 是 `null`。

## 怎麼重現

用 node 的 `http` 開一個假的收件口（回 `Access-Control-Allow-Origin: *`、`{ ok: true }`，第一次延遲回應）→
`config/app` 的 `sheetSync` 填它的網址與密鑰 → 確認客戶甲 → 等假收件口收到第一包 → 確認客戶乙 →
等 12 秒 → 放行第一包 → 再等 20 秒 → 只收到 1 包。

`data/sheetSync.js` 沒有碰 DOM，單元測試可以把 `fetch`、`localStorage`、`setTimeout` 換掉直接測 `schedule()`／`push()`，
但它 import 了 `config.js` 那幾支（會拉 Firebase），要嘛拆出一支純的排程器，要嘛在 E2E 測。

## 為什麼

`data/sheetSync.js:134`：`inFlight ??= run()...` —— 第二次的計時器到了、發現有一份在路上，
就**直接拿那一份的結果**當作這一次的；而那一份是第二筆寫入之前打包的。它成功之後 `:179` 還把
「還有沒推的」標記清掉，所以下次開 app 也不會補。

## 做法（方向）

- 記一個「版本號」：每次 `schedule()` 加一；`run()` 開始打包時記下當時的號碼，
  成功之後**只有號碼沒變**才清 `DIRTY_KEY`
- 推送在路上時又來了新的寫入：這一份回來之後**再推一次**（不是把新的請求吞掉）
- `.gs` 那側有 `LockService`（`tryLock(30000)`），兩份不會同時寫，但這一側還是一次只送一份

## 判準

- 上面那個情境：假收件口收到**第 2 包**，裡面客戶乙是 `△`；兩包都成功後 `dirty` 才清掉
- 連續存十幾筆（沒有推送在路上）：照舊只推一次
- 推失敗：痕跡照舊留著（`lastError`），不會無限重推
