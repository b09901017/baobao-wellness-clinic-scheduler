# 客戶的時間（每月一份）

## 這件事是什麼

她每個月在 LINE 問客戶「下個月哪幾天不方便排」，回覆有截圖也有文字，寫法五花八門。這支 skill 把它變成一份
**她一眼看得懂**的試算表：一位一頁、一頁一個月曆，每一天一個顏色；客戶傳的原文整段放在名字底下，
那幾天的格子裡也寫上交代的重點（幾點後、優先下午）；身上有體內金屬的，名字旁邊一塊紅色。

**讀錯一位就是排錯一位**，所以三件事一定要做：讀之前先查這一位的脈絡、讀不準的問她、做完拿第二遍閱讀逐格核對。
她每回答一件就記進 `客戶記憶.json` —— 這支 skill 要**越用越懂每一位客戶**，同一件事不要問她兩次。

**版面已經定案**（2026-10-23 她改了五輪後說「這個版本我很喜歡，之後都照這樣做」）。版面全部寫死在 `build.py`，
你只要寫對 `讀法.json`，畫出來就是那一版。不要自己另畫一份、也不要「順手美化」—— 她每一輪的意見都已經在裡面了（見最後一節）。

## 四條鐵則

1. **有真名的東西只放 `.local/references/客戶時間/`**（截圖、文字、讀法、脈絡、記憶、試算表、預覽圖）。不發佈成 Artifact、不進 commit／PR。
   這支 skill 的檔案在公開的 repo 裡：**例子一律不寫名字**。新開資料夾走 `init.mjs`（它會真的跑 `git check-ignore`）。
2. **終端機只印數字與編號**（`history.mjs`、`verify.py` 都是這樣寫的）。讀 `.local` 的其他檔案過 `.local/references/redact.mjs`。
   **例外：問她問題時要寫名字** —— 她看不懂「#16、#7」是誰。問題照人分組、用名字。
3. **Firebase 只讀**。`history.mjs` 把 firebase-admin 每一個會寫的入口換成丟錯。她問「可以直接寫進 app 嗎」時，答案在後面一節。
4. **不猜**。兩種讀法拿不準 → 問她；名字對不到 app 剛好一位 → 問她；截圖上看不出是誰 → 問她。
   拿 app 的脈絡挑讀法可以，但問題裡要講出你為什麼傾向那一種。

## 資料夾

```
.local/references/客戶時間/
  README.md           給她看的（references/her-readme.md 的複本，init.mjs 放的）
  客戶記憶.json        每一位：她回答過的事（facts）＋每個月的原文與一句話（months）
  2026-11/            第一份，也是格式的範本 —— 不確定 讀法.json 怎麼寫時打開它看
    截圖/              她放的截圖（檔名多半是客戶名字）
    文字.txt           她貼的文字（一位一段，名字在第一行）
    客戶時間-2026-11.xlsx  ← 她看這一個
    過程/
      名單.json        這個月回覆的名字（照 app 上的寫法）
      客戶脈絡.json    history.mjs 讀 app 寫的（來訪、警示、以前的不能的時間）

```

## 流程

```bash
K=.claude/skills/customer-availability-sheet/scripts
M=.local/references/客戶時間/2026-12
```

### 0. 開資料夾（她說「幫我開 12 月的資料夾」時只做這一步）

`node $K/init.mjs 2026-12` → 告訴她截圖放 `截圖/`、文字貼 `文字.txt`，放好了跟你說。

### 1. 讀原文

- 讀 `文字.txt`（Read 整份）與每一張截圖（Read 看圖）。
- 截圖**先找她自己問的那一則**：問「不方便」還是「方便」，同一句「11/3（早上）」意思相反（見 `references/reading-lessons.md` 第一節）。
  截圖上的紅框是她標的重點，**紅框外面的後續訊息也要看**（有人隔天補一句「20 日亦不行」）。
- 一則訊息裡兩個名字 → 兩位；「○○姐妹」→ 兩位（另一位是誰問她，或看 `客戶記憶.json`）。
- 名字寫進 `過程/名單.json`（陣列）。**名字用她的叫法**（多半是兩個字，app 上是含姓的全名也沒關係 ——
  `history.mjs` 會找包含它的那一位）。頁名、`讀法.json` 的 `name`、`客戶記憶.json` 的 key 全部用同一個叫法，三邊才對得上。
  只有她**打錯字**（對不到任何一位）時才改成 app 上的那個字。

**哪些字算「原文」**（`raw` 就是頁面上那一塊，她要看的是客戶自己講的話，所以抄的範圍要對）：
- 文字檔：一段的第一行是她寫的名字，不抄；名字直接黏在訊息前面的（「王小明都可以排」）把名字拿掉。
  段跟段之間那一行「。」是她的分隔，不抄。其餘一字不改（錯字、全形斜線、「..」、emoji 都照抄）。
- 截圖：抄**客戶回這個問題的訊息**，以及之後**講到時間的**補充（「11月20日亦不行」）；同一個泡泡裡的招呼與道謝（「妳好」「麻煩妳了」「謝謝…晚安」）照抄。
  跟這件事無關的訊息（「我到了」「做完了先走了」、貼圖）不抄。
- 截圖的換行：泡泡跟泡泡之間一定換行；同一個泡泡裡，**寫滿泡泡寬度才斷的是自動折行**（接起來），**沒寫滿就斷的是她按的換行**（保留）。
  頁面上那一塊會自己折行，接錯了只是斷點不同，不會少字。

### 2. 查脈絡

- `node $K/history.mjs $M --project prod` → `過程/客戶脈絡.json`。終端機上看每一位**對到幾位**、有沒有「體內金屬」：
  對到的不是剛好 1 位 → 問她 app 上叫什麼（文字檔常打錯一個同音字），改好 `名單.json` 再跑一次。
  **這一步不能省**：`build.py` 的體內金屬標記就是讀這一份，沒跑就標不上去（它會講）。
- 讀 `客戶記憶.json`：每一位的 `facts`（她回答過的事）與上個月的 `months`。客戶寫「一樣～」時就是看這裡。
- 讀 `references/reading-lessons.md`：她定過的讀法。

### 3. 寫讀法、問她

照 2026-11 那一份寫 `過程/讀法.json`。形狀（名字換成假的）：

```json
{
  "month": "2026-12",
  "people": [
    { "id": "1", "name": "小明", "source": "文字.txt", "asked": "看不到",
      "raw": "12月星期五都可以！可以2～5點！", "summary": "排星期五",
      "rest": "notMentioned", "days": { "yes": ["週五"] }, "dayWords": { "週五": "2～5 點" } },
    { "id": "2a", "name": "小華", "source": "截圖/小華.jpg", "asked": "不方便",
      "raw": "每週一、四不行\n12/24 也不行，謝謝妳", "summary": "每週一、四不行；12/24 不行", "together": "跟小美一起來",
      "rest": "free", "days": { "no": ["週一", "週四", 24], "am": [9] } }
  ]
}
```

每一位：

| 欄位 | 寫什麼 |
|---|---|
| `id` | 編號（同一則訊息拆成兩位就 `6a`、`6b`） |
| `name` | 她的叫法，跟 `名單.json` 一字不差（體內金屬靠它去 `客戶脈絡.json` 對） |
| `source`、`asked` | 從哪裡來（`文字.txt`、`截圖/xxx.jpg`）；她問的是 `不方便`、`方便`，文字檔看不到問法就寫 `看不到` |
| `raw` | **客戶的原文，一字不改**（範圍照第 1 步「哪些字算原文」），換行用 `\n`。兩位同一則訊息時兩位都放**完整**那一則（不是「同上」）。原樣畫在「客戶交代（原文）」那一塊 |
| `memo` | 給自己看的註記，不上頁面（例：文字檔把名字打錯了、第二行是隔天補的）（選填） |
| `summary` | 名字底下一句話，短 |
| `together` | 「跟 X 一起來」「姊妹：X」（選填） |
| `reminders` | 你的提醒，接在原文後面、字小一號（例：這一位你問的是方便的日期；「眼前知」＝目前知道的）（選填） |
| `rest` | 沒寫到的日子：`free`（都可以 → 綠色）或 `notMentioned`（她只給了可以的日子 → 灰色「沒提到」） |
| `days` | `no`／`am`／`pm`／`partial`／`yes`／`unsure`，每一種是一串：`3`、`"9-13"`、`"週一"`…`"週日"`、`"週末"`、`"整個月"`；同一天兩種時不行贏 |
| `dayWords` | 格子裡的字，把交代的重點寫進那幾天：`{"12": "早上可排復能", "週五": "2～5 點", "10-30": "優先"}`（`partial` 一定要有）。`"週五"`、`"9-12"` 這種一次寫好幾天的，只會寫到其中有顏色、又不是「不行」的那幾天；寫單一天（`"12"`）時那一天要有顏色而且不是不行，不然 `build.py` 會停下來講 |
| `pending` | 還沒確定的那一句（她回答之後拿掉） |

讀不準的**照人分組問她**，用名字，每一題寫「我現在的畫法」與理由（脈絡怎麼支持）。可以先做一版試算表給她看再問 ——
她是看著表回答最快。

### 4. 第二遍閱讀（核對）

重新讀一次原文、`客戶記憶.json` 的 facts 與她這次的回答，直接把每一位每一種的日子**列成數字**寫進 `過程/核對.json`
（格式寫在 `verify.py` 檔頭；`am`／`pm`／`partial` 全部寫進 `partial`）。這一份是拿來抓第一遍讀錯的 ——
從讀法.json 抄過來就什麼都抓不到。

自己剛寫完讀法.json 再寫這一份，其實不算獨立（腦子裡還是第一遍的讀法）。**最好交給一個 subagent**：
只給它原文的位置、`客戶記憶.json`、`references/reading-lessons.md`、她這次的回答與 `verify.py` 檔頭的格式，**不給讀法.json**，
叫它寫 核對.json、不印名字。一個就好 —— 她不喜歡一次開很多個 subagent（額度燒很快）。

### 5. 做表、核對、自己看一眼

```bash
python $K/build.py $M     # → 客戶時間-YYYY-MM.xlsx（並講標了幾位體內金屬）
python $K/verify.py $M    # 「體內金屬：標了 a 位，app 上有 a 位」＋「N 頁，比了 X 格，對不上 0 格」才算數
python $K/preview.py $M   # → 過程/預覽/*.png，用 Read 看（第一頁、原文最長的、紅色最多的；也可以指定頁碼）
```

`verify.py` 也查：星期對不對得上真的日曆、紅色格子寫的是不是「不行」、灰色格子有沒有多寫字、體內金屬標得跟 app 一不一樣。
不是 0 就回去看是哪一遍讀錯 —— **不要為了變綠去改核對.json**。這台沒有 Excel 與 LibreOffice，`preview.py` 是近似的畫法。

### 6. 交付、記住

- 回她：檔案連結、這次幾位、標了幾位體內金屬（用名字）、核對結果一句、還沒確定的照人列（用名字）。
- 她回答之後：改 `讀法.json`（拿掉 `pending`）與 `核對.json`、重跑第 5 步，再**把她的回答寫進 `客戶記憶.json`**：
  某一位自己的習慣進那一位的 `facts`（`{text, since, from}`），每個月的原文與一句話進 `months`。
  **對所有客戶都成立的讀法**寫進 `references/reading-lessons.md` 那張表 —— 不寫名字。
- 她對版面有新的意見 → 改 `build.py`（`verify.py` 的顏色表要一起改），再把那一條補進最後一節。

## 可以直接寫進 app（Firebase）嗎

**現在不建議**。app 的「不能的時間」（`customers/{id}/availability`，一人一個月一份，ADR-0053）只存得下
「某天／某星期幾／一段日子不行（可選上午或下午）」與「偏好」，**存不下「不一定」「幾點以後」「沒提到」**；原文會留著，但壓表算不到。
她要的三級＋時間備註記在 `.scratch/availability-certainty/issues/01-three-levels-and-time-notes.md`，等 app 那一輪做完再接。
真的要寫的話：一律走正式站的四步（她先匯出備份 → 試跑只數不動 → 她點頭才寫 → 整份讀回來比對，CLAUDE.md「上線」那一節），
不要用這支 skill 的腳本寫（它們故意只讀）。

## 卡住的時候

| 症狀 | 原因 | 怎麼辦 |
|---|---|---|
| `history.mjs` 權限錯誤／沒有憑證 | 她的 gcloud ADC 失效 | 照 `month-end-reconciliation/SKILL.md`「卡住的時候」第一列（服務帳號金鑰，存成 `.local/references/*-sa.json`）。不要叫她重新 `gcloud auth`（防毒擋） |
| 某一位「對到 0 位」或好幾位 | 打錯字、或 app 上的名字長一點 | 問她 app 上叫什麼；`name` 與 `名單.json` 寫 app 上的、`memo` 註明 |
| `build.py` 講「沒有客戶脈絡」或「對不到 app 的幾位沒查」 | 沒跑第 2 步、或名字對不上 | 跑 `history.mjs`／把名字改成 app 上的 —— 體內金屬沒查過的頁不可以交出去 |
| `build.py` 丟「認不得的日子寫法」 | `days` 寫了它不認的字 | 只收 數字、`"9-13"`、`"週一"`…`"週日"`、`"週末"`、`"整個月"` |
| `verify.py` 對不上 | 兩遍閱讀不一樣 | 回原文看哪一遍對 |
| `preview.py` 截不了圖 | 沒有 playwright 的 Chromium | `npx playwright install chromium`（repo 的 E2E 也要它） |

## 她定案的版面（2026-10-23，五輪改出來的）

`build.py` 已經全部照這個畫。列在這裡是讓你知道**每一樣為什麼是這樣**，她下次提新意見時不要退回舊的：

| 她說過的話 | 所以現在是 |
|---|---|
| 一張大表（每人一列、每天一欄）「太醜了，資訊太多了，好躁，要有呼吸感」 | 一人一頁、一頁一個月曆（星期一開頭，同 app），格子之間留縫，資訊只留名字、一句話、原文、月曆、圖例 |
| 「客戶補充的特殊需求…可以標得更明顯」 | 名字底下一塊藍色、左邊一條深藍；交代的重點也寫進那幾天的格子 |
| 「客戶交代那邊就直接呈現所有原文就好」 | 那一塊叫「客戶交代（原文）」，`raw` 一字不改、一行一行畫；你的話只放 `reminders` |
| 「有體內金屬的，也要幫我紅色標上去」 | 名字右邊一塊紅底白字「⚠ 體內金屬」，資料來自正式站的 `customer.flags`（`RED_FLAGS`） |
| 「可以的時間那就是綠色，像是整個月都可以的應該是綠色」 | `rest: free` 的日子也是綠色「可以」 |
| 「沒提到（先排綠色）會讓人誤會沒提到的是綠色的」 | 圖例：綠色「可以，優先排」、灰色「沒提到」 |
| 「背景好像有點白…有點淺淡，會看不清楚」（但「整體配色很好看」） | 紙色底（`PAPER`），五種顏色各加深一階，字加粗加大；色相不換 |
| 問題用編號「我不知道是誰」 | 問題照人分組、寫名字 |

顏色（`LOOK`）：不行 淡紅、只有部分時間可以 淡橘、可以 淡綠、不一定 淡黃、沒提到 暖灰。要多一種先問她 —— 加一種就多一個要記的顏色。
