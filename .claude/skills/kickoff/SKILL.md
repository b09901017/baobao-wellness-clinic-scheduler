# 開一輪大改動

這支 skill 的存在理由只有一個：**把「決策」和「幹活」拆開。**

一次跑到底不會避開 context 累積，它保證累積 —— context 變長時會被自動摘要，
而最先被壓掉的是細節與原話。這個 repo 的整個文化建立在保住她那幾句話上
（打開任何一支 domain 檔案，檔頭都是「她的原話是…」）。**對抗壓縮的辦法不是
少講幾輪，是把知識寫到 context 以外的地方** —— 那個地方是 `.scratch/<slug>/`。

她自己的話（2026-10-08）：

> 我怕這個session的上下文太多會讓你的實作被上下文汙染，也希望可以用不同effort的session去完成(像是matt-code-review我可能就希望用xhigh單獨完成…)，所以你可以自己分任務。並且必須在每次任務完成後後給我一段給新session的開場讓他繼續接手

所以流程是四段：**談 → 開 issue 與分段 → 一段一段做 → 審查與合併**。
第一段結束時一定要停下來；第二段結束時也停（把下一段的開場交給她），除非整輪小到當下就做得完。

## 這支 skill 不重複 CLAUDE.md

`CLAUDE.md` 已經規定的東西這裡一個字都不再寫：要先讀哪幾份文件、PR 的基底是
`develop`、issue 的格式、測試怎麼跑、改完 domain 要回頭補 SPEC 與 ADR、
`public/` 動了要顧 `sw.js`。**同一件事寫兩遍會讓模型猜「講兩遍的是不是比較重要」。**

---

## 第一段：先回答，不要動 code

**一行程式都不要改。** 這一段的產出是對話裡的答案，不是檔案。

1. **分出兩種需求。** 使用者標了「這條我覺得邏輯怪怪的」的那幾條，跟「這是
   bug」是**兩種工作**：
   - bug → 找到哪一行、修
   - 「邏輯怪怪的」→ **先翻 `docs/adr/` 問「當初為什麼這樣決定」**，然後可能
     回答「那個決定還成立，是畫面沒講清楚」

   猜錯的成本不對稱：把「邏輯怪怪的」當成 bug 修，等於重構一個本來沒壞的東西。

2. **回答她問的架構疑問**，而且要從 ADR 與 commit 歷史找證據，不要憑讀 code
   推測當初的意圖。她問「我當時是怎麼想的」的時候要的是**那份紀錄**，不是你的
   重新推導。找不到就說找不到 —— 編一個理由比說不知道糟得多。
   她給過的參考資料（`.local/references/`）也算紀錄：她問「我不是給過你了嗎」
   的時候，先去翻、再回答，漏看了就直說漏看了。

3. **清查連動。** `CLAUDE.md` 的「容易漏掉的連動」那張表是起點不是終點：
   照她要動的東西，把**實際依賴它的模組全部列出來**（`grep`／graphify 都用），
   一支一支說「這裡會怎麼受影響」。漏一個的症狀通常是「畫面看起來對、資料是錯的」。
   `docs/agents/lessons.md` 是之前一再犯的坑，拿它的每一句自問掃一遍。

4. **提出重構策略與風險**，包含「不改」這個選項。既有決定推得翻要說清楚翻的是
   哪一支 ADR，而**不要改掉舊的那一支**（補一支新的）。
   她要的是「想清楚、對她順手」的答案，不是照字面做 —— 她常說「幫我動動腦子想想怎樣比較合理」。
   想到她沒講、但照她的用法一定會撞到的情境，提出來。

5. **停下來。** 把答案與策略給她，等她回話。給她看的東西用表格、白話、
   一題附一個建議（她可以只回「照建議」）—— 一大片文字她會看不下去。

### 第一段結束時要問的

問完就停，不要自己回答：

- 要她拍板的幾題（每一題附你的建議）
- 這幾條裡**哪幾條必須一起出貨**？（分兩個 PR 上 staging 的話中間那個狀態會不會怪）
- 策略同意嗎？不同意的是哪一段？
- issue 要她逐支看過，還是照她平常的做法：**subagent 過目後直接分段**？

## 第二段：開 issue、過目、分段，再停一次

取得共識之後才開檔案。格式與慣例見 `docs/agents/issue-tracker.md`。
**先 `git fetch`、從最新的 `origin/develop` 開這一輪的分支**（第三段那一節講為什麼），
`.scratch/` 跟著這條分支走。

- `.scratch/<feature-slug>/spec.md` 放這一輪的全貌、她的原話、第一段談定的策略與她選的答案
- `.scratch/<feature-slug>/issues/NN-<slug>.md` 一支一個可以獨立出貨的東西
- `.scratch/<feature-slug>/HANDOFF.md` 放分段、每一段的開場、進度、中途發現的事

**每一支 issue 一定要有的三塊**（照這個 repo 既有的寫）：

| 那一塊 | 放什麼 |
|---|---|
| 她要的 | **原話，逐字貼上，不要整理。** 「我甚至不知道為甚麼中間要多一個來訪的介質」比「請重構 Visit-Slot 關係」有用十倍 |
| 為什麼會這樣 | 現在那一行在哪、它為什麼長這樣。查到的 ADR 編號寫進去 |
| 判準 | 怎麼知道做對了。**「這一行會不會讓 X 被算成 Y」那種問句**，不是「要能正常運作」 |

還要有 `Status:` 一行（`todo` / `done`）與「動工前先讀」一行（檔案、函式、ADR、
`CLAUDE.md` 的哪幾列、`lessons.md` 的哪幾條）。**依賴要標出來**：`Blocked by: 04` 那種。
順序錯了的代價是後面那幾支建築在會被改掉的東西上。

### 過目

她不逐支看的時候，開一個**唯讀**的 subagent 對著程式碼過目：檔名、函式、行號、
現在的行為描述對不對；設計做不做得出來、會不會算錯；漏掉的連動；判準能不能寫成測試；
依賴與分段；公開 repo 不能有真名。**這個環境的 subagent 寫不了 `.md`**，所以叫它回報、
主控代改。主控**自己再對一次最重的幾條**再改 —— 2026-10-08 那次過目抓到三支 issue
寫了已經不存在的 bug、或指定了撈不到資料的查詢，而 subagent 自己也會看錯。

她要逐支看的時候，清單給她看過再動工 —— 她看一份清單要三分鐘，
看一個三千行的 PR 要一小時而且只能整包信或整包不信。

### 分段

**不要為了分段而分段。** 整輪小到這個 session 剩下的力氣就做得完（幾支文案、
一兩支不碰 domain 的修正），直接做、直接走到第四段。分段是為了兩件事：
不讓上一段的 context 污染下一段的實作、讓她替每一段挑 effort。

要分的時候，照**下一段需不需要繼承「我剛剛想過但沒寫下來」的東西**來切：
需要的就寫進 issue 或 HANDOFF，然後切。常見的切法：

| 這一段在做 | 建議 effort |
|---|---|
| 動 domain 規則、狀態機、次數、跨模組資料形狀 | xhigh（或 high，看有幾條會算錯次數的路） |
| 畫面、接線、存檔迴圈、確認框的句子 | high |
| 文件、ADR、部署、跑測試、開 PR | medium |
| `/matt-code-review` 那一段 | xhigh，**單獨一段** |

**每一段的開場**寫進 `HANDOFF.md`，第二段結束時把第一段實作的開場貼在回覆裡
（程式碼區塊，她直接複製到新 session），並寫建議的 effort。開場要自己站得住 ——
新的 session 什麼都不記得：

- 這一輪在做什麼（一句）、分支名、上一段做到哪
- 先讀：`HANDOFF.md`、`spec.md`、這一段那幾支 issue、`docs/agents/lessons.md`、
  `CLAUDE.md` 跟這一段有關的那幾列
- 這一段做哪幾支、**不做**哪幾支
- 提醒：動手前用 `grep`／graphify 找每一個要改的函式的所有呼叫端與畫面上的字；
  中途發現她沒發現的關聯問題或類似的問題，**先記進 HANDOFF 的「中途發現」、繼續做別的**
- 做完要交什麼：每支一個 commit、`Status: done`、`npm run verify`、
  HANDOFF 的進度、把「中途發現」**一次列給她問要不要修**、下一段的開場與 effort

然後**停下來**，把開場交給她。

## 第三段：一段一段做

### 動工前先 `git fetch`，在**最新的** `develop` 上

**一支 issue 常常是別的對話在做**（那正是這支 skill 想要的形狀），而它們看不見
彼此。從舊的點開分支，寫的時候一路順，合回去才發現撞在同一個共用檔案上 ——
而那時候要在解衝突的當下判斷「留誰的」，那是一天裡最容易判斷錯的時刻。

2026-09-09 就發生了一次：平行化那支從 `673f95f` 開，而同一天稍早合進 develop
的 E2E 分級也動了 `tests-e2e/fixtures/app.js`，兩邊改的都是 `settled()`。

這一輪的分支已經開了的話，接手的那一段先 `git fetch`，develop 往前走了就 **rebase，不要重做**。
幾個 commit 的 rebase 是十分鐘的事，而重做會丟掉那個對話已經建立的理解。

一支 issue 一個 commit。**每一支都走完整條路再開始下一支**：

1. 紅燈：先寫一支重現得出來的失敗測試，跑過確認它真的紅（`CLAUDE.md` 有這條）
2. 修到綠
3. `npm run verify`
4. commit，把那支 issue 的 `Status:` 改成 `done`，在 issue 底下寫「做完時留下的」
   （下一段與審查要知道你實際做成什麼樣子，不是 issue 原本猜的樣子）

### 為什麼是一支一個 commit

她可以在任何一支之後說「停，這個方向不對」，而已經做完的那幾支不用回頭。
一個包含八支 issue 的巨大 commit 沒有這個性質。

### 中途發現的事

做的時候常會看到她沒發現的關聯問題，或同一個形狀的另一個 bug。**不要當場岔出去修**
—— 那會讓這一支的 commit 混進別的東西，也會讓她來不及判斷要不要。記進 HANDOFF 的
「中途發現」（哪裡、什麼情境會錯、你的建議），繼續做這一段的。**一段結束時一次列給她**，
問要不要修；她說修的，修之前再 `grep` 一次會不會牽連別的地方，照一支 issue 的規矩做。

### 一段結束時

更新 HANDOFF 的進度 → 列中途發現、問要不要修 → 把下一段的開場（附 effort）貼給她 → 停。

## 第四段：審查、PR、合進 develop

1. **`/matt-code-review`** 單獨一段（她想用 xhigh），審這一輪的全部改動；照建議修，
   提過沒改的寫理由進 HANDOFF。審查兩個 subagent 吃很多用量 —— 大的一輪不要
   做完實作接著跑，留給新的一段
2. **手動測試清單**：條列她可以**照順序點**的路
3. PR 開向 `develop`（`CLAUDE.md` 的「上線」那節）。推之前看一眼 commit 訊息與 PR 內文：
   公開 repo，一個真名都不帶
4. CI 全綠之後**合進 develop** —— 她要的是一路做到合進去（2026-10-15：「最後要幫我開pr以及合併進develop」）。
   合完 staging 會自動部署；拍照的 Function 不歸 CI，要部署的照 `docs/STAGING.md`。
   **進 `main` 不在這一輪**，那要她另外說

手動測試清單的兩個常見寫壞方式：

- **寫成「我做了什麼」的複述。** 她要的是「你可以怎麼點」——
  `日曆 → 點 9/14 那格 → 點客戶A 那一列 → 按鉛筆`，不是「修好了單段編輯」
- **照自己的意圖寫，沒有真的走過。** 同一件事在兩個入口的選擇器常常不一樣
  （壓表的品項丸子是 `[data-ivproduct]`、來訪編輯器是 `[data-chip="s0-iv"]`），
  沒走過的清單會叫她去點一個不存在的東西

## 這一輪結束前

- 每一支 issue 的 `Status:` 都是 `done`，HANDOFF 寫了「已合進 develop（commit）」
- 推翻或新增的連動關係已經回去補進 `CLAUDE.md` 的那張表
  —— **不補的話那張表的價值會隨每一輪重構衰減**，而下一輪她又得在提示詞裡
  重新要求你去釐清它本來就該擋住的事
- 既有決定被推翻的話補了新的 ADR，舊的那一支一個字都沒改
- 踩到 `lessons.md` 沒寫過的新坑，照它的格式補一條
