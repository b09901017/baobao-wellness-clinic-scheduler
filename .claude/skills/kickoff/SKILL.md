# 一輪改動：談 → 開 issue → 做 → 審查與合併

這支 skill 把「決策」和「幹活」拆開。一次跑到底，context 會越來越長，被自動摘要時最先掉的是細節和使用者的原話；
所以知識寫到 context 以外的地方（`.scratch/<slug>/`），大的一輪分成幾個 session，每個 session 只拿到它要的。

**主控**＝跑這支 skill、開 issue 的那個 session。**段**＝主控開出去、做其中幾支 issue 的 session。

## 整輪都適用的規矩

skill 只在叫的時候讀一次，下面這幾條要一直記著，每一段的開場也都要帶到。

- **issue 不給使用者看**：subagent 過目、主控再對最重的幾條，然後直接做。使用者說要看才給看。
- **只問真的要使用者想的**：一次一題、白話、附建議，使用者可以只回「照建議」。能自己查到、自己判斷的不問。
- **改一個已經存在的函式、型別或畫面上的字之前**，照 `ripple-check` 找出它所有的呼叫端、波及範圍與畫面上出現的地方；修完 bug 照它找同一個形狀的地方。
- **中途發現的事不岔出去修**：沒人提過的關聯問題、同一個形狀的類似問題，記進 HANDOFF 的「中途發現」（哪裡、什麼情境會錯、建議），繼續做原本的。
  段末一次問。使用者說要修的，修之前再照 `ripple-check` 查一次牽連，照一支 issue 的規矩做（commit、`Status`、判準）。
- **同時最多兩個 subagent**：開太多會在幾分鐘內燒光額度。
- **專案限定的事看專案的 `CLAUDE.md`**：基底分支、驗證指令、合併規定、推之前要掃什麼、手動驗收在哪個環境。這裡不重寫，
  同一件事寫兩處，模型會猜寫兩遍的是不是比較重要，兩處不一致時還會隨便挑一條。

## 兩條路

| 現在的狀況 | 走哪條 |
|---|---|
| 專案初期、決策還沒定、在談東西該怎麼設計 | `/grill-with-docs`：Skill 叫 `grilling` 與 `domain-modeling`，邊談邊寫詞彙表與 ADR |
| 地基打好、一輪一輪加功能或改規則 | 這支 |
| 一個 bug、一個 UI 微調、文案 | 都不用，直接做 |

談到一半發現其實是「決策還沒定」，就換到 `grill-with-docs`，談定了再回來開 issue。

## 第一段：談，不動 code

這一段的產出是對話裡的答案，一行程式都不改。

1. **分出 bug 與「邏輯怪怪的」**。bug → 找到哪一行。「怪怪的」→ 先翻記決定的文件（plan、ADR）和 commit，
   問「當初為什麼這樣決定」；答案可能是「決定還成立，是畫面沒講清楚」。
2. **設計疑問從紀錄找證據**，不憑讀 code 猜當初的意圖。使用者給過的參考資料也算紀錄（使用者問「我不是給過你了嗎」時，先去翻；漏看了就直說）。
   找不到就說找不到 —— 編一個理由比說不知道糟得多。
3. **清查連動**：把實際依賴要改的東西的模組全部列出來（照 `ripple-check`：graphify 找相關的文件與決定、CodeGraph 找呼叫端與波及範圍），一支一支說會怎麼受影響；
   `docs/agents/lessons.md` 的每一句自問掃一遍。
4. **提策略與風險，包含「不改」**。推翻既有決定要說推翻哪一條。想清楚怎樣對使用者比較順手，不是照字面做；
   使用者沒講、但照使用者的用法一定會撞到的情境，提出來。
5. **有要使用者決定的才停**：照「只問真的要使用者想的」問，順便問哪幾條必須一起出貨。沒有要決定的就直接往下。

---

## 第二段：開 issue、過目、分段

先 `git fetch`，從基底分支（專案 `CLAUDE.md` 有寫照它，沒寫就是 `main`）最新的那一點開這一輪的分支。
平行的對話看不見彼此，從舊的基底開，最後會撞在共用的檔案上。

檔案格式照 `docs/agents/issue-tracker.md`：

- `.scratch/<slug>/spec.md`：這一輪的全貌、使用者的原話、談定的策略與使用者選的答案
- `.scratch/<slug>/issues/NN-<slug>.md`：一支一個可以獨立出貨的東西。切法照 `.claude/skills/to-tickets/SKILL.md` 第 3 步
  （tracer bullet、`Blocked by:`）；它第 4 步「給使用者逐支確認」跳過，改成下面的過目
- `.scratch/<slug>/HANDOFF.md`：分段表（段、issue、effort、狀態）、每一段共同的規矩、過目抓到的、中途發現（分段記）、
  要使用者決定的、使用者已經決定的、每一段的開場

每一支 issue 都要有：

| 那一塊 | 放什麼 |
|---|---|
| 使用者要的 | **原話，逐字貼上**，不整理。原話比「請重構 X 與 Y 的關係」有用得多 |
| 為什麼會這樣 | 現在那一行在哪、為什麼長這樣、相關的決定 |
| 判準 | 寫成「這一行會不會讓 X 被算成 Y」的問句，不是「要能正常運作」 |

還有 `Status:`（`todo`／`done`）、「動工前先讀」、`Blocked by:`。順序錯了，後面幾支會蓋在會被改掉的東西上。

### 過目

開一個**唯讀**的 subagent 對著程式碼過目：檔名、函式、現在的行為描述對不對；設計做不做得出來、會不會算錯；
漏掉的連動；判準能不能寫成測試；依賴與分段；公開 repo 不能有真名或帳號資料。
叫它**回報、不要改檔**，主控改：一個人改才不會兩邊各改一半。subagent 也會看錯，主控**自己再對一次最重的幾條**才改，
改了什麼記進 HANDOFF 的「過目抓到的」。

使用者說要逐支看的時候，先給清單再動工：看清單三分鐘，看一個幾千行的 PR 要一小時，而且只能整包信或整包不信。

### 分段

小到這個 session 做得完就直接做，不分段。要分的時候照「下一段需不需要我剛想過、但沒寫下來的東西」來切：
需要的寫進 issue 或 HANDOFF，然後切。

| 這一段在做 | 建議 effort |
|---|---|
| 資料模型、金流規則、跨模組資料形狀 | xhigh |
| 畫面、接線、互動 | high |
| 文件、部署、跑測試、開 PR | medium |
| `/matt-code-review` | xhigh，**單獨一段**（它開兩個 subagent，很吃額度，大的一輪不要接在實作後面跑） |

### 每一段的開場

寫進 `HANDOFF.md`。新的 session 只拿到開場，什麼都不記得，所以開場要讓它**不用問任何問題就能開工**：

1. 這一輪在做什麼（一句）、分支、上一段做到哪（commit）
2. 這一段做哪幾支、照什麼順序、**不做**哪幾支
3. 先讀：具體到 HANDOFF 的哪幾節、哪幾支 issue 的「做完時留下的」、哪幾份決定，加上 `CLAUDE.md`、`docs/agents/lessons.md`
4. 「整輪都適用的規矩」裡的 `ripple-check`（改前查牽連、修完找同類）、中途發現、使用者說修的再查牽連、subagent 上限
5. 這一段要先一次問使用者的題目（有才寫）；審查段另寫「要特別看的」：「這一行會不會讓 X」的問句，加上要查牽連的符號與要 grep 的字串
6. 「主控會開下一段：不要自己開 session，也不要存 limit-guard 的開場 JSON」（理由見第三段）
7. 做完要交：每支一個 commit、`Status: done`、issue 底下「做完時留下的」、驗證指令通過、更新 HANDOFF（狀態、中途發現、要使用者決定的）、
   下一段的開場與 effort 寫進 HANDOFF；最後回覆簡短說做了什麼、卡在哪

## 第三段：一段一段做

### 主控開段

主控用 `mcp__ccd_session__start_session` 開第一段：`initiation: "user_asked"`（使用者叫你跑這一輪，就是叫你開）、
`context: "fresh"`、`prompt` 放那一段的開場全文、`background` 放 spec 的一段摘要、`effort` 放這一段建議的。
段是一段接一段、同一條分支，一次只有一段在寫，所以共用這個 checkout（`use_worktree: false`）。

一段結束，app 會通知主控。主控：

1. **自己看 commit 與 HANDOFF**，確認真的做了 —— 段的回報不是證據。
2. 段末的問題：**擋住下一段的**，先問使用者再開下一段；**不擋的**留在 HANDOFF「要使用者決定的」，下一段跑的時候一題一題問。
   使用者的答案寫進 HANDOFF，下一段的開場用得到的也寫進開場。
3. 照 HANDOFF 裡的開場開下一段。

主控自己少讀 code：主控的 context 要撐完整輪。

**段自己不開下一段**：從 session 開出來的 session，app 不讓它再開；兩邊都開還會變成兩個 session 做同一段。

**開不了的時候**（沒有這個工具，例如在終端機或雲端；app 拒絕；使用者說要自己開）：把開場用程式碼區塊貼給使用者複製。

**跟 limit-guard 不重複**：有載入 mods 的地方，limit-guard 會叫 Claude 把開場另存成 `~/.claude/mods-data/handoffs/*.json`，
使用者下一次開新對話時自動放進輸入框。**已經用 `start_session` 開了的段不存這份**，否則使用者下一次開新對話，同一段又會被帶進來。
只有兩種情況照 limit-guard 存：開不了、改成給使用者貼的時候；額度快用完、中途收尾要接著做同一段的時候。
專案另有規定（例如某個時期不能存）照專案。

### 段裡每一支 issue

動工前先 `git fetch`；這一輪的分支落後基底就 rebase，不重做。一支一個 commit，走完一支再開始下一支：

1. 紅燈：先寫一支重現得出來的失敗測試，跑過確認它真的紅（文件、研究那種沒有程式的 issue，用判準逐條自查代替）
2. 修到綠
3. 跑專案的驗證指令
4. commit，`Status:` 改 `done`，issue 底下寫「做完時留下的」（實際做成什麼樣子）

一支一個 commit，使用者才能在任何一支之後說「停，方向不對」，做完的不用回頭。

改的是 `~/.claude/mods`（commit 進客廳）時例外：客廳的自動同步會在每個對話開始／結束時，把改到一半的檔先備份成「自動同步」commit，
所以客廳那邊不要求一支一個 commit，**最後一個 commit 的狀態完整**（測試全過、跟 `~/.claude/mods` 逐檔相同）就算數。

## 第四段：審查、PR、合併

1. **`/matt-code-review`** 單獨一段（Skill 叫 `matt-code-review`），審這一輪全部的改動。照建議修（每條先紅燈），沒改的寫理由進 HANDOFF。
2. **手動驗收清單**：條列使用者可以**照順序點**的路，而且自己真的走過一次。
   常見的兩種寫壞法：抽象（「修好了記帳」，要寫「首頁 → 點 + → 輸入 120 → 選錢包 → 存」）；照意圖寫、沒有走過。
3. **開 PR**（內文用 `pr` skill）。推之前看一眼 commit 訊息與 PR 內文：沒有人會幫你掃，公開 repo 不能帶真名、帳號、email、金鑰。
4. **合併照專案 `CLAUDE.md` 的合併規定**。專案沒寫：CI 綠了問使用者一次，答案寫進專案的 `CLAUDE.md`，之後照它。

## 這一輪結束前

- 每一支 issue 都是 `done`，HANDOFF 寫了合進哪個 commit
- 推翻了使用者的決定，就更新專案記決定的文件，只寫使用者確認過的
- 新的坑照 `docs/agents/lessons.md` 的格式補一條
- 新發現的連動寫在**離那段程式最近的地方**：子目錄的 `CLAUDE.md`、有 `paths:` 的 `.claude/rules/`、ADR、lessons。
  不往根目錄 `CLAUDE.md` 加表格 —— 根目錄的每一行每次對話都會載入，只加不減會長到沒人遵守（要整理時用 `claude-md` skill）
