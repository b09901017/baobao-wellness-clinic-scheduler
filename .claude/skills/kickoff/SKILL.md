# 開一輪大改動

這支 skill 的存在理由只有一個：**把「決策」和「幹活」拆開。**

一次跑到底不會避開 context 累積，它保證累積 —— context 變長時會被自動摘要，
而最先被壓掉的是細節與原話。這個 repo 的整個文化建立在保住她那幾句話上
（打開任何一支 domain 檔案，檔頭都是「她的原話是…」）。**對抗壓縮的辦法不是
少講幾輪，是把知識寫到 context 以外的地方** —— 那個地方是 `.scratch/<slug>/`。

所以流程是三段，而**第一段結束時一定要停下來**。

## 這支 skill 不重複 CLAUDE.md

`CLAUDE.md` 已經規定的東西這裡一個字都不再寫：要先讀哪幾份文件、PR 的基底是
`develop`、issue 的格式、測試怎麼跑、改完 domain 要回頭補 SPEC 與 ADR、
`public/` 動了要顧 `sw.js`。**同一件事寫兩遍會讓模型猜「講兩遍的是不是比較重要」。**

---

## 第一段：先回答，不要動 code

**一行程式都不要改。** 這一段的產出是對話裡的答案，不是檔案。

1. **分出兩種需求。** 使用者標了「這條我覺得邏輯怪怪的」的那幾條，跟「這是
   bug」是**兩種工作**：
   - bug → 找到哪一行、修
   - 「邏輯怪怪的」→ **先翻 `docs/adr/` 問「當初為什麼這樣決定」**，然後可能
     回答「那個決定還成立，是畫面沒講清楚」

   猜錯的成本不對稱：把「邏輯怪怪的」當成 bug 修，等於重構一個本來沒壞的東西。

2. **回答她問的架構疑問**，而且要從 ADR 與 commit 歷史找證據，不要憑讀 code
   推測當初的意圖。她問「我當時是怎麼想的」的時候要的是**那份紀錄**，不是你的
   重新推導。找不到就說找不到 —— 編一個理由比說不知道糟得多。

3. **清查連動。** `CLAUDE.md` 的「容易漏掉的連動」那張表是起點不是終點：
   照她要動的東西，把**實際依賴它的模組全部列出來**（`grep`／graphify 都用），
   一支一支說「這裡會怎麼受影響」。漏一個的症狀通常是「畫面看起來對、資料是錯的」。

4. **提出重構策略與風險**，包含「不改」這個選項。既有決定推得翻要說清楚翻的是
   哪一支 ADR，而**不要改掉舊的那一支**（補一支新的）。

5. **停下來。** 把答案與策略給她，等她回話。

### 第一段結束時要問的三件事

問完就停，不要自己回答：

- 這幾條裡**哪幾條必須一起出貨**？（分兩個 PR 上 staging 的話中間那個狀態會不會怪）
- 策略同意嗎？不同意的是哪一段？
- 哪幾支 issue 要她逐支看過，哪幾支可以一次做完不用問？

---

## 第二段：開 issue，再停一次

取得共識之後才開檔案。格式與慣例見 `docs/agents/issue-tracker.md`。

- `.scratch/<feature-slug>/spec.md` 放這一輪的全貌與第一段談定的策略
- `.scratch/<feature-slug>/issues/NN-<slug>.md` 一支一個可以獨立出貨的東西

**每一支 issue 一定要有的三塊**（照這個 repo 既有的那 12 支寫）：

| 那一塊 | 放什麼 |
|---|---|
| 她要的 | **原話，逐字貼上，不要整理。** 「我甚至不知道為甚麼中間要多一個來訪的介質」比「請重構 Visit-Slot 關係」有用十倍 |
| 為什麼會這樣 | 現在那一行在哪、它為什麼長這樣。查到的 ADR 編號寫進去 |
| 判準 | 怎麼知道做對了。**「這一行會不會讓 X 被算成 Y」那種問句**，不是「要能正常運作」 |

還要有 `Status:` 一行（`todo` / `done`）與「動工前先讀」一行。

**依賴要標出來**：`Blocked by: 04` 那種。順序錯了的代價是後面那幾支建築在會被
改掉的東西上。

**issue 清單給她看過再動工。** 這是第二個閘門，而且它便宜 —— 她看一份清單要
三分鐘，看一個三千行的 PR 要一小時而且只能整包信或整包不信。

---

## 第三段：一支一支做

一支 issue 一個 commit。**每一支都走完整條路再開始下一支**：

1. 紅燈：先寫一支重現得出來的失敗測試，跑過確認它真的紅（`CLAUDE.md` 有這條）
2. 修到綠
3. `npm run verify`
4. commit，把那支 issue 的 `Status:` 改成 `done`

### 為什麼是一支一個 commit

她可以在任何一支之後說「停，這個方向不對」，而已經做完的那幾支不用回頭。
一個包含八支 issue 的巨大 commit 沒有這個性質。

### 什麼時候要換一個 session

**動到 domain 規則或狀態機那幾支，做完一支就 `/clear`。** 下一支從讀 issue
檔案開始 —— 那份檔案裡有它需要的一切，這就是第二段花那些功夫的回報。

一串小的 UI 修可以留在同一個 session（換 session 的成本是重新讀一遍那幾個檔案）。

判準：**這一支做完之後，下一支需不需要繼承任何「我剛剛想過但沒寫下來」的東西？**
需要的話那個東西應該先寫進 issue，然後就可以 `/clear` 了。

---

## 交付

1. PR 開向 `develop`（`CLAUDE.md` 的「上線」那節）
2. **`/matt-code-review`** 審這一輪的全部改動，照建議微調
3. **手動測試清單**：條列她可以**照順序點**的路

手動測試清單的兩個常見寫壞方式：

- **寫成「我做了什麼」的複述。** 她要的是「你可以怎麼點」——
  `日曆 → 點 9/14 那格 → 點客戶A 那一列 → 按鉛筆`，不是「修好了單段編輯」
- **照自己的意圖寫，沒有真的走過。** 同一件事在兩個入口的選擇器常常不一樣
  （壓表的品項丸子是 `[data-ivproduct]`、來訪編輯器是 `[data-chip="s0-iv"]`），
  沒走過的清單會叫她去點一個不存在的東西

---

## 這一輪結束前

- 每一支 issue 的 `Status:` 都是 `done`
- 推翻或新增的連動關係已經回去補進 `CLAUDE.md` 的那張表
  —— **不補的話那張表的價值會隨每一輪重構衰減**，而下一輪她又得在提示詞裡
  重新要求你去釐清它本來就該擋住的事
- 既有決定被推翻的話補了新的 ADR，舊的那一支一個字都沒改
