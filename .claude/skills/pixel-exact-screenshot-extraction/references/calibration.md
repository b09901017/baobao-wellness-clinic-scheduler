# 校正：讓本機畫出來的像素跟截圖一模一樣

目錄：為什麼做得到 → 要校的四樣東西 → 字型 → 字級 → 起始位置 → 色調對照 → 背景與墨的門檻 → 判準的刻度 → 校不起來時

## 為什麼做得到

瀏覽器畫一個字串，結果只由這幾件事決定：字型檔、字級（換算成裝置像素）、字的原點落在像素格的哪個小數位置、
文字顏色與背景、以及作業系統的點陣化方式。這幾件事一樣，像素就一樣 —— 不是「很像」，是每個通道的值都相同
（`selftest.py` 會重畫兩次確認這一點）。

截圖把這些像素原樣存了下來（PNG 是無失真的）。所以只要在本機把那幾件事重現出來，候選字串畫出來的小塊
就可以拿去跟截圖逐像素比。**JPEG 截圖不適用這個判準**（壓縮會改掉像素值）；要用的話門檻要重新量，而且會有灰色地帶。

### 次像素渲染：一個像素其實是三個

Windows 的 ClearType（以及任何 LCD 次像素渲染）把紅、綠、藍三個子像素當成三個獨立的水平位置來用。
黑字的邊緣不是灰色，是偏紅或偏藍的 —— 那不是雜訊，是**三倍的水平解析度**。
一個 5 像素寬的字有 15 個水平取樣，這是 4～5 像素高的中文字還分得出彼此的原因。

所以比對一律用三個通道，不要先轉灰階。`selftest.py` 會印「次像素渲染：有／沒有」：
畫出來三個通道一樣（灰階反鋸齒）而截圖是彩色邊緣，或反過來，那就是點陣化方式不一樣，後面不用試了
（Chromium 啟動參數 `--disable-lcd-text` 可以關掉次像素渲染，寫在 `profile.json` 的 `chromium_args`；這一條沒有實戰驗證過）。

### 起始位置（phase）

字串的原點通常不在像素邊界上（表格欄位的 x 是算出來的小數）。原點往右挪 0.1 個像素，
每個字的每個邊緣落在子像素上的比例都變了，畫出來是另一組像素值。

- 版面的最小單位是 **1/64 CSS px**。所以一個裝置像素裡只有 `64 / deviceScaleFactor` 個不同的起始位置。
- 截圖原本的縮放大約是 0.375（字級 14.2 CSS px × 0.375 ＝ 5.33 裝置像素），那就只有 171 個位置。
  但我們不知道原本確切的縮放，所以合成時用**更小的 deviceScaleFactor（0.125）配上等比例放大的字級**：
  裝置像素上的字一樣大（驗證過：同一個位置畫出來的像素完全相同），而每個像素有 512 個位置可以試，涵蓋了原本的 171 個。
- 一個字串在 512 個位置上大約只畫出 30 種不同的樣子（位置是一段一段的：連續十幾個位置畫出來一樣）。
- **同一張圖同一欄的每一格，起始位置都一樣**（靠左對齊的字都從同一個 x 開始）。所以它是「一張圖一欄校一次」，不是一格一次。
- 垂直方向不用校。基線會貼齊整數像素：列距是 19.6 這種小數，每一列的字照樣跟同一份合成吻合。

## 要校的四樣東西

| 參數 | 存在哪 | 怎麼找 | 差一點的後果 |
|---|---|---|---|
| 字型 | `profile.json` 的 `font` | `calibrate.py font` | 誤差多一倍以上，永遠到不了 1.1 |
| 字級 `em`（裝置像素／em） | `profile.json` 的 `em` | `calibrate.py em` | 差 0.01 像素：12 個錨點剩 9 個吻合；長字串先壞 |
| 色調對照表 | `lut.npy` | `calibrate.py lut` | 誤差停在 2 多，一格都過不了 |
| 起始位置 | 每張圖每一欄各一個，不存檔 | `match.calibrate()`／`calibrate_prefix()` | 那一欄誤差 3～5 |

順序是 **字型 → 字級（粗）→ 色調 → 字級（細）→ 色調 → check**。色調對照是拿「已經對齊的合成」跟截圖配對出來的，
所以字型字級要先大致對；而字級的細掃要有對照表才看得出 0.005 的差別。

錨點（`anchors.json`）是整件事的地基：

```json
[{"stem": "shot1", "row": 1, "seg": 1, "text": "2026-05-21"},
 {"stem": "shot1", "row": 3, "seg": 9, "text": "否"}]
```

- `row` 是第幾列資料（從 1 起算），`seg` 是 `slice_grid.py` 印的欄號。
- 內容要**確定**：放大後明確看得出的數字、整欄都一樣的固定值、使用者說的。猜的不算。錨點錯了，整個校正會往錯的方向收。
- **數字與中文都要有**（網頁的字型堆疊常常讓英數字與中文來自不同的字型）。
- **越長越好**：字級的誤差是沿著字串累積的，10 個字的日期比 1 個字的「否」敏感十倍。
- 多拿幾張圖的。每張圖的縮放理論上一樣，實際上使用者中途調過縮放也不奇怪 —— 那樣就要一張圖一份 profile。

## 字型

`calibrate.py font` 把每個候選字型畫一次，印每個錨點的誤差。看法：

- 第一名明顯小於第二名（實測：正確的 3.6，第二名 8.2，其他 20 以上）才算找到。這時候誤差還到不了 1 —— 字級與色調還沒校。
- 標「＝預設」的是畫出來跟不存在的字型一模一樣：這台機器沒裝那個字型，或它本來就是預設字型。
  **字型沒裝的時候瀏覽器不會報錯，會安靜地換一個。** 所以候選裡排第一名的如果標著「＝預設」，要想一下是哪一種。
- 數字錨點與中文錨點分開看。一邊吻合一邊不吻合，就是字型堆疊：把兩個字型照順序寫成 `Arial, 'Microsoft JhengHei'` 這樣再比。
- **UI 變體是另一個字型。** 「Microsoft JhengHei UI」與「Microsoft JhengHei」的中文一樣，數字 1、2 等幾個字形不同、行高不同。
  實測（Windows 繁中）：網頁寫 `system-ui` 拿到的是 UI 版；什麼都沒指定（預設的 sans-serif）拿到的是一般版。
- 手上有截圖當時的網頁就直接看 CSS 的 `font-family`，比猜快。

還不知道字級時，先量一個粗估：**全形中文字的字距就是 1 em**。量一串連續中文字的寬度除以字數。

## 字級

量得到的只有一個數字：一個 em 佔幾個截圖像素。它是「CSS 字級 × 頁面縮放 × 螢幕 DPR」的乘積，三個拆不開，也不需要拆。

```bash
python scripts/calibrate.py em 5.0 6.0 0.05     # 粗掃：看「大小對得上」的範圍
python scripts/calibrate.py em 5.30 5.36 0.005  # 細掃（要先有色調對照）
```

實測的樣子（正確值 5.33）：

```
em 5.3000  吻合 7/12   平均 2.23  最差 5.97
em 5.3200  吻合 9/12   平均 0.97  最差 1.77
em 5.3300  吻合 12/12  平均 0.78  最差 0.88
em 5.3400  吻合 10/12  平均 1.13  最差 2.94
em 5.3600  吻合 5/12   平均 3.27  最差 9.64
```

千分之二的誤差就看得出來。原因：一個 10 個字的字串，字級差 0.2% 累積起來是 0.1 個像素 —— 剛好是會讓邊緣換一組值的量。
所以**判斷字級要看最長的那幾個錨點**，短錨點在一個範圍內全部吻合，分不出來。

掃出來最好的值寫回去：`python -c "from pxx import conf; conf.save(em=5.33)"`（在 `scripts/` 底下、`PXX_WORK` 設好）。

**有長字串之後再掃一次。** 12 個字以內的錨點分不出 5.330 與 5.333（差 0.003 像素／字，30 個字才累積到 0.1 像素）。
讀出幾則 15～25 個字的句子之後，拿它們當錨點細掃：看的不是「吻合幾個」，是**每個長錨點吻合的起始位置有幾個** ——
字級越準，那個範圍越寬（實測：5.326 時 25 個字的那一則 0 個位置吻合，5.328 是 9 個，5.3333 是 2 個）。

即使字級校到最好，模型的字距也只準到大約 0.01 像素。這對短字串沒有影響；對三十個字以上的字串，
意思是「整格在同一個起始位置上對齊」做不到 —— 那是讀取與驗證長字串要分段算的原因（`reader.md`）。

## 色調對照表（LUT）

字型字級都對了，誤差還是停在 2 多。把同一格的合成值與截圖值一個通道一個通道對起來看，會發現它們落在一條平滑的曲線上，
不是對角線：中間調差幾個灰階（實測：合成 96 → 截圖 99、合成 160 → 截圖 158，全程最多差 6）。
來源是兩邊文字對比／gamma 的設定不同（使用者的螢幕設定、有頭與無頭模式）。

差這麼少為什麼要緊：判準是「每個通道平均差不到 1」。系統性的 2～3 個灰階正好把正確答案推到門檻外面，
同時把「正確」與「差一個像素」之間的距離吃掉一半。**有了對照表：0.73～0.79，12／12。沒有：2.0～2.45，0／12。**

`calibrate.py lut` 的做法：每個錨點在所有起始位置畫一次（不套對照），挑「大小完全一樣而且最像」的那一個，
逐通道收集（合成值 → 截圖值），每個合成值取中位數，沒觀測到的值內插，最深的那一段照最後的斜率外推。

看它印的兩個數字：

- 用了幾個錨點、幾個不同的合成值。合成值太少（< 40 種）表示錨點太少或太短，曲線是內插出來的，多加幾個。
- 「5%～95% 的範圍」：同一個合成值對到的截圖值有多分散。很小（1～3）才是乾淨的。很大表示配對本身就沒對齊
  （字型、字級或起始位置不對），那條曲線是糊的，不要用。

**門檻改了、背景正規化改了，都要重新擬合** —— 對照表是在那些設定下配出來的。

## 背景與墨的門檻

- 小塊存的是「背景減像素」（正值＝比背景暗），不是原始像素。
- **斑馬紋的灰底列**：字是黑的、底是灰的，等比例放大回白底（乘上 255／背景值）。驗證過：同一個字串在灰底與白底的小塊，
  差的就是這個比例。每一列的背景自己量（那一列像素的中位數），不要假設只有兩種。
  滑鼠停在上面的那一列、被選取的那一列會是第三種顏色 —— 只要是灰階就一樣處理；帶顏色的底要三個通道分開正規化（`grid.norm_patch` 目前只用一個通道）。
- **有墨的門檻（`ink_th`，預設 4）兩邊要一樣。** 觀測那一側門檻用 10、合成那一側用 4 的時候，
  字的邊緣很淡的那一欄像素在觀測側被裁掉、合成側留著，兩邊寬度差一欄 —— 症狀是「明明是對的字，誤差卻 3～4」。
- 文字顏色不是純黑時改 `profile.json` 的 `color`。量法：找一個粗筆畫的中心像素（三個通道都最暗的地方）。
  灰色的字（例如 `#606266`）跟「黑色的字過了一條色調曲線」在小字上很難分 —— 先當黑色加對照表試，不行再換顏色。

## 判準的刻度

誤差＝每個「觀測有墨的通道值」的平均絕對差，對齊容許 ±1 像素。實測的分布：

| 誤差 | 意思 |
|---|---|
| 0.6～0.9 | 正確的字串在正確的起始位置。絕大多數吻合落在這裡 |
| < 1.1 | 吻合（`match.EXACT`） |
| 1.1～1.6 | 差一兩個很淡的像素。筆畫密的字、貼著邊界的起始位置會這樣。收，但標出來（`match.CLOSE`） |
| 3～8 | 差一個字、或起始位置差一點 |
| ≥ 10 | 不同的字串 |
| 999 | 大小就對不上（寬或高差超過 1 個像素），沒有比 |

封閉候選的欄位另外看**第一名與第二名的差距**：實測日期那一欄最小的差距是 2.2、時段是 2.3。
差距小於 1 的那一格不要收 —— 兩個候選在那個解析度下分不出來，把兩個都列出來。

換一批截圖，這張表要重新看一次（`calibrate.py check` 與第一個封閉欄位跑完時印的數字）。
字更小、對比更低的圖，正確答案的誤差會整體往上移，門檻要跟著它的實際分布定，不是照抄 1.1。

## 校不起來的時候

用 `peek.py <stem> <列> <欄> "候選字串"` 把觀測與合成並排印出來，看數字：

- **大小不一樣**（寬差 2 以上）：字級差很多，或字型的字寬不同。先粗掃字級。
- **大小一樣、形狀明顯不同**：字型錯。看數字的 1、2、4、7 最容易分辨字型。
- **形狀一樣、整體深淺差一截**：文字顏色不是黑的，或還沒有色調對照。
- **只有最左或最右一欄像素不一樣**：墨的門檻兩邊不一致，或那一格旁邊貼著別的東西（圖示、按鈕、欄線）。
- **每個錨點各自在不同的字級吻合**：那幾張圖的縮放不一樣，一張圖一份 profile。
- **怎麼掃都在 3 以上**：截圖不是這種瀏覽器／作業系統畫的；或圖被縮放、壓縮過（不是原始截圖）。
  量一下列距是不是小數、字的邊緣有沒有彩色 —— 被縮放過的圖邊緣是糊的灰色，那就不適用這套方法了，照實跟使用者說。
