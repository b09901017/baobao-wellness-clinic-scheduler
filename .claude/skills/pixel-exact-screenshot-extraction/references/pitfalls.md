# 踩過的坑

每一條都是實際發生過的：先看到症狀、花時間找到原因、才有現在的做法。照領域排，每條三段 —— **看到什麼／為什麼／怎麼辦**。
標 ✦ 的是「安靜地錯」的那一種：沒有錯誤訊息，結果看起來正常，只是不對。那幾條最貴。

目錄：一、為什麼不用看的 · 二、校正 · 三、渲染 · 四、比對與起始位置 · 五、逐字讀取 · 六、切格子 · 七、機器 · 八、工具鏈 · 九、回報

---

## 一、為什麼不用看的

**1. ✦ 把圖放大給模型（或人）讀。**
看到什麼：放大 8 倍之後數字好像看得出來，讀出來的名字也都像名字。
為什麼：字只有 4～5 個像素高，資訊量不夠決定一個中文字；讀的人用的是「這裡應該是什麼」的先驗。錯的都是合理的錯。
怎麼辦：放大圖只拿來**認版面**（哪一欄是什麼、徽章有幾種顏色、錨點的日期）。內容一律逐像素比。

**2. ✦ 分給好幾個 agent 各讀一次、取多數決。**
為什麼：小字的錯誤不是隨機的。同一團像素，每個讀的人都會讀成同一個比較常見的字。多數決在這裡是把錯誤蓋章。
怎麼辦：不要。驗證要用跟「讀」不一樣的機制 —— 這裡是重畫再比。

**3. 想用現成的 OCR。**
為什麼：一般 OCR 是為 20 像素以上的字訓練的，而且先把圖轉成灰階 —— 剛好把次像素那三倍的水平解析度丟掉。
怎麼辦：字夠大（10 像素以上）時 OCR 加抽樣核對是合理的，那不是這個 skill 的場合。

## 二、校正

**4. ✦ 字型差一個變體。**
看到什麼：誤差卡在 3～8，怎麼掃字級都下不去；中文看起來都對，數字怪怪的。
為什麼：「Microsoft JhengHei UI」與「Microsoft JhengHei」中文字形一樣，數字 1、2 等不同。YaHei 與 JhengHei 也是這種關係。
怎麼辦：`calibrate.py font`。候選要包含 UI 版與 `system-ui`。數字錨點與中文錨點分開看。

**5. ✦ 字型沒裝，瀏覽器安靜地換了一個。**
看到什麼：畫得出字、沒有任何錯誤，但所有候選都對不上。
怎麼辦：`selftest.py` 會拿「不存在的字型」畫一次來比；`calibrate.py font` 把這種標成「＝預設」。

**6. 字級只差一點點。**
看到什麼：短字串吻合、長字串不吻合；或一欄裡一半吻合一半誤差 2～5。
為什麼：字級的誤差沿著字串累積。差 0.2%，十個字之後就是 0.1 個像素。實測差 0.01 像素（千分之二），12 個錨點剩 9 個。
怎麼辦：用最長的錨點細掃到 0.005。字級找到之後換過色調對照表的話，再掃一次。

**7. 想把字級拆成「CSS 字級 × 縮放」。**
為什麼：拆不開，也不需要。量得到的只有乘積。花時間猜「原本是 14px 縮 37.5% 還是 13px 縮 41%」沒有意義。
怎麼辦：`profile.json` 只存一個 `em`（截圖像素／em）。

**8. ✦ 沒有色調對照表。**
看到什麼：字型字級都對了，形狀一模一樣，誤差就是停在 2.0～2.5，一格都過不了 1.1。
為什麼：兩邊的對比曲線差幾個灰階（最多 6）。很小，但判準是「平均差不到 1」。
怎麼辦：`calibrate.py lut`。有了之後是 0.7～0.8。

**9. 色調對照表在最深的那一段平掉。**
看到什麼：筆畫密的字（深色像素多）誤差偏高。
為什麼：錨點裡沒有夠深的像素，內插把沒觀測到的那一段當成水平線。
怎麼辦：照最後一段的斜率外推（`calibrate.py lut` 已經這樣做）；錨點裡放幾個筆畫多的中文字。

**10. 改了門檻或正規化，沒有重新擬合對照表。**
為什麼：對照表是在那一組設定下「合成值 ↔ 截圖值」配出來的。
怎麼辦：`ink_th`、背景正規化、文字顏色，動任何一個都重跑 `lut` 與 `check`。

**11. ✦ 觀測與合成兩邊「有墨」的門檻不一樣。**
看到什麼：明明是對的字，誤差 3～4；`peek.py` 看到兩邊寬度差一欄。
為什麼：門檻高的那一側把字邊緣很淡的一欄像素裁掉了。少一欄 → 對齊錯一格 → 誤差算在整格上。
怎麼辦：兩邊都讀 `conf.P['ink_th']`。自己切格子（`obs_fn`）時最後的裁切也要用它。

**12. 灰底的列全部對不上。**
為什麼：斑馬紋。字是黑的、底是灰的，「背景減像素」比白底列小一截。
怎麼辦：每一列自己量背景，乘上 255／背景（`grid.norm_patch`）。帶顏色的底（選取中的列）要三個通道分開做，目前沒有實作。

## 三、渲染

**13. ✦ 頁面太大，後段沒有被畫出來。**
看到什麼：逐字讀取讀到一半莫名其妙斷掉；同一格重跑一次斷在不同的地方；封閉候選少數幾格「沒有候選吻合」。沒有任何錯誤訊息。
為什麼：一頁放了幾千個磁磚（幾萬 CSS px 高）時，截圖照樣成功，但頁面後段是空白的。空白的磁磚＝「這個候選畫不出東西」＝不吻合，正確的候選就這樣消失了。
　　實測：12,000 × 31,000 CSS px 每次都是最後一段空白；12,000 × 12,000 約四分之一的頁有空白；12,000 × 6,000 沒有。看的是面積。
怎麼辦：`synth.py` 把每一頁壓在 12,000 × 6,000 以內，**而且不靠它**：畫完之後檢查「有字的字串一定要有墨」，
　　一頁裡有一塊該有墨卻空白，整頁拆小重畫（邊界上的磁磚是「畫了一半」的字，不是空白，只查空白查不到）。
　　跑完看 `synth.stats()['repainted']`，不是 0 就表示上限對這台機器還是太大。
教訓：**任何「畫不出來」都不可以安靜地變成「不吻合」。**

**14. 每一批都重開一次瀏覽器。**
看到什麼：數字欄（字集只有十個字）讀一格要四十幾秒，CPU 一直在轉。
為什麼：開一次 Chromium 一秒多，而小字集的一批只有幾十個磁磚。實測 174 批花了 243 秒 —— 每批 1.4 秒，幾乎全是在開瀏覽器。
怎麼辦：瀏覽器開著不關、一批一批送（`render.cjs --serve`）。同樣大小的批，141 批 24 秒。

**15. 截圖卡住，永遠不回來。**
為什麼：Playwright 當函式庫用的時候，`page.screenshot()` 預設沒有逾時。
怎麼辦：Node 那邊給 `timeout`；Python 這邊一頁超過 60 秒就當失敗、關掉那個瀏覽器換一個重來（`PAGE_TIMEOUT`）。

**16. 機器忙的時候偶爾「Unable to capture screenshot」。**
怎麼辦：等一兩秒、換一個瀏覽器重試，最多五次。這是暫時性的，不是程式錯。**但它也是機器已經太忙的訊號** —— 看到就把同時數調低。

**17. 畫出來的檔案把磁碟吃光。**
看到什麼：工作目錄幾個小時長到 13 GB。
為什麼：每一批的像素檔（十幾 MB）、PNG、規格檔都留著當快取。逐字讀取的每一批都是獨一無二的，快取永遠不會命中。
怎麼辦：預設用完就刪（`keep=False`）。只有「同一份候選要重複比很多次」才留，而且有上限（`PXX_CACHE_MB`）。

**18. 連續的空白、尾巴的空白不見了。**
怎麼辦：畫字的那個元素要 `white-space: pre`。

**19. 想確認兩種縮放畫出來一樣。**
合成用的是比原圖小的 deviceScaleFactor 配上放大的字級（為了每個像素有 512 個起始位置）。這件事驗證過是逐像素相同的；
換一種字型或瀏覽器版本時值得再確認一次：同一個字串、同一個位置，兩種設定各畫一次比一下。

## 四、比對與起始位置

**20. 起始位置試得太疏。**
看到什麼：一欄裡大部分吻合，少數幾格誤差 3～5，而且換一張圖是另外幾格。
為什麼：一個字串吻合的位置只是一小段；每像素只試 16 或 64 個位置，那一段剛好落在兩個取樣之間。
怎麼辦：每像素 512 個位置（deviceScaleFactor 0.125）。封閉候選跑完，還差一點的格子用 `fine_decode` 在所有位置上再比。

**21. ✦ 用一個詞（或一段短前綴）校出來的範圍，只抽三個點去用。**
看到什麼：逐字讀取第一個字就放棄、只花幾秒；或封閉候選有幾格誤差 5 而不是 0.8。
為什麼：每個字串吻合的範圍邊界都不一樣，真正的位置在它們的交集裡，可能只有 0.01 像素寬。0.08 像素寬的範圍抽頭中尾，全部落在交集外面是常態。
怎麼辦：整段都用（`match.spread()`）。`pick_phases()` 只在「好幾個不同的錨點一起校出來」之後用。
　　實戰裡有一欄九格因為這個從頭到尾沒讀出來，還被當成「那幾格比較難」。

**22. 以為每一格的起始位置都要各自找。**
為什麼：同一張圖同一欄靠左對齊的字，原點都在同一個 x。
怎麼辦：一張圖一欄校一次。例外：格子前面有圖示的，字的起點不同，要分開校。

**23. 只看第一名的誤差。**
為什麼：候選裡沒有正確答案時，第一名可能是「最不差的錯字」，誤差 2～3。
怎麼辦：門檻（1.1）之外，同時看第一名與第二名的差距。封閉候選印「最小差距」；小於 1 的格子單獨處理。

**24. 單一個字的格子誤差偏高。**
看到什麼：「是／否」「男／女」這種欄位，一批格子落在 1.09～1.22。
為什麼：有墨的像素少，一兩個灰階的差佔的比例大。
怎麼辦：看另一個候選差多遠（實測 44）。差得遠就收，標成「只差一兩個像素」。

## 五、逐字讀取

設計上的十個決定寫在 `reader.md`，這裡只列症狀與來龍去脈。

**25. 錯的寬字贏過對的窄字。** 用整格的殘差排名時會這樣。→ 只留前綴誤差過門檻的。

**26. 中文一個字都讀不出來，候選名單全是標點與細字母。** 細字到處都「局部吻合」。→ 粗篩分寬／中／細三類各留一些。

**27. 字串裡的空白讀不出來。** 空白不佔墨。→ 每一步另外開一條「後面接空白」的前綴。

**28. ✦ 第一個字就放棄、只花幾秒。** 那個字不在字集裡。Big5 那一萬三千字裡沒有的字，人名與品牌名會用。→ 換 `TEXT_ALL`（整個 CJK 基本區）。
　　先確認不是第 21 條：用 `phs=None` 單獨讀那一格。

**29. 讀出來了，套不回自己那一格。** 極少見：讀取時吻合的起始位置不在那一欄校出來的範圍裡。→ `Field` 會直接記下來；看到這種格子，那一欄的起始位置值得重校。

**30. 同一個值讀了好幾次。** → 沒吻合的格子先照「像素完全相同」分組，一組讀一次；讀出來馬上套到所有圖。

---

**30a. ✦ 整格誤差過關，裡面卻夾著錯字。**
看到什麼：長句讀出來了，誤差 0.8～1.4，字看起來也通順。逐字對才發現有一個字、一個標點不對。
為什麼：誤差是平均。30 個字裡錯 1 個只多 0.4；長得幾乎一樣的字、選錯的標點連 12 個字的字串都看不出來。
　　讀取時也一樣：整條前綴一起平均的話，讀到第 25 個字，一個完全錯的字照樣過關。
怎麼辦：讀取時只看尾段（兩個字寬）；讀完看區域誤差（`match.local_err`，一個字寬的滑動視窗）；最後驗證用 `verify_local()`。
　　實戰：六則備註的全形逗號被讀成全形減號或間隔點，整格誤差全部在 1.1 以內。

**30b. ✦ 窄的正確候選輸給寬的勉強候選。**
為什麼：排名只看「蓋得寬的優先」。逗號的墨只有一兩個像素寬；「空白＋一個橫畫的字」勉強過關（1.25）但比較寬。
怎麼辦：排名分兩層，乾淨吻合的（< 1.3）永遠排在勉強過關的前面。

**30c. 選錯一個細字，下一步就沒有任何字接得上，整格放棄。**
怎麼辦：每一步沒被選上的候選留在退路裡，死路時退回去試。「後面接空白」也放在退路裡（每一步都畫的話成本多一倍）。

**30d. ✦ 長字串讀到第二十幾個字突然斷掉，而那個字明明在字集裡。**
為什麼：把每一步吻合的起始位置一路取交集。模型的字距只準到約 0.01 像素，每一步的範圍 0.08 像素寬、邊界各不相同，
　　三十個字的交集常常是空的。同一則正確的 30 字備註，整格在同一個位置上比，尾巴的區域誤差是 15。
怎麼辦：起始位置跟著走 —— 只要求最近三步有交集，每一步可以漂 0.023 像素。長字串的吻合與驗證都分段算（`reader.check`），
　　**不要拿 `verify()`／`local_err()` 判長字串**，會把對的判成錯的。
　　排除過的解釋：每個字多一點字距（掃過，0 最好）、字級差一點（用長字串細掃過，現值就在最好的範圍裡）。

**30e. 粗篩只畫範圍的中間點。**
看到什麼：某個字就是讀不下去，只花幾秒；用全部位置暴力比，那個字明明吻合（0.83）。
為什麼：前綴在 0.201～0.217 吻合，下一個字只在 0.215～0.217 吻合。粗篩畫 0.209，正確的字排不進前 16 名。
怎麼辦：粗篩畫範圍的頭與尾。貴一倍，但少了它整格讀不出來。

**30f. 校出來的範圍只留誤差最小的位置；一個差一點的錨點拖垮整欄。**
看到什麼：重啟之後，同一張圖那一欄本來吻合的四格全部變成沒讀出。
為什麼：一則讀得差一點的長句（誤差 1.41）進了詞彙、當了錨點，共同最佳位置上的最差誤差過不了門檻，整欄就不校了。
怎麼辦：把最差的錨點拿掉再校；範圍留 0.3 的餘裕（`calibrate(tol=)`）。

**30g. 撤回重讀、讀出同一個字串，結果每次重啟都再讀一遍。**
為什麼：從 log 撿詞彙時「所有撤回過的都不要」。重讀出來的是同一個字串，也被拿掉了，那一格每次都當成沒讀過（一次八分鐘）。
怎麼辦：log 一行一行照順序處理：讀到 → 加、修正 → 換、撤回 → 拿掉。

**30h. 一格要讀十幾分鐘，超過單次的時間上限，永遠讀不完。**
怎麼辦：`read()` 被打斷時交回讀到的地方，下次用 `prefix=` 接著讀。換字集時也從讀到的地方接，不重頭來。

**30i. 字集裡沒有的符號被「最像的」頂替。**
看到什麼：見 30a。讀取器只能選字集裡有的。
怎麼辦：`charset.SYMBOLS`（各種破折號、間隔點、注音、全形英數標點）已經在 `TEXT` 裡；讀完跑 `refine_suspects()`。
　　全形空白也是：不佔墨，另外一條退路（`BLANKS`）。

## 六、切格子

**31. 同一個欄位在每張圖是不同的欄號。**
為什麼：整欄沒有字的欄不會被切出來；使用者每次橫向捲動的位置不同；有的圖多拍到幾欄。
怎麼辦：每張圖各寫一份欄位對應。對完之後用「這一欄出現過的值」檢查一次 —— 對錯一欄的話，值的種類會很奇怪。

**32. ✦ 「第幾列」有兩種算法。**
為什麼：表頭、被截掉的半列也被切成一「列」。內部索引跟人數的第幾列不一定差 1。
怎麼辦：給人看、給人填的一律是「第幾列資料，從 1 起算」，用 `grid.ri_of()` 換。錨點指錯格的症狀是「十二個錨點有兩個誤差 10 幾」。

**33. 字旁邊貼著圖示或按鈕。** 見 `recipes.md`「格子裡除了字還有別的東西」。三個細節：字貼著方塊時要在邊框切開；
切的時候很淡的邊緣要留著；「第一個空欄」遇到一串 1 會多切掉一個字（而少一位的字串照樣吻合 ✦）。

**34. 滑鼠停著的那一列、選取中的那一列，背景是第三種顏色。** 每一列自己量背景，不要寫死兩種。

**35. 檔名排序不是時間順序。** `10-12.png` 排在 `5-21.png` 前面。順序有意義時把檔案照順序列出來。

## 七、機器

**36. 把使用者的筆電跑到過熱斷電（兩次）。**
發生了什麼：同時開了三四個工作，每個工作各自再開四到六個瀏覽器，16 個邏輯核心全滿，持續一個多小時。
　　第二次之前還把工作丟成獨立行程「讓它活過工作階段」—— 沒有人看得到它，也沒有人能停它。
為什麼：每個工作都覺得自己只開了四個。上限寫在每個行程自己身上，乘起來沒有人管。前面幾十秒的短爆量都沒事，出事的是「持續」。
怎麼辦：
- 同時幾個瀏覽器是**整台機器**的上限，用作業系統的檔案鎖做（`synth._Slot`）。驗證過：三個行程同時跑，加起來還是 2。
- 預設 2。量過：這台機器 1 個瀏覽器整機 25%、2 個 43%，速度只多六成。不是越多越好。
- 重的步驟設時間上限、每讀一格存一次檔；超過十分鐘的先問使用者。
- 不丟背景。
- 溫度感測器在一般權限下讀不到，所以沒有辦法「看溫度自動降速」—— 只能靠上限與時間。

**37. 估錯一個數量級。**
為什麼：「幾格 × 幾個字 × 字集大小 × 幾條前綴 × 幾個位置」每一項都不大，乘起來是百萬。
怎麼辦：`reader.estimate()` 乘上格數，除以 `selftest.py` 量到的速度，**在開跑之前**。

**38. 能搬到雲端跑嗎。** 不行（通常）。雲端的沙盒是 Linux：沒有那個字型，就算裝了字型，FreeType 與 Windows 的點陣化結果也不同，像素對不起來。
而且截圖是使用者的私人資料，本來就不該離開他的機器。

## 八、工具鏈

**39. 裝不了 Pillow。** 公司網路、防毒軟體會擋 pip。→ Windows 上用 PowerShell 的 System.Drawing 把 PNG 轉成不壓縮的 BGR（`to_raw.ps1`）。
兩個細節：`DrawImage` 要指定寬高（不然會照圖檔裡的 DPI 縮放）；每一列後面有對齊用的填充，要一列一列複製。

**40. 從 shell 寫 Python 檔，反斜線被吃掉。** `'\n'` 變成真的換行，檔案就壞了。→ 用寫檔工具直接寫；非得從 shell 寫就用 `chr(10)`、`chr(92)`。寫完跑一次語法檢查。

**41. 輸出接了管線就看不到進度。** → `print(..., flush=True)`。

**42. 中文印出來是亂碼。** → 每支腳本開頭 `sys.stdout.reconfigure(encoding='utf-8')`。

**43. Playwright 的 PNG 解碼器是內部路徑。** 升版可能搬家。→ `render.cjs` 先找 `pngjs`，沒有才用 Playwright 包的那一份。壞了就 `npm i pngjs`。

**44. 背景工作逾時被移到背景之後還在跑。** 指令逾時不等於行程結束。→ 逾時之後先查有沒有殘留的 `node render.cjs` 與 Python 行程，停掉再繼續。

## 九、回報

**44a. 逾時的指令沒有任何輸出。** 輸出接了管線（`| cut`、`| python 濾內文`）時，被 `timeout` 砍掉的行程來不及把緩衝區吐出來，
看起來像「什麼都沒發生」。→ `python -u`；長的步驟自己先存檔再印；時間上限設在程式裡（`set_deadline`），比外面的 `timeout` 短。

**44b. 除錯時把真實內容印進對話。** 要看「讀到哪裡、錯在哪」，多半只需要長度、誤差、哪一個字的碼位。
→ 先印統計；真的要看內文，只看那一格。印出來的東西不要貼進 skill、commit 訊息、issue。

**45. 把「解碼時吻合」說成「驗證過」。** 兩件事。前者是每一格在讀的當下的誤差；後者是全部讀完之後、只拿（像素, 最後寫進輸出的字）重畫再比。
中間有彙整、有合併、有手動修正，任何一步都可能放錯格。→ `match.verify()` 沒跑完，就寫「獨立驗證沒有跑」。

**46. 把沒讀出來的格子填上最接近的候選。** 見鐵則二。

**47. 把兩種寫法「修」成一樣。** 見鐵則一。實戰裡同一個編號真的對到兩個只差一個字的名字、同一個人真的有兩個編號 ——
那些正是使用者要拿這份資料去抓的東西。

**48. 真實的字進了版控。** log、pkl、報告、甚至你為了除錯印在註解裡的一格內容。→ 工作目錄在 `.gitignore` 擋住的地方；
skill 與腳本裡只用假名；交付前 `git status` 看一眼。
