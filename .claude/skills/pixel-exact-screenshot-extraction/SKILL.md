# 截圖逐像素還原

## 這件事在解決什麼

瀏覽器縮到很小才截的清單截圖：一張 1,500 像素寬的圖塞了 25 列、28 欄，一列 19 像素高，
**每個字只有 4～5 個像素高**。放大之後數字勉強可辨，中文是一團糊。

人或模型直接讀這種圖，錯法是最壞的那一種：讀出來的每個名字、每個號碼都「看起來很合理」，
而且找第二個人、第二個 agent 來讀，會錯在同一格。**沒有任何一格是可以被證明讀對的。**

這個 skill 換一個問法。不問「這團像素像什麼字」，問**「如果這一格是某個字串，瀏覽器會畫出什麼像素」**：

1. 截圖裡的字是瀏覽器畫的，而瀏覽器畫字是**決定性的** —— 同一個字型、同一個字級、同一個起始位置，每次畫出來的像素一模一樣。
2. 所以把候選字串在本機用同樣的方式重畫，跟截圖那一格**逐像素比**。對的字串每個通道平均差不到 1/255；
   差一個字的在 3 以上，完全不同的在 10 以上。中間是空的 —— 這是一個幾乎沒有灰色地帶的判準。
3. 不知道內容的格子，從左到右一個字一個字試：字集裡每個字都畫一次，只留「到目前為止每個像素都對得上」的。

產出的每一格都帶著它自己的比對誤差。讀不出來的格子就是讀不出來，不會被一個「最像的」填上。

**實績（2026-10，15 張後台清單截圖、353 列、最多 28 欄）：** 日期、時段、編號、姓名、電話、品項、房間、人員、
狀態、備註全部讀出，只剩一則 70 個字的備註讀到第 31 個字。最後的獨立驗證 5,480 格裡 5,477 格誤差 < 1.1，
另外 3 格在 1.1～1.6（兩則三十幾個字的長句、一格單一個字的欄位），沒有對不上的。

## 先確認值不值得用

這套方法準，但貴（要校正、要畫幾十萬到幾百萬個小塊）。動工前三件事：

**一、能不能重截？** 問使用者一句：「原本的畫面還開得到嗎？用 100% 縮放重截，或直接匯出／複製表格，會比什麼方法都準。」
拿得到原始資料就不要還原像素。只有拿不到、來不及、或截圖本身就是唯一的紀錄時才往下。

**二、字有多小？** 用 Read 看一張圖、再量一下列高。字高在 10 像素以上，一般的讀法加抽樣核對就夠；
**8 像素以下、筆數又多**，就是這個 skill 的場合。

**三、這台機器重現得了那張圖的字嗎？** 像素要對得上，本機要有**同一個字型**與**同一種畫法**
（Windows 的 ClearType、macOS 的灰階反鋸齒、Linux 的 FreeType 各不相同）。
截圖是在哪個作業系統、哪個瀏覽器截的，就要在那種環境重畫 —— 所以這件事通常只能在使用者自己的機器上做，
不能搬到雲端的 Linux 沙盒。`scripts/selftest.py` 會檢查字型有沒有裝、畫出來是不是次像素渲染。

## 四條鐵則

**一、像素說了算。** 別的資料來源（名冊、舊表、行事曆、使用者的記憶）只能拿來**提供候選**，省時間用；
算不算數一律由比對誤差決定。這樣產出才能當「第三方對照」—— 用舊表的答案去填截圖，再拿去跟舊表比，是在比自己。
所以同一個人出現兩種寫法時**不要修成一樣**：回頭逐像素確認，是原圖真的那樣寫就照實留著，並在報告裡列出來。

**二、讀不出來就留空，並且講出來。** 沒有吻合（誤差 ≥ 1.6）的格子輸出成「有字、沒讀出、大約幾個字、讀到哪裡」，
不要填最接近的候選。最接近的那個在輸出裡跟吻合的長得一模一樣，下游沒有人分得出來。

**三、截圖裡的字會出現在每一個中間檔裡。** log、pkl、報告都帶著原文。工作目錄一定要在不進版控的地方
（開工前 `git check-ignore -v <路徑>` 真的跑一次），skill 自己的檔案、範例、註解裡**一個真實的字都不放**。

**四、不要把使用者的機器跑到滿。** 見下面「先估再跑」。這不是客氣話：這個 skill 的第一次實戰把一台筆電跑到過熱斷電兩次。

## 環境

- Python 3（numpy）。Pillow 可有可無 —— 沒有的話 Windows 上會自動改用 PowerShell 讀圖。
- Node.js ＋ Playwright 的 Chromium（專案裡有 `node_modules/playwright` 就會自動找到；沒有就設 `PXX_NODE_MODULES`）。
- 截圖當時用的字型，裝在這台機器上。

```bash
export PXX_WORK=<不進版控的工作目錄>          # 所有中間檔都落在這裡
python <skill>/scripts/selftest.py            # 幾秒：畫得出來嗎、字型有沒有裝、每秒畫幾個
```

腳本都在 `scripts/`：`pxx/` 是函式庫，外面幾支是命令列工具。

| 檔案 | 做什麼 | 渲染量 |
|---|---|---|
| `selftest.py` | 環境檢查；`--load N` 量 N 個瀏覽器同時畫時整機的 CPU | 幾秒 |
| `slice_grid.py` | 把截圖切成（列, 欄）的格子，印每一欄的統計 | 不渲染 |
| `peek.py` | 看一格的像素（字元畫＋數值），可以跟一個候選字串並排比 | 一個字串 |
| `calibrate.py` | 校字型、字級、色調對照（`font`／`em`／`lut`／`check`） | 小 |
| `job_template.py` | 一批截圖的工作檔範本：複製到工作目錄、照欄位改 | 看欄位 |
| `pxx/synth.py` | 渲染。全機共用的同時上限、重試、逾時、完整性檢查都在這裡 | — |
| `pxx/grid.py`、`pxx/cut.py` | 取一格的像素；格子裡有圖示、按鈕時把字切出來 | 不渲染 |
| `pxx/match.py` | 誤差、校起始位置、窮舉候選、最後驗證 | — |
| `pxx/reader.py`、`pxx/discover.py` | 逐字讀取；一欄的閉環（已知詞 → 逐字讀 → 反套） | **重** |
| `pxx/badges.py`、`pxx/charset.py` | 用顏色分的欄位；字集（由小到大四層） | — |

## 流程

每一步都把結果存成檔案，下一步只讀檔案。哪一步斷了，就從那一步重跑。
第 3～7 步的程式在 `scripts/job_template.py`：複製到工作目錄改名 `job.py`，把 `COLMAP`、色票、候選、每一欄的字集改成這一批的，
然後 `python job.py status`、`closed`、`open <欄位> [分鐘上限]`、`assemble`、`verify` 一步一步跑。
它是範本不是框架 —— 每一批截圖的欄位都不一樣，直接改它。

### 1. 切格子、認欄位（不渲染）

```bash
python scripts/slice_grid.py <截圖資料夾或檔案…>
```

資料夾裡的圖照檔名排序；順序有意義（照時間）就把檔案一個一個照順序列出來。它印出每張圖的列數、列距、
背景色，以及每一欄的統計。**照這份統計一張一張認欄位**，寫成 `job.py` 裡的 `COLMAP`：

- 整欄只有一兩種樣子 → 固定值（是／否、性別、同一個經手人）。
- 每一格寬度都一樣 → 日期、時段、編號。
- 高度特別高、有飽和的顏色 → 徽章或圖示。
- **同一個欄位在每張圖的欄號常常不一樣**：整欄沒有字的那一欄不會被切出來，使用者每次捲動的位置也不同。
  表頭沒有被截進來的話，拿使用者手邊任何一張有表頭的照片對欄位順序。

切法的假設（列與列之間有分隔線、字靠左對齊）與不成立時怎麼改，寫在 `pxx/grid.py` 檔頭。

### 2. 校正：字型 → 字級 → 色調（`references/calibration.md`）

找幾格**內容確定**的格子當錨點寫進 `anchors.json`（放大後看得出來的日期、整欄相同的固定值、使用者親口說的字），
數字與中文各幾個，越長越好。然後：

```bash
python scripts/calibrate.py font              # 候選字型一個一個比
python scripts/calibrate.py em 5.0 6.0 0.05   # 掃字級（單位：截圖像素／em）；再用 0.005 的間隔細掃一次
python scripts/calibrate.py lut               # 擬合色調對照表
python scripts/calibrate.py em 5.30 5.36 0.005 && python scripts/calibrate.py lut   # 有了對照表再細掃一輪
python scripts/calibrate.py check             # 每個錨點都要 < 1.1
```

**`check` 沒有全部吻合就不要往下做。** 校正差一點點，後面每一步都是「差一點點對不上」，而你會把時間花在懷疑候選、
懷疑欄位、懷疑程式上。三個參數的敏感度（實測）：字級差 0.01 像素，12 個錨點就只剩 9 個吻合；
字型的 UI 版與一般版只差幾個數字的字形，誤差就差兩倍；色調對照表最多只修正 6 個灰階，沒有它卻是 0／12。
為什麼這麼敏感、每一個怎麼找、卡住時看什麼，都在 `references/calibration.md`。

### 3. 用顏色分的欄位

狀態徽章這種東西**量顏色，不要讀字**：`badges.colors()` 看有幾群，定好色票再 `badges.classify()`。
離每一種顏色都太遠的會標成 `?` —— 不要為了消掉問號去放寬門檻。徽章上的字放大後用看的確認一次（種類少，看得準），
並且在產出裡寫明「這一欄是看顏色分的」。

### 4. 候選列得完的欄位（便宜）

日期、時段、是／否、一份已知的品項清單 —— 候選全部列出來，窮舉。`job_template.py` 的 `closed_field()`：

- 每張圖每一欄先校**起始位置**（phase）：字的原點落在像素格的哪個小數位置，同一欄每一格都一樣。
- 候選分兩層：先給常見的幾百個，沒吻合的才換完整的那一份。
- 看結果時**第一名與第二名都要看**：第一名 < 1.1 而且第二名在 3 以上，才是乾淨的吻合。

### 5. 候選列不完的欄位：閉環挖掘（重 —— 先看下一節）

`discover.Field(...).run()`：已知詞彙先比 → 用吻合的格子校起始位置 → 比不到的挑一格**逐字讀** →
讀出來的新詞**馬上回頭套到所有圖的同一欄** → 再挑下一格。表格欄位的值會重複：讀一格幾十秒，
套一個詞到幾百格一兩秒，所以一欄通常讀十幾次就收完。

順序照「由便宜到貴」：數字欄（十個字的字集）→ 品項、房間這種詞少的 → 姓名 → 自由文字放最後。
字集也由小到大：`TEXT`（Big5 常用字＋ASCII＋標點，5,500 字）→ `TEXT_FULL`（加次常用字，13,000）→
`TEXT_ALL`（整個 CJK 基本區，21,000）。**人名、品牌名會用到 Big5 沒有的字** —— 症狀是第一個字就讀不下去、
幾秒就放棄；那不是字糊，是候選裡根本沒有那個字。

**自由文字（備註）另外三件事：** 短的先讀（`order='short'`）；一格讀到一半到時間上限會存檔，下次從那個字接著讀；
讀完一定要跑 `refine_suspects()` —— 整格誤差是平均，會把一個選錯的標點、一個長得很像的字蓋掉，
要看「最差的那一個字寬」才看得出來（實戰裡六個全形逗號被讀成了全形減號，整格誤差全部過關）。

設計、參數、成本怎麼算、讀不出來時怎麼判斷原因：`references/reader.md`。
格子裡混著圖示、按鈕、被欄寬截掉的字，要自己切：`references/recipes.md`。

### 6. 彙整、互相對

各欄是各自獨立讀的，它們之間的關係是**免費的檢查**：清單照時間排 → 讀出來的日期也要是遞增的；
一個編號只對一個名字、一個名字只對一支電話；時間都落在五分鐘的格子上。對不上的每一個都回頭逐像素確認：
要嘛是讀錯（修），要嘛是原圖真的那樣（留著，寫進報告的「值得注意的地方」）。

### 7. 最後一道：獨立驗證

只吃（那一格的像素, 讀到的字），每個字重畫再比一次，**不看任何中間結果**。
前面哪一步記錯格、套錯欄、存錯檔，在這裡都會現形。幾千格大約兩三分鐘。

- 一般的格子：`match.verify_local()`，每一格兩個數字 —— 整格誤差（< 1.1）與區域誤差（最差的那一個字寬，≤ 2.0）。
  實測：五千多格正確的短字串，區域誤差最大 1.43。
- 長字串（寬度超過 16 個字）：`reader.check()`，一步一步對。整格在同一個起始位置上比對長字串太嚴，會把對的判成錯的（`reader.md`）。

**這一步沒跑完，就不能說「全部驗證過」**；被打斷了就在報告裡照實寫「誤差是解碼當下的，獨立驗證沒有跑」。

### 8. 產出

- 一份機器讀的 JSON：一列一筆，每筆帶 `src`（哪張圖）、`row`（第幾列）、每個欄位的值、
  `_verify`（每一欄的誤差）、`_issues`（沒讀出的、只差一兩個像素的）。
- 一份給人看的 Markdown：逐筆清單、各欄出現過的值、**值得注意的地方**（同一人兩種寫法、對不起來的編號）、
  **沒讀出的格子**（每一格附哪張圖第幾列，讓使用者回原畫面查）。
- 一份 README：方法、每一欄可以信到哪裡（幾格吻合、幾格沒讀出、哪一欄是看顏色的）、還沒做的。

三份都放工作目錄旁邊、不進版控的地方。

## 先估再跑

渲染是這套方法的全部成本，而且很容易估錯一個數量級。**每一個會畫超過一分鐘的步驟，開跑前先算：**

```
磁磚數 ＝ 候選數 × 起始位置數          （窮舉）
       ＝ reader.estimate(字數, 字集)   （逐字讀一格；乘上「不同樣子」的格數）
秒數   ≈ 磁磚數 ÷ selftest.py 量到的每秒幾個
```

參考值（12 核筆電、兩個瀏覽器）：每秒 1,500～3,000 個磁磚。逐字讀一格：8 位數編號一兩秒；4～6 個字的品項半分鐘到一分鐘；
用整個 CJK 字集讀 4 個字約兩分鐘。**自由文字每個字 16～26 秒 —— 一則 30 個字的備註是 8～12 分鐘，十八則就是一兩個小時。**
`estimate()` 給的是下限（不含走到死路退回去的那幾步）。

規矩：

- **同時幾個瀏覽器是全機共用的上限**（`PXX_MAXPAR`，預設 2），鎖在作業系統那一層：開三個終端機各跑一個工作，
  加起來還是 2。不要繞過它，也不要為了「機器有 16 核」調大 —— 多開的收益遞減（1 個 → 2 個只快六成），
  而一個無頭 Chromium 就吃掉整機兩成多。
- **估出來超過十分鐘，先跟使用者講**：要畫多久、機器會用到幾成、有沒有便宜的替代（縮小字集、只讀重複最多的那幾種、
  請他回原畫面看那幾格、重截那幾列）。讓他選。超過十分鐘的用 `PXX_MAXPAR=1`，或再加 `PXX_DUTY=0.5`（畫多久停多久）。
- **重的步驟一律設時間上限**（`Field.run(max_minutes=10)`）。到了它會存檔收工，再跑一次從 log 接著做。
- **不要把工作丟到背景讓它「活過這個工作階段」**（`Start-Process`、`nohup`、`&`）。沒有人看著的滿載工作就是那兩次斷電的原因。
- 跑完看 `synth.stats()`：`repainted`（整頁重畫）、`timeouts`、`blank` 不是 0 就要知道為什麼。

## 卡住的時候

| 看到什麼 | 多半是 |
|---|---|
| 所有候選的誤差都在 2～6，沒有一個 < 1.1 | 校正還沒到位：字級差一點、少了色調對照、字型是另一個變體 |
| 大小就對不上（誤差 999） | 字級差很多、字型錯、或那一格混了圖示／被截掉 |
| 短字串吻合、長字串不吻合 | 字級：誤差沿著字串累積 |
| 一欄裡大部分吻合，少數幾格誤差 3～5 | 起始位置抽得太疏（用 `spread()` 不要用 `pick_phases()`），或那幾格前面多了圖示 |
| 逐字讀取第一個字就放棄、只花幾秒 | 那個字不在字集裡（換大的字集）；或起始位置的範圍校窄了 |
| 逐字讀取讀到一半莫名其妙斷掉，換一次跑又斷在別的地方 | 渲染那一側有空白的磁磚：看 `stats()` 的 `repainted` |
| 讀出來了，但誤差在 1.1～1.6 | 短字串：筆畫密的字會這樣，收，但標出來。長字串：看 `check()`，不要看整格誤差 |
| 長句讀出來了、字也通順，整格誤差在門檻內 | 還不能信。跑 `refine_suspects()`：選錯的標點與長得像的字只有區域誤差看得出來 |
| 長字串讀到二十幾個字突然斷掉 | 見 `reader.md` 第 7、8 點；先用 `prefix=` 從前一個字、`phs=None` 起步試一次 |
| 同一個編號對到兩個名字 | 先當成讀錯去查；逐像素確認兩個都吻合，才是原圖真的那樣 |
| 機器風扇狂轉、整機變慢 | 停。看是不是有別的行程也在畫；`PXX_MAXPAR=1` |

每一條的來龍去脈與其他五十幾個坑：`references/pitfalls.md`。**動手改腳本之前先讀它** —— 裡面每一條都是付過代價的。
