# 測試太慢的時候

2026-09-09 這個 repo 做過一輪：**CI 全量 21.7 分鐘 → 8 分 05 秒**，
日常驗收 21 分鐘 → 1~2 分鐘，**一支測試都沒刪、一個斷言都沒放寬，反而多了四個**。
這份是那一輪的方法與踩過的坑。全部過程在 `.scratch/e2e-speed/issues/`（01~07）。

## 鐵律三條，先讀

1. **先量，不要猜。** 這一輪我推估過兩個數字（「無頭快一倍 → 12 分鐘」、
   「分片省 60%」），兩個都錯，而且都被寫進文件才發現。**沒量過的數字不要寫進
   任何檔案。**
2. **拿掉墊子會露出東西，那是收穫不是災難。** 拿掉 `settled()` 那顆 350ms 之後
   八支紅了 —— 其中七支的根因是一個從第一天就在的缺陷。**紅了先問「它為什麼
   現在才紅」，不要急著把墊子加回去。**
3. **新的判準不可以比舊的寬鬆。** 把固定等待換成「等狀態」時，新作法最快回來的
   時間**不可以早於**原本那個固定秒數 —— 不然你換到的不是「比較準」，
   是「比較快而且比較容易錯」。

## 第一步：量，不要猜

Playwright 每次跑完都會寫 `.artifacts/results.json`。每一支的秒數在裡面：

```bash
node -e "
const r=JSON.parse(require('fs').readFileSync('.artifacts/results.json','utf8'));
const by={};function w(s,f){f=s.file||f;for(const sp of s.specs||[])for(const t of sp.tests||[])for(const x of t.results||[])by[f]=(by[f]||0)+x.duration;for(const c of s.suites||[])w(c,f);}
for(const s of r.suites||[])w(s);
for(const [f,d] of Object.entries(by).sort((a,b)=>b[1]-a[1]))console.log((d/1000).toFixed(1).padStart(7)+'s  '+f);
console.log('wall '+(r.stats.duration/60000).toFixed(1)+' 分鐘');"
```

**要單一測試的秒數就 `--reporter=list`**，它每一行都印。這一步不能跳 ——
`07-chaos` 看起來是「整支都慢」，量下去發現是**三個地方在等逾時**，其餘正常。

時間分成三個桶，先算出哪一桶最大：

| 桶 | 怎麼算 | 這一輪的值 |
|---|---|---|
| **每個測試的固定成本** | 最短那支的秒數 × 測試支數 | 3.5s × 193 ＝ **11 分鐘**（一半） |
| **空等** | `grep -o "waitForTimeout([0-9]*)" \| ...` 加總 | 217 個呼叫 ＝ **216 秒** |
| **全部都跑** | 全量時間 − 相關的那幾支 | 21 分鐘 vs 1~2 分鐘 |

## 第二步：照這個順序挑

順序是**投報率 ÷ 風險**，不是省下來的秒數。

| | 做什麼 | 這一輪的實際值 | 風險 |
|---|---|---|---|
| **① 分級** | 只跑跟這次改動相關的那幾支 | 21 分 → **1~2 分** | 低 |
| **② 無頭** | 拿掉 headed 與 `slowMo` | 66s → 18.6s（`00-smoke`） | 零 |
| **③ CI 分片** | 三台機器各跑三分之一 | 21.7 分 → **8 分 05 秒** | **幾乎零** |
| **④ 拿掉空等** | 固定等待換成等狀態 | 一支 spec 330s → 120s | 中，會露出真缺陷 |
| **⑤ 砍固定成本** | 登入只走一次、不要每次清空 | 每測試 −1 秒 ＝ −3.2 分 | 高 |
| **⑥ 同機平行** | `workers: N` | **沒做**（見下） | 高 |

**①②③ 先做完再碰 ④⑤。** 前三個不動任何共用的測試程式，壞掉最多就是 CI 紅。

### ① 分級是日常唯一有感的那一個

她一天驗收五次，全量二十分鐘 ＝ 兩小時。分級之後改一支 domain 模組只跑 4 支。

對照表要有**大聲的爛掉方式**：新增一支 spec 忘了登記要紅、路徑不存在要紅，
而且**認不出來的檔案一律退回全跑**。少列一條的代價是多跑幾支，
不可以是「那一支沒跑到而且看不出來」。

### ③ 分片 ≠ `workers`

- `workers: 3` ＝ 同一台機器三個瀏覽器，**共用一顆模擬器**。互相洗資料庫。
- `--shard=1/3` ＝ **三台機器**，各有自己的模擬器。沒有東西共用，沒有東西會撞。

**分片是繞過問題，不是解決問題。** 代價：只在 CI 有用（本機只有一台）。

**地板 = 開機成本 + 最大那一支 spec。** 分片切不開一個檔案。實測開機是 48 秒
（checkout / node / java / `npm ci` / 裝瀏覽器）。所以分再多片也快不過
「48 秒 + 最肥的那一支」。

什麼時候該加片：三個 job 差不多而最慢的 > 10 分鐘 → 加一片（一行）。
最慢那個是別人兩倍以上 → 加片沒用，去拆那支肥的 spec。

### ⑥ 為什麼沒做同機平行

隔離做好了（一個 worker 一個模擬器命名空間）也還有第二層：
**那顆 Firestore 模擬器是單一 Java 行程**，而且每個測試都從 CDN 重載一次
Firebase SDK。人越多搶越兇。CI 分片之後這件事的價值又掉一截 —— `workers: 1`
留著是對的。

## 第三步：把固定等待換成等狀態

`page.waitForTimeout(N)` 兩邊都錯：順的時候白等，慢一拍的時候讀到還沒重畫的
畫面。**兩種症狀都不指向那一行。**

| 在等什麼 | 換成 |
|---|---|
| 點一下之後有一層推上來 | 等那一層裡一定會有的東西 visible |
| 存檔 | 等 toast 離開「儲存中」（而且**寫失敗要丟例外**） |
| 一頁畫完 | 等佔位字消失 **而且** 內容連續 N 次沒變 |
| 丸子被按下 | `toHaveAttribute('aria-pressed', 'true')` |
| 摺疊打開 | `toHaveAttribute('open', '')` |
| 長按 | 按住直到選單出現再放手，不要按固定秒數 |

**兩種不要換**：
- 等的是真實時間本身（長按門檻、產品定義的逾時）
- **要證明某件事沒有發生** —— 這種一定要找到一個「該發生的事」可以等
  （例如「沒有確認框就是直接寫下去」→ 等那次寫入結束，然後才斷言沒有確認框）。
  找不到就**留著那個固定等待**，並在那一行寫出理由。

用一張只准變短的豁免表管進度（`tests/e2e-waits.test.js` 的 `PENDING`），
清完一支就把那一列刪掉 —— 留著 0 等於留一個可以偷偷長回去的位子。

## 踩過的坑，一個都不要再踩

**`.catch()` 會把逾時吞掉，看起來只像「這支就是慢」。**
`07-chaos` 的連點測試，第 2~5 下點在已經消失的按鈕上，每一下燒滿 15 秒
`actionTimeout` ＝ 一支 60 秒。**一支測試莫名其妙慢，先找 `.catch()`。**

**「畫完了沒」的判準漏掉一種佔位字。**
`settled()` 只認得「載入中…」，而資料健檢那一頁用「掃描中…」。症狀是斷言讀到
那三個字，而錯誤訊息長得像 app 壞了。**要用測試掃原始碼盯這張表** ——
那道守衛自己又抓出兩個沒人知道的（其中一個在壓表那一頁）。
只找畫進標籤裡的（`<p class="muted">X中…</p>`），toast 那一族不算。

**同一件事在兩個入口的選擇器不一樣。**
壓表是 `[data-ivproduct]`，來訪編輯器是 `[data-chip="s0-iv"]`。等錯一個不存在的
選擇器，症狀是跑滿 15 秒然後紅在一句無關的斷言上。**每改一支都要真的跑那一支。**

**`git diff --name-only` 會把中文路徑轉成八進位跳脫。**
`"docs/\345\270\270..."` 對不上任何規則，於是分級每次都退回全跑，而畫面上只寫
「沒有登記」。一律帶 `-c core.quotepath=false`。

**`upload-artifact@v4` 預設排掉隱藏檔。**
`.artifacts/` 是點開頭的目錄 → **失敗證據從來沒有上傳過**，而且那一步是**綠的**
（只印一句 warning）。要 `include-hidden-files: true`。
**這種「綠著失敗」的步驟只有在真的紅過一次時才驗得到** ——
所以驗分片的時候要故意弄壞兩份，那是唯一能同時證明「名字不撞」與「真的有上傳」的組合。

**本機的秒數不能拿來比較。**
同一份程式在同一台機器上跑出過 16.5 分鐘也跑出過 21.3 分鐘，差 30%。
**要比就用 CI 的數字**，或者比單一 spec 的秒數。

**Windows 的 CRLF 會讓掃原始碼的測試假紅。**
`core.autocrlf=true` 讓新 checkout 出來的檔案是 CRLF，而掃原始碼的樣式帶著
換行符，永遠對不上。CI 在 Linux 上永遠是綠的。`.gitattributes` 一行
`* text=auto eol=lf` 解決。

**命名空間對不上的症狀是「畫面全空，沒有錯誤訊息」。**
因為「空的資料庫」跟「這位客戶本來就沒資料」長得一樣。所以動隔離機制之前，
**先做一支會大聲的檢查**（問 app「你讀的是哪一個命名空間」，對不上就丟例外），
再動設定。沒有它就只能猜，而猜著猜著會加一層「先等兩秒再試」——那才是補丁。

## 什麼時候停

**量出來不值得就關掉那個念頭，把數字寫下來。** 這一輪的「一個測試一個命名空間」
量完是省 7 秒（全套的 0.6%），代價是動全套最深的共用 fixture ——
關掉，把量到的寫進 issue。**那是正確結果，不是沒做完。**

判斷還有沒有得壓：

```
地板 = 開機成本 + 最大那一支 spec
```

離地板還遠就繼續，接近了就停。

**而且要分清楚你在優化誰的時間。** 日常那一段（分級）是她一天碰五次的；
全量是 CI 在跑的。①做完之後，剩下的都是在優化一個「按一下就丟給 CI」的東西 ——
**那時候該回去做功能了。**
