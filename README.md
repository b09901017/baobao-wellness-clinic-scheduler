# baobao-wellness-clinic-scheduler

> 健康管理師個人排課系統：客戶次數追蹤、壓表排程、系統掛號待辦。
> 手機／iPad PWA + Firebase，取代白紙與 Google 試算表。

---

## 這是什麼

一位健康管理師每天要幫二十幾位客戶安排療程課程。她的流程是：LINE 問時間 → 寫在白紙上 → 坐到公司電腦前壓表 → 再問客戶可不可以 → 記進 TimeTree 和 Google 試算表 → 客戶來之前還要到另外幾個系統掛號。

中間所有的「誰回覆了沒」「這個人還剩幾次」「他哪天不能來」「哪個系統還沒登記」，全部記在腦袋裡。

**這個 app 就是那顆腦袋的外接硬碟。**

## 為什麼沒有桌機版

因為公司的電腦連不了外網 —— 這個 app 在那台電腦上打不開。

實際的使用姿勢是：**一手拿自己的裝置看 app，一手在公司電腦上操作公司的預約系統**。載具只有 Android 手機和 iPad，各約一半。

這決定了整個 UI：全觸控、無 hover、無拖拉；把判斷所需的資訊一次攤開，她自己決定後在公司系統上輸入，回來只要快速記錄。

手機負責走動時的待辦勾選和臨時查詢，iPad 負責坐下來的壓表作業和資料整理。但**不做兩套 app、也不做只有某台裝置能用的功能** —— 同一組元件三段斷點，iPad 只是看得更多。壓表進度存在雲端，壓到一半換裝置接著做。

## 為什麼不用現成的預約系統

因為問題不在「預約」，在**排班前的決策**和**排班後的收尾**：

- 公司的預約系統只管時段有沒有被佔走，不知道這位客戶的復能還剩幾次、他這個月哪幾天出國、他體內有金屬所以不能用超磁場。
- 試算表可以記次數，但記不住狀態 —— 壓了表但客戶還沒回覆的那段空窗，是最容易掉東西的地方。
- 一次壓十幾個人，每個人後續要做的系統登記都不一樣，來不及一一記錄。

這不是預約系統，是**決策支援 + 待辦收尾**工具。壓表本身仍然在公司系統上做。

## 核心功能

**壓表模式**
選定課程後，把判斷所需的資訊一次攤開：可用日、剩餘次數、喜好、限制原文。系統依「可用天數最少 › 喜好 › 急迫度」排序，並把理由攤成人話標籤，但那只是預設順序，她隨時可以跳著處理。**不出建議時段** —— 判斷是她的，app 只負責把資訊攤開與記錄結果。

**來訪編輯器**
排班的單位是「某人某天來一次」，一次含 2–3 個連續時段。體內金屬等醫療禁忌會直接鎖掉不能選的器材 —— 那是唯一的硬性阻擋。診間與治療師衝突只提示不阻擋，因為 app 看不到同事在 Abovee 上壓了什麼。

**待辦中心**
每筆來訪自動產生對應的系統任務，依死線排序，逾期變紅。客戶改時間時自動產生「回去取消舊登記」的任務。

**時段反查**
臨時空出一格時，輸入時段，系統推薦誰可以補。

**次數三段式**
不再只有「已排」一個數字，而是 `已完成 / 已排未上 / 剩餘`，並在來訪真正發生後才扣。

**日曆**
日／週／月三種檢視，取代 TimeTree。只顯示她自己排的來訪 —— 同事在 Abovee 上壓的看不到，所以空的格子不等於那個時段真的空著。

**LINE 訊息**
問這輪的時間、問壓好的時間可不可以、來訪前提醒、臨時空一格的邀約，四種草稿一鍵複製。打錯一個日期就是白跑一趟。

## 資料是不能弄丟的

這是內部工具，但處理的是客戶的療程次數和健康資訊，錯一筆就是實際損失。所以：

- **永不硬刪除** —— Security Rules 直接禁止 delete，刪除只是標記
- **全量稽核紀錄** —— 每次寫入都留 before/after，可回溯
- **關鍵操作可復原** —— 手機單手操作最容易誤觸
- **資料健檢頁** —— 定期對帳次數、找孤兒資料、抓狀態異常，發現問題顯示差異而不自動偷改
- **雙層驗證** —— 前端擋一次，Firestore Rules 再擋一次
- **試算表唯讀** —— 它現在是報表不是資料來源，由 app 產生後貼回去，不做雙向同步

## 技術棧

| | |
|---|---|
| 前端 | 原生 HTML / CSS / JS，PWA，觸控優先響應式（<600 / 600–899 / ≥900） |
| 後端 | Firebase（Firestore + Auth + Security Rules + Hosting） |
| 部署 | Firebase Hosting，GitHub Actions 自動部署（push 即上線） |
| 舊系統銜接 | app 產生與現行試算表同構的報表，複製或下載後貼回去。單向，不做 Apps Script 定時同步（ADR-0010） |

刻意不用 React、不用 build pipeline。維護者只有一個人，能直接看懂原始碼比較重要。

程式碼分三層：`/data`（只有這裡碰 Firestore）、`/domain`（純函式業務規則）、`/ui`。規則不寫在事件處理器裡。

## 開始開發

沒有 build 步驟，也沒有相依套件。

```
npm test                    # 跑 domain 純函式測試與分層守衛
npx firebase-tools emulators:start   # 本機跑 Auth + Firestore + Hosting
```

第一次要做三件事，都在 Firebase Console：

1. 建專案，把前端 config 填進 `public/js/firebase-config.js`（那串不是密鑰，可以 commit）
2. `.firebaserc` 填專案 ID
3. 開 Google 登入，然後在 Firestore 手動新增一份空文件 `allowedUsers/{你的 uid}` —— 沒有這步，登入了也讀不到任何資料

自動部署需要一個 repository secret：`FIREBASE_SERVICE_ACCOUNT`（服務帳號 JSON 全文）。push 到 main 就會跑測試並上線。

那個服務帳號還需要在 Google Cloud IAM 加上 **Firebase Rules Admin** 與 **Cloud Datastore Index Admin** 兩個角色，否則 Rules 與索引會部署失敗（預設角色只夠讀寫資料）。

## 隱私

資料含客戶健康資訊。

**Repo 私有不等於網站私有** —— 部署出去的站是公開網址，前端程式碼人人可看。真正的防線是 Firebase Auth + Firestore Security Rules，判準只有一條：沒登入的人查不到任何一筆資料。

- Firebase 前端 config 可以 commit，那不是密鑰
- **Service account 金鑰、任何含真實客戶資料的匯出檔或截圖，絕對不能 commit** —— 進了 git 歷史就拿不掉了
- Rules 絕不使用測試模式的全開規則，並用 Emulator Suite 寫測試驗證

細節見 [`SPEC.md`](./SPEC.md) 技術棧章節。
