# baobao-wellness-clinic-scheduler

> 健康管理師個人排課系統：客戶次數追蹤、壓表排程、系統掛號待辦。
> 手機／iPad PWA + Firebase，取代白紙與 Google 試算表。

---

## 這是什麼

一位健康管理師每天要幫二十幾位客戶安排療程課程。她的流程是：LINE 問時間 → 寫在白紙上 → 坐到公司電腦前壓表 → 再問客戶可不可以 → 記進 TimeTree 和 Google 試算表 → 客戶來之前還要到另外幾個系統掛號。

中間所有的「誰回覆了沒」「這個人還剩幾次」「他哪天不能來」「哪個系統還沒登記」，全部記在腦袋裡。

**這個 app 就是那顆腦袋的外接硬碟。**

## 為什麼沒有桌機版

因為公司的電腦連不了外網 —— 這個 app 在那台電腦上打不開。

實際的使用姿勢是：**一手拿自己的裝置看 app，一手在公司電腦上操作公司的預約系統**。載具只有 Android 手機和 iPad，各約一半。

這決定了整個 UI：全觸控、無 hover、無拖拉；把判斷所需的資訊一次攤開，她自己決定後在公司系統上輸入，回來只要快速記錄。

手機負責走動時的待辦勾選和臨時查詢，iPad 負責坐下來的壓表作業和資料整理。但**不做兩套 app、也不做只有某台裝置能用的功能** —— 同一組元件三段斷點，iPad 只是看得更多。壓表進度存在雲端，壓到一半換裝置接著做。

## 為什麼不用現成的預約系統

因為問題不在「預約」，在**排班前的決策**和**排班後的收尾**：

- 公司的預約系統只管時段有沒有被佔走，不知道這位客戶的復能還剩幾次、他這個月哪幾天出國、他體內有金屬所以不能用超磁場。
- 試算表可以記次數，但記不住狀態 —— 壓了表但客戶還沒回覆的那段空窗，是最容易掉東西的地方。
- 一次壓十幾個人，每個人後續要做的系統登記都不一樣，來不及一一記錄。

這不是預約系統，是**決策支援 + 待辦收尾**工具。壓表本身仍然在公司系統上做。

## 核心功能

**壓表模式**
一批是一個月的一串客戶，不是一個課程 —— 她面對的是公司系統上的一張時段表，看到空的就搶，而且習慣把一個客人的所有課程壓完再換下一個人。卡片上最大的一塊是「不能的時間」（只有解析出來的條件，原文收在一摺裡），旁邊是各課程剩餘次數、這個月與上個月來幾次、特殊備註。可用性照**壓的那個月**挑，那個月沒問過就寫「還沒問 9 月的時間」。記錄用小日曆挑日子（他說不行的紅色劃掉、你休假的霧藍、已經過去的變淡），課程、時段、器材、治療師、診間全部用點的，而且**選一個東西不會重畫整頁**。

系統依「可用天數最少 › 喜好 › 急迫度」排序，並把理由攤成人話標籤，但那只是預設順序，她隨時可以跳著處理，也可以整個換一種排法（喜好、剩最多次、最久沒來、問到時間的先）或直接搜尋姓名。**不出建議時段** —— 判斷是她的，app 只負責把資訊攤開與記錄結果。

**來訪編輯器**
排班的單位是「某人某天來一次」，一次含 2–3 個連續時段。體內金屬等醫療禁忌會直接鎖掉不能選的器材 —— 那是唯一的硬性阻擋。診間與治療師衝突只提示不阻擋，因為 app 看不到同事在 Abovee 上壓了什麼。

**待辦中心**
首頁只放分類與數字，完整內容點進去看。每筆來訪自動產生對應的系統任務，依死線排序，逾期變紅。客戶改時間時自動產生「回去取消舊登記」的任務。

壓表記完之後會長出「跟客人確認時間」：按打勾跳出確認畫面，把這個人所有時段攤開，客人說哪幾段不行就逐筆退回，其餘照樣成立並排進日曆。另外有**隨手記**收客人的零碎小要求，可勾掉、可掛在某位客戶身上。

**時段反查**
臨時空出一格時，輸入時段，系統推薦誰可以補。

**次數三段式**
不再只有「已排」一個數字，而是 `已完成 / 已排未上 / 剩餘`，並在來訪真正發生後才扣。

**二返**
健檢做完之後要再約一次回院聽報告。買幾次健檢就有幾次二返，所以它有自己的額度，
跟著健檢的額度成對建出來；健檢那一筆標成已完成就長出「約二返」的待辦，
死線是健檢日往後算（預設 7 天，設定頁可調），約掉了就自己收起來。
**系統不會自動幫她約** —— 時間是她跟客戶談出來的。

**日曆**
日／週／月三種檢視，**可以直接編輯**，取代 TimeTree。上面有兩種東西：**來訪**（綁客戶、產生任務、扣次數）與**個人行程**（公出、休假、演講，不綁客戶，可以跨天）。月檢視把跨天的東西畫成橫跨格子的色條。

只顯示她自己排的來訪 —— 同事在 Abovee 上壓的看不到，所以空的格子不等於那個時段真的空著。

**兩條匯入路**
舊試算表貼上就能匯（來訪只有日期，時間欄位刻意留空）。另一條是**合併檔**：
`.claude/skills/calendar-sheet-merge` 這支 skill 把試算表與 TimeTree 行事曆對照過，
補上時間、診間、治療師與器材，並且把兩邊對不起來的地方全部列出來 ——
行事曆記了卻忘記回試算表打勾是最常見的一種，而它在試算表上看不出來。
產出的 JSON 貼進「設定 → 合併檔匯入」就寫得進去。

**LINE 訊息**
問這輪的時間、問壓好的時間可不可以、來訪前提醒、臨時空一格的邀約，四種草稿一鍵複製。打錯一個日期就是白跑一趟。

## 資料是不能弄丟的

這是內部工具，但處理的是客戶的療程次數和健康資訊，錯一筆就是實際損失。所以：

- **永不硬刪除** —— Security Rules 直接禁止 delete，刪除只是標記
- **全量稽核紀錄** —— 每次寫入都留 before/after，可回溯
- **關鍵操作可復原** —— 手機單手操作最容易誤觸
- **資料健檢頁** —— 定期對帳次數、找孤兒資料、抓狀態異常，發現問題顯示差異而不自動偷改
- **雙層驗證** —— 前端擋一次，Firestore Rules 再擋一次
- **試算表唯讀** —— 它現在是報表不是資料來源。app 產生後貼回去，或讓 app 自動推過去；在試算表上改的東西會被當場還原，不做雙向同步

## 技術棧

| | |
|---|---|
| 前端 | 原生 HTML / CSS / JS，PWA，觸控優先響應式（<600 / 600–899 / ≥900） |
| 後端 | Firebase（Firestore + Auth + Security Rules + Hosting） |
| 部署 | Firebase Hosting，GitHub Actions 自動部署（push 即上線） |
| 舊系統銜接 | app 產生與現行試算表同構的報表，可以複製貼回去，也可以讓 app 自動推給試算表的 Apps Script 排版上鎖。**單向** —— Apps Script 只收不取，那一側沒有任何憑證（ADR-0010、ADR-0013） |
| 客戶那一頁 | `/form.html`，獨立入口，不載 app 也不註冊 service worker。整份 Rules 裡唯一讓未登入的人寫得進來的地方，四道限制見 `firestore.rules` 的「客戶自己填的時間」與 ADR-0031 |

刻意不用 React、不用 build pipeline。維護者只有一個人，能直接看懂原始碼比較重要。

程式碼分三層：`/data`（只有這裡碰 Firestore）、`/domain`（純函式業務規則）、`/ui`。規則不寫在事件處理器裡。

## 開始開發

沒有 build 步驟，也沒有相依套件。

```
npm test                    # 跑 domain 純函式測試與分層守衛
npx firebase-tools emulators:start   # 本機跑 Auth + Firestore + Hosting
```

第一次要做三件事，都在 Firebase Console：

1. 建專案，把前端 config 填進 `public/js/firebase-config.js`（那串不是密鑰，可以 commit）
2. `.firebaserc` 填專案 ID
3. 開 Google 登入，然後在 Firestore 手動新增一份空文件 `allowedUsers/{你的 uid}` —— 沒有這步，登入了也讀不到任何資料

自動部署需要一個 repository secret：`FIREBASE_SERVICE_ACCOUNT`（服務帳號 JSON 全文）。push 到 main 就會跑測試並上線。

那個服務帳號還需要在 Google Cloud IAM 加上 **Firebase Rules Admin** 與 **Cloud Datastore Index Admin** 兩個角色，否則 Rules 與索引會部署失敗（預設角色只夠讀寫資料）。

2026-08-21 第一次拿**真實資料**跑完整條匯入路（開新試算表 → 貼 `.gs` → 清空
Firebase → 載入種子資料 → 設好推送網址 → 貼合併檔）。流程本身是對的，
但四個地方在真資料上壞掉了，梳理與待辦在 `.scratch/first-real-import/`：

- 試算表推送每一次都在丟例外（凍結欄切到合併儲存格），而**自動推送把錯誤吞掉了** ——
  兩件事分兩支修：例外本身，以及「推不出去要在設定頁講出來」
- 匯入分不出「已經來過」和「還沒來」：舊表上未來的預約也有打勾，那一格在她的
  用法裡是「排了」不是「來了」。改成依匯入當下的日期決定狀態
  （[ADR-0029](./docs/adr/0029-imported-visits-take-their-status-from-the-date.md)），
  而未來那幾筆會照 ADR-0027 長出登記待辦 —— 那些事是真的還沒做
- 候選清單改成**先分時間再分來源**（還沒發生的／已經發生的），未來的預設勾起來
  （[ADR-0030](./docs/adr/0030-future-candidates-are-ticked-by-default.md)）；
  對得上兩位客戶的那幾筆從此看得到
- 跨天的行事曆事件匯不進來：skill 的 `parseIcs()` 從來沒讀過 `DTEND`

**這一輪五件事有四件的共同點是「東西不見了，而畫面上什麼都沒說」。**
所以每一支修的除了行為本身，還有「講出來」那一半：推送失敗留得下痕跡、
`ambiguous` 有地方看、讀不出來的行事曆事件會列進報告。

梳理與待辦在 `.scratch/schedule-polish/`：

- 點一顆丸子就整頁重畫，「像重新整理一樣，閃一下並且回到最上面」——
  改成事件委派 + 只重畫真的變了的那一塊
  （[ADR-0038](./docs/adr/0038-picking-an-option-does-not-repaint-the-page.md)）
- **壓八月的表卻吃到九月那一份可用性**，交集是空的，於是一位只是「還沒問」的客戶
  帶著假的「可用 0 天」排到第一位。可用性改成照壓的那個月挑
  （[ADR-0036](./docs/adr/0036-availability-is-picked-by-the-month-being-scheduled.md)）
- 卡片上只留條件丸子，原文收進一摺 —— 現在幾乎每一份都是表單產生的，
  那段原文跟丸子講的是同一件事
  （[ADR-0035](./docs/adr/0035-the-wall-shows-rules-not-the-raw-answer.md)）
- 小日曆的米色太不明顯：他說不行改成紅色劃掉，你休假是霧藍，已經過去的才是淡的
- 卡片牆多了搜尋框與可切換的排法，但那幾種都只是同一份名單的重排，不是第二套計分
  （[ADR-0037](./docs/adr/0037-the-wall-can-be-re-sorted-but-never-re-scored.md)）
- 標題寫成「9月壓表」—— 她講的是「九月的表」，不是「2026-09 的表」

`quick-capture/`：

- **壓表的小日曆把半天丟掉了。** 客戶在表單上點「只有上午不行」、解析器讀懂了、
  `dayStatus()` 也算得出 `blockedPart` —— 只有 `miniCal()` 沒有接它，
  所以那件事在她唯一要用到的那一格上長得跟沒事的日子一模一樣。改成被擋的那半邊
  塗紅、寫上「上午」或「下午」並劃掉那兩個字，數字擠進還可以排的那半邊
- **「休假」與「已確認的來訪」本來是同一個 `#5b7a8c`** —— 兩件事的意思相反而畫面
  一模一樣。日曆上要分辨的是六種東西，而借用語意色只借得到四五個
  （[ADR-0039](./docs/adr/0039-six-things-on-the-calendar-need-six-colours.md)）。
  休假不搶第六個色相，改用灰青加斜線紋。個人行程還可以自己挑顏色，
  但休假的斜線不跟著換
  （[ADR-0040](./docs/adr/0040-a-personal-event-picks-its-own-colour.md)）
- **月檢視色條的省略號拿掉了。** 11px 的字裡那顆「…」吃掉快兩個中文字，
  換來的資訊是「還有字」，而她本來就知道。文字改成放得下就置中、放不下靠左從右邊切
- **一次建立一群客戶**（`#/customers/bulk`）：一場顧客會來了八位，
  購買通路、購買日、方案填一次，底下只打名字（貼一串會自己拆開），
  需要的那幾位才「微調」數量、不套方案、加購單項。加購跟方案走同一個 commit，
  所以「方案 + 健檢」買到的健檢**連二返一起長得出來**（ADR-0022）
- **待辦首頁右下角一顆鉛筆泡泡**：「三秒內記完」要從她掏出手機開始算，
  不是從捲到底開始算。點下去鍵盤自己上來，送出之後不關也不重畫 ——
  重畫會把輸入框那個節點換掉，等於把鍵盤收起來再叫一次

**這一輪有六個問題是只有把畫面真的畫出來才看得到的**（`npm test` 全綠、
程式碼讀起來也對）：劃掉的線壓在數字上、「上午」兩個字印在下半格、
`openSheet()` 同步呼叫 `onMount` 造成的 TDZ、`update()` 讓監聽疊成兩層、
`.fab__menu { display: flex }` 蓋掉 `[hidden]`、`display: flex` 的 `summary`
吃掉 `::marker`（那個展開三角形從來沒出現過）。

## 隱私

資料含客戶健康資訊。

**Repo 私有不等於網站私有** —— 部署出去的站是公開網址，前端程式碼人人可看。真正的防線是 Firebase Auth + Firestore Security Rules，判準只有一條：沒登入的人查不到任何一筆資料。

- Firebase 前端 config 可以 commit，那不是密鑰
- **Service account 金鑰、任何含真實客戶資料的匯出檔或截圖，絕對不能 commit** —— 進了 git 歷史就拿不掉了
- Rules 絕不使用測試模式的全開規則，並用 Emulator Suite 寫測試驗證

細節見 [`SPEC.md`](./SPEC.md) 技術棧章節。
